# 業務の概要

## 目的と業務の領域

`tag-refactor` は、AWS のアカウントのタグを整える、利用者の端末で動かすコマンドラインのツールです(Go、モジュール `github.com/yucn6201g/tag-refactor`、公開済みの版は `v0.1.0`)。サーバーには配置しません。

扱う課題は、同じ意味のタグのキーや値が、チームやスタックごとに違う書き方(`env`、`Env`、`environment` など)で付いていることです。書き方がばらばらだと、コストの配分、権限の条件(`aws:ResourceTag/...`)、検索が正しく働きません。ツールは次の順で課題を解きます。

1. 調べる(`scan`): 全リージョンのタグを読み、書き方の違うキー、必須タグの欠落、一度もタグが付いていないリソースを示す。
2. 決める(`rules suggest`、ルールファイル): 正しいキー名、別名、値の書き方、必須タグ、消すキーをルールファイル(YAML)に書く。下書きは今のタグから作れる。
3. 計画する(`plan`): ルールファイルから変更案(キー名の変更、値の変更、必須タグの追加、削除)を作り、変わるタグを参照する IAM とリソースポリシーを「影響あり」「判定できない」として示す。変更案はファイルに保存できる(`--out`)。
4. 書き換える(`apply`): 変更案のとおりに AWS のタグを書き換え、書き換える前のタグを記録に残す。
5. 取り消す(`rollback`): 記録をもとに、`apply` で書き換えたキーを元に戻す。
6. ソースをそろえる(`iac`): 変更案を CloudFormation のテンプレートと Terraform の `.tf` に反映し、次に IaC を適用したときにタグが元に戻らないようにする。AWS を呼ばない。

## 主な利用者と使い方

- 利用者は、AWS アカウントのタグの方針を持つ運用者やプラットフォームの担当者です。認証情報は AWS の SDK の標準の方法(環境変数、共有の設定、SSO)で読み、ツール自身は認証情報を受け取りません。
- 表示は英語と日本語(`--lang`、または `LC_ALL`/`LC_MESSAGES`/`LANG`、Windows の表示言語)で、標準出力には結果だけ、標準エラーには進み具合や案内を出します。結果の形式は `table`、`diff`、`json`、`markdown`(`plan`)で、Markdown はプルリクエストや Wiki に貼る用途です。
- 終了コードは 0(問題なし)、1(エラーや不完全)、2(人の確認が要る)で、スクリプトや CI から判定できます。

## 主な機能と業務の決まり

| 機能 | 業務の決まり(抜粋) |
|---|---|
| 読み取りだけのコマンド | `scan`、`plan`、`rules suggest` は書き込みの口を持たない(型で保証)。`aws:` で始まるキーは対象にしない |
| 影響分析 | IAM の管理ポリシー(付いているもの、権限の上限)とインラインポリシー、S3・KMS・SQS・SNS・Secrets Manager のリソースポリシーを照合する。影響があり得る参照を「影響なし」にはしない |
| 書き換え | `yes` の入力か `--yes` が要る。影響のある変更は `--allow-impact` がないと `--yes` でも止まる。書き換える前に記録を保存し、保存できなければ書き換えない。同じアカウントの同時実行は印で防ぐ |
| 取り消し | `apply` が触れたキーだけを比べて戻す。`apply` のあとに変えられたリソースは `--force` がない限り飛ばす |
| IaC への反映 | 既定は差分だけ。`--write` は、`--dir` が git の作業ツリーで、書き換えるファイルがコミット済みで変更がないときだけ書く。変えるのはキーと値の範囲だけで、式やアンカー、モジュール、`count`/`for_each` などは「手で直す一覧」に出す |

## 今回の意図との関係

進行中の意図 `iac-cdk-pr` は、`iac` に次の2つを足すものです。

- CDK(TypeScript と Python)のソースへのタグの変更の反映。今は CDK で作ったリソースは論理 ID がテンプレートに見つからず、理由 `templateNotFound` で手で直す一覧に出ます(`internal/display/iac.go` の文にも「CDK は後の作業」とある)。`cdk.out` のフォルダーは探しません。
- 反映した変更からの GitHub のプルリクエストの作成(利用者の `gh` と `git` を使う)。今の `iac` は git を読み取り(`rev-parse`、`ls-files`、`ls-tree`)にしか使わず、コミット、push、`gh` の呼び出しはありません。

README の「まだできないこと」と「iac の限界」の節が、この2つを後の作業として明記しています。

## 対象外と制約

- `iac` は `default_tags`、スタックのタグ、変数、モジュールを追いかけません。
- IAM のロールとユーザーはタグ付けの API が返さないため `scan` で集まらず、変更案に入りません。
- CI は実際の AWS を呼ばず、検証用アカウントでの確認は手元の `scripts/verify.sh` だけで行います。
- 公開は人が `vX.Y.Z` のタグを付けて push したときだけで、配り方は GitHub Releases と `go install` です(チームの方針)。

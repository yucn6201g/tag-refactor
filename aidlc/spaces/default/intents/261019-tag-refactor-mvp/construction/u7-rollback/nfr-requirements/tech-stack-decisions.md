# 技術の選択と、性能・移植性・保守性の要件: U7 取り消し

U1〜U6 の技術の選択(Go、AWS SDK for Go v2、cobra、`golang.org/x/sync`、`golang.org/x/term`)はそのまま使います。U7 で新しく足すライブラリはありません。ここでは、U7 で使う部品と、書き戻しの速さ、3つの OS で動くこと、テストの要件を決めます(U7 は `library` の作業単位で、性能の要件のファイルを別に作らないため、ここに置きます)。

出典: 要件 NFR1、NFR5、NFR9、NFR10、機能設計(`construction/u7-rollback/functional-design/`)、契約 C4・C6・C10・C12、`nfr-requirements-questions.md` Q2、Q3、Q5、U6 の NFR 要件(NFR5.12〜NFR5.17、測る条件)。

## 技術の選択

| 用途 | 選ぶもの | 理由 |
|---|---|---|
| タグの読み取りと書き込み | U6 の AwsAccess の口(ARN を指定した `GetTags`、TagWriter の `TagResources`・`UntagResources`) | 再試行、時間の上限、`aws:` の防御、失敗の分け方(状態コードが先)を U6 と同じにできる |
| リージョンの同時の数、止め方、一時的な失敗の数え方、書き込みの順番 | U6 の `internal/apply` の部品(リージョンの役、止める役、数え役、付けるのが先・途中だけ50を超えるなら消すのが先の書き方)を、apply と rollback の両方が使える形にして使う。同じ役割の部品を別に作らない | 2段の止め方、一時的な失敗の数え方、書き込みの順番を apply と同じにでき、テストも共有できる。ただし、まとまりと読み直しの単位の作る順は apply と違う(下の「書き戻しの進め方」)。apply の作り方は変えず、U6 の NFR5.13 のテストはそのまま通る。部品の分け方は NFR の設計で決める |
| 記録、印、ログファイル | U6 の `internal/journal`(壊れない保存、5秒ごとの保存、印、ログ)に、rollback の結果の3つの呼び出し(契約 C10)と、知らない項目を生の JSON のまま持つ読み込みを足す | 保存の仕方と印を apply と同じにできる(セキュリティの要件 NFR6.3) |
| 確認の入力、端末かどうか、Ctrl+C | U6 と同じ(`golang.org/x/term`、`os/signal`、`context`) | 機能設計 BR4.2〜BR4.4、BR5.5 |

## 書き戻しの進め方(要件の前提)

rollback では、付けるタグと消すキーが今のタグから決まり(機能設計 BR3.4)、読み直しのたびに求め直します(機能設計 BR5.6)。そのため、apply(まとまりを変更案から先に作り、それを束ねて読み直しの単位にする)と順を変え、次の順にします。

1. **読み直しの単位を先に切る:** リージョンごとに、判定する項目を ARN の順に並べ、100個ずつに切る。リージョン r の単位の数は R(r) = ⌈N(r) ÷ 100⌉。
2. **単位ごとに読み直す:** 書く直前に、単位の項目の今のタグを `GetResources` で1回読み(機能設計 BR5.6)、判定し直して、付けるタグと消すキーを求める。
3. **単位の中でまとめる:** 単位の中で、付けるタグの組み合わせ(キーと戻す値)と消すキーの組み合わせがまったく同じ項目を、20個までまとめる。まとまりは単位をまたがない。1つのまとまりに、付ける呼び出し1回と消す呼び出し1回(それぞれ、あれば)を使う。
4. **単位ごとに読み戻す:** 単位のすべてのまとまりを書いたあと、`GetResources` を1回呼んで読み戻す(機能設計 BR5.3)。値が違った項目があれば、その項目だけを最大3回読み直す(NFR5.24)。
5. **同時の数:** リージョンは同時に4つまで。1つのリージョンの中は単位を順に処理する。数は固定で、利用者は変えられない(Q2)。

| NFR5.18 | rollback の読み取りと書き込みも、U2 の AwsAccess の時間の上限、再試行、回数の上限に当たったときの待ちを通し、`TagResources`・`UntagResources` の答えのリソースごとの失敗は U6 と同じに分ける(U6 の NFR5.12)。呼び出し側は再試行しない(契約 C6) | U6 の NFR5.12 のテストが、rollback から呼んだ場合にも通る(同じ部品を使うことを、rollback の偽の AWS のテストで確かめる) |
| NFR5.19 | 書き戻しは、上の「書き戻しの進め方」のとおりに、読み直しの単位(100以下、ARN の順に先に切る)、単位の中のまとまり(20以下)、リージョン4つまでの同時、リージョンの中は順で行う(Q2) | 偽の AWS で、1回の書き込みの項目が20を超えないこと、組み合わせの違う項目が同じ呼び出しに入らないこと、1つの呼び出しに2つの単位の項目が入らないこと、1回の `GetResources` の ARN が100を超えないこと、同時に動くリージョンが4を超えないこと、1つのリージョンの中で呼び出しが重ならないことを数えるテストが通る |
| NFR5.20 | rollback の呼び出しの回数は、次の式の上限以下である。記号: N(r) = リージョン r の判定する項目の数、R(r) = ⌈N(r) ÷ 100⌉(読み直しの単位の数)、a(g)・d(g) = まとまり g に付けるタグ・消すキーがあれば1、なければ0、M(r) = リージョン r で読み戻しの値が違って読み直した単位の数(0 ≤ M(r) ≤ R(r))。リージョン r の回数 = ⌈N(r) ÷ 100⌉(最初の読み取り。機能設計 BR3.1)+ 2 × R(r)(読み直しと読み戻し)+ 3 × M(r)(読み戻しの読み直し)+ Σg (a(g) + d(g))(書き込み)。合計は全リージョンの和。再試行の分は数えない | 偽の AWS に置いた件数とまとまりから式で上限を計算し、操作ごとの回数が上限以下であることを確かめるテストが通る(数を手で書かない)。読み戻しがいつも一致する場合(M(r) = 0)と、偽の AWS が決めた単位の読み戻しで古い値を返す場合(M(r) > 0。返す単位の数を M(r) に入れる)の両方で確かめる |

## 測る条件(NFR5.20〜NFR5.22)

U6 の測る条件(1万リソース、17リージョン、偏ったリージョンに2,000件、残りの16リージョンに500件ずつ)で apply した記録を戻します。偏ったリージョンの単位の数は R = 20 です。

| 分布 | 単位の中のまとまり | 偏ったリージョン(2,000件)の回数と時間の例(1回0.3秒とする) |
|---|---|---|
| よくある変更(`env` → `Environment`、値 `Prod` → `prod`、`CostCenter` の追加)を戻す | 1つの単位(100件)の中で、`env` に戻す値(3つ)ごとに約33件。それぞれ2まとまりで、単位あたり約6まとまり、全体で約120まとまり。どのまとまりも `Environment` と `CostCenter` を消す | 最初の読み取り20回、読み直しと読み戻し40回、書き込み約240回(まとまり約120 × 付ける・消す)で約300回、約1.5分(1.2倍で約1.8分) |
| 値がばらばらなキー名の変更(`Owner` → `owner`)を戻す | `Owner` に戻す値がリソースごとに違うため、まとまりはほぼ1項目 | 最初の読み取り20回、読み直しと読み戻し40回、書き込み約4,000回で約4,060回、約20分(1.2倍で約24分) |
| どちらかで、すべての単位の読み戻しが遅れた場合(M = R = 20) | 上と同じ | 上に、読み直し60回(約0.3分)と待ち 20 × 7秒(約2.3分)が足される。よくある変更で約4.6分、値がばらばらで約27分 |

apply と比べると、まとまりが単位をまたがないぶん、よくある変更の書き込みが約2割多くなります(apply は約210回)。値がばらばらな場合は、どちらも1項目に付ける・消すの2回です。

## 当てはまらない要件

| 要件 | 理由 |
|---|---|
| NFR1(scan と plan の10分) | U7 は scan と plan を使わない。rollback の時間は NFR5.21 で決める |
| NFR2(影響分析の検出率) | U7 は影響分析を使わない(戻すのは apply の前の状態で、影響は apply のときに確かめた) |
| NFR12(配布) | 配布の仕組みは作業単位に含めず、別の作業で行う |

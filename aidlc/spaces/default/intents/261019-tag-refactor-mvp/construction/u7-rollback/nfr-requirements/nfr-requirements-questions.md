# NFR の要件 — 質問(U7 取り消し)

U7 は、apply が書き換えたタグを、記録をもとに書き換える前に戻す作業単位です。戻すのに要る権限、書き戻しの速さと呼び出し回数、記録の保存、読み戻しの読み直し、NFR4(差分0)の確かめ方を決めます。

決まっていること(質問しません):

- 時間の上限、待ち時間を延ばしながらの再試行、呼び出し回数の上限に当たったときの待ちは、U2 の AwsAccess のまま(NFR5)。書き込みは U6 の TagWriter(`TagResources`、`UntagResources`)、読み取りは U6 の ARN を指定した読み取り(`GetResources`)を使う。
- 認証情報は表示にも記録にもログにも出さない(NFR8)。ログファイルにはエラー文とタグの値を書かない(U6 と同じ。機能設計 BR6.4)。
- 記録は途中で壊れない方法で保存し(NFR6)、同じアカウントの apply と rollback の同時実行は U6 の印で防ぐ(NFR7、機能設計 BR2.1〜BR2.3)。記録と印とログファイルの置き場所と権限は U6 のまま(U6 の NFR8.24、NFR8.25)。
- 3つの OS で動く(NFR9)。カバレッジは80%以上(NFR10)。色がなくても意味が分かる(NFR11)。
- `aws:` のキーは書きも消しもしない。TagWriter の念のための防御(U6 の NFR3.12)もそのまま効く。

## Q2. 書き戻しのまとめ方と同時の数

1万件を戻すとき、書き戻しをどうまとめますか?

## Q3. 戻す時間の目標

1アカウント・全リージョン・1万リソースの rollback の時間に、目標を置きますか?

A. apply と同じ: 変更の多くがまとまる「よくある変更」の apply を戻す場合に、見積もりで30分以内。まとまらない最悪の場合の見積もりも記録するが、合否には使わない。見積もりの式は U6 の NFR5.15 と同じ形(最初の読み取り、読み直しと読み戻し、付ける・消す呼び出しの数)で、U7 のチェックポイントで測る
B. 問題が起きたときにすぐ戻すため、よくある変更で15分以内
C. 時間の目標は置かず、進み具合の表示だけを確かめる

## Q4. 結果を記録に保存する頻度

rollback は、apply の記録(1万件で約10 MB)に結果を足して、全体を書き直します(機能設計 BR6.1)。どの頻度で保存しますか?

A. apply と同じく、書き戻しの途中は5秒ごとと、止めたとき・終わったときに保存する。前の保存が終わっていなければその回は飛ばし、3回続けて失敗したら新しい書き込みを止める(U6 の NFR6.2 と同じ)

C. 終わったときと止めたときだけ保存する(判定は今のタグで行うので、途中の結果がなくても、もう一度の rollback で正しく戻せる)

## Q5. 読み戻しで値が違ったときの読み直し

書いた直後の読み戻しで値が違ったときは、タグの API の反映の遅れを考えて、上限つきで読み直してから失敗(`notRestored`)にします(機能設計 BR5.3)。回数と間隔をどうしますか?

A. 違った項目だけを、1秒、2秒、4秒おいて最大3回読み直す(1つのまとまりで合わせて最大7秒)。読み直しは書き込みのまとまりと同じ単位で行い、読み直しの呼び出しも呼び出しの数の式に入れる
B. 読み直さず、すぐに `notRestored` にする
C. 違った項目だけを、2秒おいて最大5回読み直す(最大10秒)

## Q6. NFR4(差分0)の確かめ方

NFR4 は「apply のあと別の変更が入っていなければ、rollback でタグが apply の前と完全に一致する(差分0)」です。どう確かめますか?

A. 偽の AWS では、変更の4種類(キー名の変更、値の変更、必須タグの追加、キーの削除)と、途中で止まった apply(付けたあと消す前、消すのが先で消したあと付ける前、結果が分からない)を含む記録で apply と rollback を続けて動かし、`aws:` を含むすべてのタグが apply の前と一致することを確かめる。検証用アカウントでは、U7 のチェックポイントで、確かめ専用のキーの追加・値の変更・キー名の変更を apply してから rollback し、5つの種類のリソースのタグが apply の前と一致することを確かめる。最後のタグまで消したリソースをタグの API が返すかも確かめて記録に残す
B. A のうち、偽の AWS の確かめだけにする
C. A のうち、検証用アカウントの確かめだけにする

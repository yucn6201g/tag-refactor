# 性能と品質の要件: U4 変更案

U1〜U3 の性能の要件(scan と plan を合わせて10分以内、呼び出し回数の上限、時間の上限)は、U4 でもそのまま守ります。U4 は AWS の呼び出しを増やさないため、ここでは AWS の呼び出しを除いた変更案の作成と出力の時間と、移植性、保守性、使いやすさの要件を定めます。

出典: 要件 NFR1、NFR9、NFR10、NFR11、機能設計 `construction/u4-plan/functional-design/`(BR1.8、BR3.1〜BR3.9、BR4.1)、`nfr-requirements-questions.md` Q1。

## 測る条件

1万リソース、1リソースにタグ20個、変更の対象5,000件(4種類の変更を含む)、衝突100件、値が未指定100件、影響の finding 100件。タグの値の半数は、表示の前の置き換えやエスケープが要る文字(制御文字、U+202E、`|`、`` ` ``、`<`)を含みます。AWS の呼び出しはテストの中の偽の収集の結果と偽の影響分析で置き換え、時間に含めません。CI の Linux の環境で測ります。`race` のビルドタグのときは、U2・U3 と同じく件数を10分の1にし、上限を10倍にします。共有の実行環境の揺れを見込み、上限は手元で測った時間の数倍に置きます(U3 の照会は1万件で約0.33秒)。

## 保存した変更案の大きさと、読み込みの上限(256 MiB)の根拠

| 変更案 | 1リソースの大きさの見積もり | 1万リソースの大きさ |
|---|---|---|
| 上の条件(タグ20個、キーと値の平均60バイト、変更1〜3件) | `beforeTags` 約1.6 KB、変更と項目の名前 約0.6 KB で約2 KB | 約20 MiB |
| 多め(タグ50個、キーと値の平均120バイト、変更5件) | 約8 KB | 約80 MiB |
| 最悪(タグ50個がすべて最大の長さ、キー128・値256文字、日本語などの3バイトの文字) | 約60 KB 以上 | 500 MiB 以上 |

256 MiB は、上の条件の10倍以上で、多めの場合も収まる大きさです。最悪の場合は収まらないため、`plan --out` は 256 MiB を超える変更案を保存せず、`--region` で分けて作るよう案内します(security-requirements.md NFR8.18)。読み込みの部品は Go の `encoding/json` で型に写すため、読み込み中のメモリはファイルの大きさの数倍になります(NFR1.15 で上限を決める)。

## 要件

| ID | 要件 | 合否の基準 |
|---|---|---|
| NFR1.13 | 変更案の作成(U3 の照会を含む、変更、衝突、値が未指定、消す候補、集計)は、上の条件で2秒以内 | 上の条件のテストで、作成の時間が2秒以内であることを確かめる(照会の時間を含めて測る) |
| NFR1.14 | 一覧、差分、JSON、Markdown のそれぞれの出力と、`--out` の保存は、上の条件(置き換えの要る値を半数含む)で3秒以内 | 上の条件のテストで、形式ごとと保存の時間が3秒以内であることを確かめる |
| NFR1.15 | 上の条件で保存した変更案(約20 MiB)の読み込みは3秒以内で、読み込みで増えるメモリ(Go の `runtime.MemStats` の `TotalAlloc` の増え)はファイルの大きさの10倍以内 | 上の条件の変更案を保存して読み込むテストで、時間とメモリの増えを確かめる。読み込みは、ファイルの大きさから先に入れ物の大きさを決めて読む(読みながら広げる確保を重ねない)。それでも10倍を超えるときは、測った値を根拠に倍率を決め直し、記録に残す |
| NFR9.6 | 同じ入力からは、3つの OS で同じバイト列(改行は LF、UTF-8、BOM なし)の一覧、差分、JSON、Markdown と、保存した変更案(`planId` と `createdAt` を除く)ができる。ツールが標準出力に書くバイト列が対象で、利用者のシェルのリダイレクト(Windows PowerShell 5.1 の `>` は UTF-16 で書き直す)は対象外。変更案の保存には `--out` を使うよう README で案内する | 決まった入力から作った4つの形式と保存した変更案を、期待のファイル(LF。`.gitattributes` で固定)と比べるテストが、3つの OS の CI で通る |
| NFR9.7 | 言語の決め方は、3つの OS で同じ規則で動く(`--lang`、`LC_ALL`、`LC_MESSAGES`、`LANG` の順。Windows だけ、3つの環境変数が空のときに最後に OS の表示言語を見る)。OS の表示言語を読めない、または空のときは英語にする。Windows の端末では、日本語がコードページによらず正しく出る | 環境変数と OS の表示言語を差し替えて言語の決め方を確かめるテストが、3つの OS で通る。Windows の CI で、実際の OS の関数を呼んで失敗しない(空か有効な言語名を返す)テストが通る。チェックポイントで、Windows の PowerShell で `--lang ja` の表示を人が確かめる |
| NFR10.6 | 4つの形式は、同じ変更案から同じ件数(変更の種類ごとの件数、総数、衝突、値が未指定、消す候補のキーの数、IaC、影響あり、判定できない)を出す | 乱数の種を固定して作った変更案(200通り)から4つの形式を作り、それぞれから読み取った件数が一致することを確かめるテストが通る |
| NFR10.7 | 英語と日本語の文言は、すべての文言にどちらの言語もあり、差し込む値(件数、キー、ARN など)の数と順が同じ | 文言の一覧のすべての項目に英語と日本語があり、差し込みの印が一致することを確かめるテストが通る |
| NFR10.8 | U4 のテストを足しても、カバレッジは `cmd` と `internal` のすべてで80%以上のまま | CI のカバレッジのジョブで確かめる |
| NFR11.7 | 色を付けた出力から色の制御の文字を取り除くと、色なしの出力と同じになる(意味を色だけで表さない)。色を出すのは、標準出力と標準エラーのそれぞれについて、(1) そのストリームが端末で、(2) `NO_COLOR` が設定されていないか空で、(3) `TERM` が `dumb` でなく、(4) Windows ではそのストリームの仮想端末の処理を有効にできた、のすべてを満たすときだけとする。Windows で有効にした仮想端末の処理は、終了時に元に戻す | 色ありと色なしの一覧と差分を比べるテストと、`NO_COLOR=1`、`TERM=dumb`、端末でない出力先、Windows で仮想端末の処理を有効にできない場合(判定の関数を差し替える)のそれぞれで色の制御の文字が出ないテストが通る。標準出力だけが端末のときに、標準エラーに色が出ないテストが通る |

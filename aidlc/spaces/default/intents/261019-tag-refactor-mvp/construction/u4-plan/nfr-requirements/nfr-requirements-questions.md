# NFR 要件 — 質問(U4 変更案)

U4 は、変更案の作成、4つの出力形式、英語と日本語、色、変更案の保存と読み込みを完成させます。AWS の操作は増やしません。

決まっていること(質問しません):

- U1〜U3 の NFR(読み取りだけ、認証情報を出さない、表示の前の置き換え、時間の上限と再試行、3つの OS、カバレッジ80%)はそのまま守る。
- `--format`、`--lang`、`--out` を付けても、呼ぶ AWS の操作は U1〜U3 の plan と scan と同じ(NFR3)。
- `--out` は一時ファイルに書いてから名前を付け、既にあるファイルは上書きしない。一時ファイルはどの終わり方でも消す(機能設計 BR4.1)。
- Windows の端末への日本語の表示は、Go の標準の出力が端末に Unicode で書くため、コードページによらず正しく出る。ツールが標準出力に書くのは UTF-8(BOM なし、LF)。Windows PowerShell 5.1 の `>` はこれを UTF-16 で書き直すため、変更案の保存には `--out` を使うよう案内する。チェックポイントで、PowerShell での `--lang ja` の表示を人が確かめる。
- 4つの形式の件数が一致することは、乱数で作った変更案から4つの形式を作って比べるテストで確かめる(機能設計 BR3.1)。

## Q1. 変更案の作成と出力の時間の目標

AWS の呼び出しを除いた、変更案の作成と出力(4つの形式のそれぞれ)の時間の目標を決めます(要件 NFR1 は、scan と plan を合わせて10分以内)。

A. 1万リソース(1リソースにタグ20個、変更の対象5,000件、影響の finding 100件)で、変更案の作成は2秒以内、どの形式の出力も3秒以内、`--out` の保存も3秒以内(CI の環境で測る。`race` のときは件数を減らし、上限を10倍にする。U2・U3 と同じ)
B. A の件数で、作成から出力までを合わせて10秒以内(形式ごとには決めない)
C. 別の目標は決めない(NFR1 の10分の中で十分に小さいとみなす)

## Q2. 保存した変更案の読み込みの上限と、壊れにくさの確かめ

保存した変更案は、U6(apply)が読みます。利用者が手で直したり、ほかの人から受け取ったりしたファイルを読むこともあります。

A. 読み込むファイルは 256 MiB まで(1万リソース・1リソース50個のタグがすべて最大の長さでも収まる大きさ)。超えたら InvalidInput。読み込みにファジングのテストを用意し、CI では種の入力だけ、手元で5分走らせた結果を U4 のチェックポイントに残す(U3 のルールファイルと同じ扱い)
B. A と同じ上限で、ファジングはしない(単体テストだけ)
C. 上限を設けない

## Q3. Markdown に、タグの値などをそのまま書いてよいか

`--format markdown` は、プルリクエストや Wiki に貼って見ます。タグのキーや値、ARN、ポリシー名には、`|`、`` ` ``、`<`、`>`、改行、HTML(例 `</details>`、`<img src=…>`)が入りうるため、表示を崩したり、貼った先で HTML として働いたりするおそれがあります。

A. データから来る文字列は、すべて表のセルの中のコードの書式で書き、HTML として働く文字(`<`、`>`、`&`)は文字の参照(`&lt;` など)に、`|` はエスケープに、改行と制御文字は表示の前の置き換え(U1)と同じ形に変える。コードの書式の区切りは、値の中の `` ` `` の数より長くする。データから来る文字列を、生の HTML や見出しとして出さない
B. コードの書式で囲むだけにする(`|` と改行だけ変える)

## Q4. 保存した変更案のファイルの権限

保存した変更案には、アカウントID、ARN、タグ、ポリシーの名前が入ります(タグの値は秘密情報ではないとみなす。要件 AS2)。

# 機能設計 — 質問(U4 変更案)

U4 は、ルールファイル(契約 C1)のすべての項目を使って変更案を完成させ、一覧、差分、JSON、Markdown の4つの形式と、英語と日本語で出力します。変更案は `--out` でファイル(契約 C2)に保存でき、U6(apply)と U8(IaC への反映)が読みます。

決まっていること(質問しません):

- 変更の種類は契約 C2 の4つ(`renameKey`、`changeValue`、`addRequired`、`removeKey`)。種類ごとの必須の項目も C2 の表のとおり。
- 必須タグの値、正しい値、消すかどうかは、U3 の照会の部品が答える。照会には収集したままのタグを渡す(置き換えの順は照会の中で決まる。U3 BR3.2)。
- 値が決まらない必須タグは「値が未指定」に出し、変更案に入れない。そのリソースの他の変更は残す(FR3.3)。
- ルールファイルにないキー(正しいキー名、別名、必須タグ、消すキーのどれでもないキー)は「消す候補」に出し、変更案に入れない。`aws:` で始まるキーは候補にも変更にも入れない(FR3.4、契約の全体の決まり)。
- 正しいキー名と別名に違う値が付いているリソースは、U1 のとおり「衝突」として変更せずに示す(U1 BR4.2)。
- 総数は、変更が1つ以上あるリソースの数(重なっても1件。FR3.2)。
- IaC の印は U2 の収集の結果(`iacManagedBy`)を使い、変更のあるリソースのうち印のあるものを「IaC で管理されている」と示す(FR3.7)。
- 影響分析は U1 の仕組み(契約 C9)のまま呼び、影響のある変更に `!`、判定できない変更に `?` を付ける。影響分析の中身を広げるのは U5。
- JSON の形は契約 C3(標準出力)と C2(保存)のとおり。`scan` の `--format json` と `--format markdown` も U4 で作る(契約 C5)。
- 色は補助。`NO_COLOR` があるか、出力先が端末でなければ色を出さない。標準出力と標準エラーは別々に判定する(FR7.3)。
- 言語は `--lang en|ja`。指定がなければ OS の言語設定に合わせ、日本語でも英語でもなければ英語(FR7.2)。数字、ARN、ポリシー名、キー名、オプション名は訳さない。JSON の項目名と値も訳さない。
- 同じ入力からは同じ変更案ができる(変更は ARN の順、その中はキーの順に番号を付ける)。

## Q1. キー名の変更と値の変更が重なるとき

`env = Prod` のリソースに、`env` を `Environment` の別名に、`Prod` を `prod` の別の書き方にするルールを当てはめます。変更案にどう書きますか?

A. 2つの変更にする。`renameKey`(`env` → `Environment`、値は `Prod` のまま)と、そのあとの `changeValue`(`Environment`: `Prod` → `prod`)。`changeValue` の `fromKey` は変更後のキー名にする。apply はこの順に行う。差分の形では、1つのリソースの「変更前」と「変更後」として `- env = "Prod"`、`+ Environment = "prod"` と表示する(モックアップの画面5)
B. 1つの変更にまとめる。`renameKey` に `toValue` を足して「キー名と値を同時に変える」とする(契約 C2 の項目を変えるため、`version` を上げる)

## Q5. `--out` で保存するときの動き

`plan --out plan.json` の動きを決めます。

A. 既にあるファイルは上書きせずにエラーにする(`rules suggest --output` と同じ。一時ファイルに書いてから名前を付ける)。標準出力には、いつもどおり一覧(または `--format` の形式)を出し、標準エラーに「Saved plan to plan.json (N resources, account …)」を出す

C. 上書きしない。`--out` を付けたときは標準出力に何も出さず、保存したことだけを標準エラーに出す(モックアップの画面6の見た目)

## Consolidated Summary Confirmation

回答のまとめ:

- 重なる変更(Q1): キー名の変更と値の変更が重なるリソースには、`renameKey` とそのあとの `changeValue` の2つの変更を作ります。`changeValue` の `fromKey` は変更後のキー名です。差分の形では、変更前と変更後のタグとして見せます。契約 C2 は変えません。
- 既にある必須タグの値(Q2): 必須タグは、付いていないときに付けるだけです。既にある値は変えず、書き方の統一は値の別名で行います。
- 書き方だけ違う値(Q3): 正しいキー名と別名の値は、値の別名を当てはめたあとで比べます。同じになれば衝突にせず、別名のキーを正しいキー名に合わせる変更(と、必要なら値の変更)を作ります。違えば U1 のとおり衝突です。
- 終了コード(Q4): 変更、衝突、値が未指定の必須タグ、影響のある参照(判定できないものを含む)のどれかがあれば2です。消す候補だけなら0です。収集や影響分析が不完全なら1です。
- `--out`(Q5): 既にあるファイルは上書きせずにエラーにし、一時ファイルに書いてから名前を付けます。標準出力にはいつもどおり結果を出し、標準エラーに保存したことを出します。
- Markdown(Q6): 一覧の形と同じ順の節を見出しと表で書き、リソースごとの変更は `<details>` で畳んだ表で全件書きます。契約 C3 の未決事項をこれで決めます。
- 日本語の範囲(Q7): `--help` 以外のすべて(結果、進み具合、案内、警告、エラー、`rules suggest` の下書きのコメント)を日本語にします。`--help` は英語のままです。
- 3桁区切り(Q8): scan と plan の一覧、差分、Markdown の件数にカンマを付けます。JSON は数値のままです。

# 性能と移植性とテストの要件: U3 ルール

U1 と U2 の要件(収集の性能と信頼性、3つの OS、カバレッジ80%)は、U3 でもそのまま守ります。`rules suggest` の収集は U2 の scan と同じなので、収集の時間、再試行、時間の上限は U2 の要件(NFR1.6〜NFR1.10、NFR5.4〜NFR5.8)に従います。

出典: 要件 NFR1、NFR9、NFR10、機能設計 `construction/u3-rules/functional-design/`(BR6.1〜BR6.7)、`nfr-requirements-questions.md` Q1〜Q3。

| ID | 要件 | 合否の基準 |
|---|---|---|
| NFR1.11 | `rules suggest` の、収集を除いたツール自身の処理(キーと値のまとめ、下書きの組み立てと大きさの調整)は、件数に比例する手間で行う | 測るのは、収集の結果(`InventorySnapshot`)を受け取ってから下書きのバイト列ができるまで(AWS の応答の解釈は U2 の NFR1.7 で測る)。1万件・異なるキー500個で、キーの半分は異なる値が50個(値の候補を出さない)、残りの半分は異なる値が20個以下で書き方が2〜3通りあり、組み立てた下書きが 64 KiB を何度も超えて値の候補を外す調整が働く入力で、CI の各 OS で5秒以内に終わる単体テストが通る |
| NFR1.12 | ルールファイルの読み込みと照会(必須タグの値、正しい値、消すかどうか)は、U4 の plan が1万件に使っても時間を食わない | 正しいキー名100個・別名300個・値の別名500個・必須タグ20個(条件各10個)のルールファイルで、1万件のリソースに照会を3種類ずつ行う単体テストが、CI の各 OS で2秒以内に終わる |
| NFR9.4 | 下書きは、すべての OS で LF の改行で出す。同じ収集の結果からは、OS によらず同じバイト列になる(日時の行を除く) | 同じ偽の AWS の結果で作った下書きが、3つの OS の CI で同じ期待のファイル(LF)と一致するテストが通る |
| NFR9.5 | Windows PowerShell 5.1 のリダイレクト(`rules suggest > tagrules.yaml`)が書く UTF-16(BOM 付き)のファイルも、ルールファイルとして読める。読み込みは、先頭の BOM で UTF-8、UTF-16LE、UTF-16BE を見分け、UTF-16 は UTF-8 に変えてから読む(64 KiB の上限は変えたあとの大きさで判定する)。BOM のない UTF-16 や不正な文字コードは、行番号1の誤りとして「UTF-8 で保存し直す」案内を出す | UTF-16LE と UTF-16BE(BOM 付き)で保存した下書きを読み込むと、UTF-8 の下書きと同じ `RuleSet` になるテストが3つの OS の CI で通る。BOM のない UTF-16 の入力で、行番号1と直し方の誤りになるテストが通る。README に、PowerShell 7 と 5.1 での保存の例を書く |
| NFR5.9 | `rules suggest` は、U2 の収集と同じ再試行と時間の上限で動く。呼び出し回数の上限が続いても最後まで終わり、1つのリージョンが読めなくても下書きを出して終了コード 1 で終わる | 呼び出し回数の上限を3回返してから成功する偽の AWS で `rules suggest` が終了コード 0 で終わるテストと、1つのリージョンだけ拒否する偽の AWS で下書きが出て終了コード 1 になるテストが通る |
| NFR10.4 | 下書きを読み込むと、元のキー、別名、値の候補に戻る | ランダムに作ったキーと値(制御文字、引用符、`:`、`#`、空白、日本語、128文字のキー、256文字の値を含む)から作った下書きを読み込み、`RuleSet` の正しいキー名、別名、値の別名が元と一致するテストが通る(乱数の種を固定して、CI で毎回同じ入力) |
| NFR10.5 | U3 のテストを足しても、カバレッジは `cmd` と `internal` のすべてで80%以上のまま | CI のカバレッジのジョブで確かめる |

# 論理的な部品: U3 ルール

U1 と U2 のパッケージの構成と依存の向きを保ち、U3 で足すものを示します。新しいパッケージは作りません(Q1)。

出典: `nfr-design-questions.md` Q1、`security-design.md`、`nfr-requirements/`、機能設計 `functional-design/`、部品の設計 `inception/domain-design/components.md`(RuleEngine はほかの部品に依存しない)、契約 C1・C5・C8。

## パッケージごとの変更

| パッケージ | U3 で足すもの、変えるもの | 契約 |
|---|---|---|
| `internal/rules` | `values`、`required` の `default` と `when`、`remove` を `RuleSet` に読み込む。項目どうしの矛盾の確かめ(BR2.1〜BR4.1)。文字コードの見分け(UTF-8、UTF-16)。照会の関数(必須タグの値、正しい値、消すかどうか)。下書きの組み立て(キーと値のまとめ、正しいキー名の選び方、値の候補、64 KiB への調整、YAML のエスケープ)。ファジングのテスト | C1、C8 |
| `internal/cli` | `rules suggest` のサブコマンド(`--profile`、`--region`、`--output`、`--debug`)。接続の関数を二段に分け、`rules suggest` はアカウントとタグの取得だけを使う(`security-design.md` §1)。組み立て: `inventory` の収集を呼び、結果を `rules` の下書きの入力(ARN とタグの一覧)に写し、`inventory` のまとめる関数を渡す。`--output` のファイルへの書き込み(一時ファイルから名前を変える、上書きしない)。scan と plan では `rules.Load` に種類の照会の関数を渡す。終了コード(BR6.6、BR6.7)。plan の「values / required / remove are read but not applied to the plan yet」の1行 | C5(`rules suggest` に `--output` を足す) |
| `internal/inventory` | 変えない。下書きの入力に渡す関数として、U2 の `CanonicalKey`(正規化と略語の辞書)と `Abbreviations` をそのまま使う。BR3.4 の案内に使う、種類の対応表を照会する関数を1つ公開する | C7 |
| `internal/display` | 下書きのバイト列を標準出力にそのまま書く口を1つ足す(置き換えは `rules` の書き出しの関数が済ませている) | C11 |
| `README.md` | `rules suggest` の使い方、PowerShell での保存の仕方、条件に書けない種類の制限 | — |

### 依存の向き(U3 で変わるところ)

| パッケージ | 使うパッケージ | 理由 |
|---|---|---|
| `rules` | `errkind` だけ(U1 のまま) | 下書きの入力は `rules` が定義する単純な型(ARN とタグ)。まとめる関数は `SuggestInput` で、種類の照会は読み込みの `Options.TypeHint` で、関数の値として受け取る |
| `cli` | U1・U2 のものに加えて、`rules` の下書きの関数 | `inventory` の結果を `rules` の入力に写し、`inventory` の関数を渡す |

```go
// 下書きの入力(rules が定義する。inventory の型は使わない)
type SuggestInput struct {
    Resources []TaggedResource          // ARN とタグ
    KeyGroup  func(key string) string   // まとめるための鍵(inventory.CanonicalKey)
    Preferred func(group string) string // 辞書の正式な形(なければ "")
}
```

## 性能の設計(NFR1.11、NFR1.12)

- 下書き: リソースを1回だけ走査し、まとめの鍵ごとに「書き方 → ARN の集まり」と「書き方 → 値 → ARN の集まり」の対応表を作る。並べ替えはまとまりの数と値の数に対してだけ行う。64 KiB への調整は、組み立てたキーごとのバイト数を先に測っておき、値の候補を外すたびに全体を組み立て直さず、合計のバイト数から「外したキーの値の部分のバイト数」を引き、「そのキーに足す values omitted のコメントのバイト数」を足す。先頭のコメント(不完全の行を含む)のバイト数も最初から合計に入れる。調整が終わったら下書きを組み立てて実測し、上限を超えていれば調整を続ける(見積もりと実測がずれても、超えた下書きを「収まった」としない)。テストでは、調整のあとの下書きの実測が 64 KiB 以下であることを確かめる。
- 照会: `RuleSet` を読み込んだときに、別名から正しいキー名、(キー, 値の別名)から正しい値、消すキーの集まりを対応表にしておく。必須タグの値の照会は、`when` を上から順に比べる(条件の数に比例。1つのキーの条件は多くて数十)。
- テスト: NFR1.11 は `rules` の単体テストで、組み立てた入力から下書きのバイト列ができるまでを測る。NFR1.12 は1万件 × 3種類の照会を測る。どちらも CI の3つの OS で動き、`-race` のときは U2 の `race` のビルドタグで件数を減らす。

## 信頼性の設計(NFR5.9)

- `rules suggest` は U2 の収集(`inventory.Collect`)をそのまま呼ぶので、再試行、時間の上限、リージョンの失敗の集め方、認証情報の誤りでの全体の取り消しは U2 のまま。
- テスト(受け入れ条件のテストと同じ `cli` のテスト): 呼び出し回数の上限を3回返してから成功する偽の AWS で終了コード 0、1つのリージョンだけ拒否する偽の AWS で下書きが出て終了コード 1、先頭のコメントに「Results are incomplete」が入ること。

## 移植性とテストの設計(NFR9.4、NFR10.4、NFR10.5)

- 下書きの改行は `\n` だけを書く。日時の行は時計の差し込み口(U1 のまま)で固定し、決まった偽の AWS の結果から作った下書きを、`testdata/` の期待のファイル(LF)と比べる。`.gitattributes` で LF に固定されているので、3つの OS で同じ比べ方になる。
- 読み戻しのテスト(NFR10.4): 乱数の種を固定してキーと値を作り(制御文字、補助面の文字、引用符、`:`、`#`、空白、日本語、128文字のキー、256文字の値を含む)、下書きを組み立てて `rules.Parse` で読み、正しいキー名、別名、値の別名が元と一致することを確かめる。
- カバレッジは U1 と同じ測り方で80%以上(NFR10.5)。

## 障害の範囲と隔て方(U1・U2 の表に足す)

| 範囲 | 起きうる障害 | 広がりを止める仕組み |
|---|---|---|
| ルールファイル | 誤り、細工した入力、UTF-16 | `rules` が AWS を呼ぶ前に読み切り、誤りで止める。文字コードを見分け、ファジングで止まらないことを確かめる |
| 下書き | 他人が付けたタグの制御文字、64 KiB を超える大きさ | 書き出しの関数が YAML のエスケープと大きさの調整を行う |
| rules suggest の収集 | 一部のリージョンの失敗、呼び出し回数の上限 | U2 の収集のまま。下書きは出して終了コード 1 |

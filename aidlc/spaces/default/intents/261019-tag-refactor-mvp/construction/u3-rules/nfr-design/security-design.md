# セキュリティの設計: U3 ルール

U1 と U2 のセキュリティの設計(読み取りの口だけを渡す、操作の表と例のポリシーの照合、認証情報を出さない、ルールファイルの安全な読み方、表示の前の置き換え)は、そのまま使います。ここでは U3 で足す部分を定めます。

出典: `nfr-requirements/security-requirements.md`(NFR3.6、NFR3.7、NFR8.12〜NFR8.14)、`nfr-requirements/performance-requirements.md`(NFR9.5)、`nfr-design-questions.md` Q1、機能設計 `functional-design/`(BR1.1〜BR1.5、BR6.4、BR6.7)。

## 1. rules suggest は読み取りの口だけで動く(NFR3.6)

- 今の `cli` の接続の関数は、5つの読み取りの口(AccountResolver、TagReader、ConfigReader、ExplorerReader、PolicyReader)をまとめて作る。`rules suggest` では、接続の関数を「アカウントとタグの取得だけを持つ型を返す関数」と「残りの口を足す関数」の二段に分け、`rules suggest` は一段目だけを使う。こうすると、`rules suggest` の組み立てには AWS Config、Resource Explorer、IAM の口が存在しない。
- テスト: HTTP の層の偽の AWS で `rules suggest` を動かし、記録された操作がすべて `sts:GetCallerIdentity`、`ec2:DescribeRegions`、`tag:GetResources` のどれかであることを確かめる(U1 の仕組みのまま)。

## 2. 誤ったルールファイルで AWS を呼ばない(NFR3.7)

- scan と plan の組み立てでは、ルールファイルの読み込み(`rules.Load`)を、`awsaccess` のセッションを作るより前に行う。誤りがあれば、そこで2行の案内を出して終える。
- テスト: 誤りのあるルールファイルで scan と plan を動かし、偽の AWS が要求を1つも受け取らないことを確かめる。

## 3. 下書きの書き出しの守り(NFR8.12)

### 保存の仕方(文字化けを防ぐ)

Windows の PowerShell は、リダイレクト(`>`、`| Out-File`)のときに、子のプロセスの標準出力をコンソールのコードページ(日本語の環境では 932)で読んでから書き出します。ツールは UTF-8 で出すので、日本語のタグの値は保存の時点で文字化けし、読み込めても元の値と違う下書きになります。そこで `rules suggest` に `--output <ファイル>` を足し(契約 C5 への追加)、下書きを UTF-8(BOM なし、LF)でファイルに直接書きます。

- `--output` を付けたときは、標準出力には何も書かず、標準エラーに書いたファイルの名前を出す。ファイルは、同じフォルダの一時ファイルに書いてから名前を変える(途中で止まっても壊れたファイルを残さない)。既にあるファイルは上書きしない(`--force` はつけない。上書きしたいときは消してから実行する)。
- `--output` がないときは、これまでどおり標準出力に出す(Linux や macOS のパイプ、PowerShell 7 で UTF-8 の設定をした場合)。
- README の Windows の例は `--output` を使う。リダイレクトを使う場合は、PowerShell 7 で `[Console]::OutputEncoding = [Text.Encoding]::UTF8` を先に設定する必要があることを書く。
- テスト: 日本語、補助面の文字を含む値で `--output` に書いたファイルを読み戻し、元の値と一致することを3つの OS の CI で確かめる。既にあるファイルを指定したときに上書きせず誤りになることを確かめる。U3 のチェックポイントでは、人が手元の Windows の PowerShell で `--output` で保存し、読み戻せることを確かめる。

### エスケープ

下書きは `internal/rules` の書き出しの関数がバイト列として組み立て、`display` の標準出力の口(または `--output` のファイル)にそのまま渡します(下書きは YAML として正しくなければならず、`display` の置き換えの形(`\u{...}`)では読み戻せないため、置き換えは書き出しの関数の中で YAML のエスケープとして行います)。

| 入力の文字 | 下書きでの書き方 |
|---|---|
| `"` と `\` | `\"` と `\\` |
| 基本多言語面の印字できない文字(Cc、Cf、Zl、Zp。例 ESC、0x9B、U+202E、U+2028) | `\uXXXX`(大文字の16進4桁) |
| 補助面の印字できない文字(Cf。例 U+E0001、U+E0041、U+1D173) | `\UXXXXXXXX`(大文字の16進8桁) |
| 不正な UTF-8 のバイト | U+FFFD(Go の文字列の範囲の読み方で、不正なバイトは U+FFFD になる) |
| それ以外(日本語などの印字できる文字、`:`、`#`、空白) | そのまま(二重引用符の中なので YAML の意味を持たない) |

- キーと値は、すべて二重引用符で囲む。コメントの行に入れる文字列(アカウント ID、リージョン、ツールの版)は、ツールが作る決まった形の文字列だけにし、AWS から読んだ文字列をコメントに入れない。
- `display` を通さずに標準出力に書く経路はこの1つだけで、U1 の「`display` と `cmd` の外から標準出力を使わない」の検査は変えない(書き出しの関数はバイト列を返すだけで、書くのは `display`)。
- テスト: NFR8.12 の文字を含むキーと値で、下書きのバイト列に元の文字(ESC、0x9B、U+202E、U+E0001 など)が1つも含まれないこと、下書きを `rules.Parse` で読むと元の文字列(不正な UTF-8 は U+FFFD)に戻ることを確かめる。

## 4. ルールファイルの読み込みの壊れにくさ(NFR8.13、NFR8.14、NFR9.5)

### 読み込みの入口と置き場所

- 種類の照会(BR3.4 の直し方に使う U2 の対応表)は、読み込みの関数に省略できるオプションとして渡す: `Load(path, opts)`、`Parse(path, data, opts)`、`Options{TypeHint func(cfnType string) (arnForm string, ok bool)}`。`TypeHint` が nil なら、CloudFormation の形はすべて「この種類は条件に書けない」の案内にする。`cli` は scan、plan、後の apply で `inventory` の対応表を引く関数を渡す。ファジングは `Options{}`(nil)で動かす。
- 文字コードの見分け、変換、変換したあとの大きさの判定は、すべて `Parse` の最初で行う。`Load` はファイルの種類の確認と、128 KiB + 1 バイトまでの読み取りだけを行い、残りは `Parse` に任せる。こうするとファジング(`Parse` が対象)が、文字コードと大きさの経路を含めたすべてに届く。

### 文字コード(NFR9.5)

`Parse` の最初(大きさの判定の前)に、先頭のバイトで文字コードを見分けます。

| 先頭 | 扱い |
|---|---|
| `EF BB BF`(UTF-8 の BOM) | 取り除いて UTF-8 として読む(U1 のまま) |
| `FF FE`(UTF-16LE の BOM) | Go の標準の `unicode/utf16` で UTF-8 に変える |
| `FE FF`(UTF-16BE の BOM) | 同じく UTF-8 に変える |
| BOM がなく、長さが偶数で、バイトの4分の1以上が 0x00(ASCII だけの UTF-16 は UTF-8 としては正しいため、UTF-8 として正しいかどうかは見ない。ルールファイルに NUL は書かれない) | BOM のない UTF-16 とみなし、行番号1の誤り「the rule file is not UTF-8」と直し方「save it as UTF-8 (use rules suggest --output tagrules.yaml)」 |
| それ以外 | UTF-8 として読む。不正な UTF-8 があれば、その行の誤りにする |

- UTF-16 のファイルは2倍近い大きさになるため、`Parse` に渡すバイト数の上限は 128 KiB とし、変換したあとの UTF-8 を 64 KiB までとする。UTF-8 のファイルの上限は U1 のまま 64 KiB。128 KiB を超えるバイト列は、変換の前に誤りにする(ファジングが渡す大きな入力もここで止まる)。
- BOM 付きの UTF-16 で長さが奇数のときは、最後の1バイトを U+FFFD に変える。対になっていないサロゲートも U+FFFD に変え、そのまま YAML として読む(誤りの行で分かる)。
- 見分けの限界: BOM のない UTF-16 は、上の目安(0x00 の多さ)で見分ける。見分けられない場合は「不正な UTF-8」の行の誤りになり、どちらの場合も「UTF-8 で保存し直す」の直し方を出す。README に `--output` での保存を書く。

### ファジング(NFR8.13)

- 対象: `rules.Parse`(バイト列からの読み込みのすべて)。
- 確かめること: パニックしない。1回の呼び出しが1秒以内に終わる(テストの中で時間を測り、超えたら失敗。`-race` のときは U2 と同じく `race` のビルドタグで上限を10倍にする)。誤りを返すときは、行番号が1以上でファイルの行数以下。読めたときは `RuleSet` の規則(別名の重なりがないなど)が成り立つ。
- 種の入力: 正しいファイル(U1 と U3 の例、`rules suggest` の下書き)、機能設計の誤りの例のすべて、深い入れ子、64 KiB 近い長い行、不正な UTF-8、UTF-16LE・BE、BOM のない UTF-16(ASCII だけのものと日本語を含むもの)。`testdata/fuzz/FuzzParse/` に置き、CI では普通のテストとして動く。
- 手元: `go test -run '^$' -fuzz FuzzParse -fuzztime 5m ./internal/rules/` を U3 のチェックポイントの前に動かし、見つかった入力があれば直して種に足す。結果(走らせた時間、試した入力の数、見つかった数)をチェックポイントの記録に残す。

### 誤りと警告の文言(NFR8.14)

- 誤りと警告は `errkind.Error` と `rules.Warning` で返し、文言は `cli` と `display` が組み立てる(U1 のまま)。ルールファイルから来た文字列(キー、値)は、`%q` で引用したうえで `display` の置き換えを通す。
- テスト: 制御文字と U+202E を含むキーのルールファイルで、標準エラーにそれらがそのまま出ないことを確かめる。

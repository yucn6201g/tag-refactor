# CI/CD の流れ: U3 ルール

U1 と U2 の CI/CD の流れ(`ci.yml` のジョブ、`ci-gate`、`race` ジョブ、関門、秘密の値、検証コマンド `scripts/verify.sh`)は、そのまま使います。U3 では AWS のリソースも IAM の権限も変えないため、確認用のスタックの変更はありません。公開(GitHub Releases)も行いません。

出典: NFR の設計(`security-design.md` §3・§4、`logical-components.md`)、NFR 要件(NFR1.11、NFR1.12、NFR3.6、NFR5.9、NFR8.12〜NFR8.14、NFR9.4、NFR9.5、NFR10.4、NFR10.5)、`infrastructure-design-questions.md` Q1、チームの進め方(§Way of Working、§Testing Posture)。

## `ci.yml`

変更はありません。U3 で足すテストは、今のジョブの中で動きます。

| 足すテスト | 動くジョブ | 補足 |
|---|---|---|
| ルールファイルの読み込みと矛盾の確かめ、照会、下書きの組み立て | `test`(3つの OS × 2つの版)、`race`、`coverage` | AWS を呼ばない |
| ファジングの種の入力(`testdata/fuzz/FuzzParse/` とテストのコードの種) | 同上 | `go test` は種の入力を普通のテストとして動かす。CI ではファジングそのもの(`-fuzz`)は動かさない |
| 読み戻し(乱数の種を固定)、`--output` の UTF-8 の書き込み、UTF-16 の読み込み | 同上 | 3つの OS で同じ期待のファイル(LF)と比べる(NFR9.4) |
| 性能(NFR1.11、NFR1.12) | `test`、`race` | `race` のときは U2 と同じ `race` のビルドタグで件数を減らし、時間の上限を10倍にする |
| `rules suggest` の操作の照合、呼び出し回数の上限、リージョンの失敗(NFR3.6、NFR5.9) | `test`、`race` | 偽の AWS(U2 のまま) |

- ファジングの種のファイル(`internal/rules/testdata/fuzz/FuzzParse/`)は、Go の決まった形(`go test fuzz v1` の行と、`[]byte("...")` の引用つきの文字列)の文字のファイルで、UTF-16 や不正な UTF-8 のバイトもエスケープで書かれる。そのため改行の変換で中身は壊れないが、手で作った種の行末が変わらないよう、`.gitattributes` に `**/testdata/fuzz/** -text` を足して改行の変換から外す(`testdata/fuzz/** -text` はルート直下にしか当たらないため、`**/` を付ける)。実装のあとで `git check-attr text -- internal/rules/testdata/fuzz/FuzzParse/<種>` が `unset` になることを確かめる。
- カバレッジの下限80%は変えない(NFR10.5)。

## 検証のスクリプト(Q1)

`scripts/verify.sh` に、U3 の確認を足します。検証コマンド(`"C:\Program Files\Git\bin\bash.exe" -c "TAG_REFACTOR_SANDBOX_ACCOUNT_ID=663798383745 bash scripts/verify.sh"`)は変えません。

- **差し込む位置:** U1 の確認(`verify-u1.sh`)とアカウントの確認のすぐあと、U2 のタグのないキューを作る前に置く。U3 の確認はキューも Resource Explorer の索引も使わないので、U2 の最大30分の待ちに巻き込まれないようにする。
- **前提の確認:** 最初に、管理者のプロファイルで U1 の確認用のスタック `tag-refactor-u1-fixtures` の状態が `CREATE_COMPLETE` か `UPDATE_COMPLETE` であることを確かめる。そうでなければ「U1 の確認用のスタックをデプロイする(infrastructure-specification の手順)」と示して止める。U3 の確認は、このスタックの `env` と `Env` のタグに頼るため。
- **一時ファイルの後片付け:** 一時ファイルの名前は、確認の前に `mktemp` で決めて変数に持つ。削除は、今の `verify.sh` の `cleanup` 関数(`trap cleanup EXIT` で U2 のキューを消している関数)の中に足す。新しい `trap` は定義しない(同じ `EXIT` の `trap` を定義し直すと、キューを消す処理が置き換わってしまうため)。今の `verify.sh` では `cleanup` と `trap cleanup EXIT` が U2 のキューの節で初めて定義されるので、その定義を U3 の確認より前(スクリプトの先頭近く)に移し、`cleanup` はキューの名前や一時ファイルの名前が空のときは何もしないようにする。こうすると、U3 の確認の途中で止まっても一時ファイルが残らない。

1. 読み取り用のプロファイル(`tag-refactor-readonly`)で `rules suggest --region ap-northeast-1 --output <一時ファイル>` を動かす。終了コードが 0 であること、標準出力が空であることを確かめる。
2. 一時ファイルの先頭が `# generated by tag-refactor` で始まり、`env` のまとまりに `Env` が別名として入っていること(どちらが正しいキー名かは件数で決まるので、2つが同じまとまりにあることだけを確かめる)を確かめる。
3. 一時ファイルをそのまま `scan --region ap-northeast-1 --rules <一時ファイル>` に渡し、ルールファイルの誤りにならない(標準エラーに `Error:` がない)ことを確かめる。
4. 一時ファイルは `cleanup` 関数で消す(上の「一時ファイルの後片付け」)。
5. 結果(下書きのキーの数、`env` のまとまり)を表示する。

- `rules suggest` は読み取り用ロール R2 の今の権限で動く(新しい権限は要らない)。U2 と同じく、認証情報を表示しない。
- この確認は Go の結合テストではなく、作った実行ファイルを動かす。`rules suggest` のコマンドとしての振る舞い(`--output`、終了コード、標準出力が空)を、利用者と同じ形で確かめるため。

## チェックポイントでの人の確認

- 手元の Windows の PowerShell で `rules suggest --output tagrules.yaml` を動かし、`scan --rules tagrules.yaml` で読めることを確かめる(NFR9.5 の確認)。
- 手元で `go test -run '^$' -fuzz FuzzParse -fuzztime 5m ./internal/rules/` を動かし、結果をチェックポイントの記録に残す(NFR8.13)。Windows の Application Control が新しく作られたテストの実行ファイルをふさいだときは、同じコマンドをもう一度動かす(`verify.sh` と同じ扱い)。それでも動かないときは、WSL など別の環境で動かし、どこで動かしたかを記録に残す。

## 流れ(この Bolt)

1. `bolt/u3-rules`(`main` から作成済み)で、受け入れ条件のテスト、実装、細かい単体テストの順にコミットする。
2. push して、`main` へのプルリクエストを作る(例 `feat: complete the rule file and add rules suggest`)。
3. `ci-gate` が通り、U3 のチェックポイントで人が承認したら、人が squash マージする。

## 戻し方と秘密の値

- U1・U2 と同じ(打ち消しのプルリクエスト。CI に AWS の認証情報を置かない)。U3 は確認用のスタックを変えないので、スタックの戻しはない。

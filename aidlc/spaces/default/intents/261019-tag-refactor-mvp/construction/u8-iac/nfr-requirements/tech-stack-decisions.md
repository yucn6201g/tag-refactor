# 技術の選択と、性能・移植性・保守性の要件: U8 IaC への反映

U1〜U7 の技術の選択(Go、cobra、`github.com/goccy/go-yaml`、U4 の変更案の読み込みと表示の部品、U4 の `internal/fileout`)はそのまま使います。U8 で新しく足すライブラリは `github.com/hashicorp/hcl/v2` だけです(Q1)。ここでは、U8 で使う部品と、速さ、3つの OS で動くこと、テストと依存の要件を決めます(U8 は `library` の作業単位で、性能の要件のファイルを別に作らないため、ここに置きます)。

出典: 要件 NFR1、NFR5、NFR9、NFR10、NFR12、機能設計(`construction/u8-iac/functional-design/`)、契約 C2・C5・C12、`nfr-requirements-questions.md` Q1〜Q3、Q6。

## 技術の選択

| 用途 | 選ぶもの | 理由 |
|---|---|---|
| CloudFormation の YAML の解析と位置 | `github.com/goccy/go-yaml`(すでに直接の依存)の解析木とトークンの位置。Go の値への変換(別名の展開)はしない | トークンごとに行・桁・位置を持ち、元のテキストの範囲を求められる(機能設計 BR4.4)。アンカー・別名・タグ(`!Ref` など)・引用符の種類・ブロックスカラーを見分けられる(BR4.1、BR4.2)。位置の単位(バイトか文字か)は Code Generation の最初に確かめ、文字ならバイトに直す(セキュリティの要件 NFR3.17) |
| CloudFormation の JSON の解析と位置 | Go の標準の `encoding/json` の `Decoder`(`Token` と `InputOffset`)で、キーと値の文字列の範囲を元のテキストから求める | JSON の文字列のエスケープを JSON の規則どおりに扱える(BR4.4)。入れ子の上限がある。新しい依存が要らない。JSON を YAML として読むと、JSON と YAML のエスケープの違いを考えなければならない |
| Terraform の `.tf` の解析と位置 | `github.com/hashicorp/hcl/v2` の `hclsyntax`(新しい依存。MPL-2.0)。`hclwrite` は使わない | `resource` ブロック、`tags` 属性、オブジェクトの書き方の項目ごとの範囲(バイトの位置)が取れる。補間とヒアドキュメントを見分けられる(BR4.2)。Terraform 本体や AWS プロバイダーのライブラリは足さない |
| `terraform show -json` の読み取り | Go の標準の `encoding/json` | 形が決まった JSON で、必要な項目(`format_version`、`values`、`planned_values` などの有無、`address`、`mode`、`values.arn`)だけを読む |
| 差分(unified diff) | 自前の行単位の差分を `internal` に作る | 新しい依存を足さない。Edit の範囲から変わった行が分かるので、前後3行の範囲を作るだけでよい。差分の形は NFR の設計で決める |
| git の確かめ | `os/exec` で利用者の `git` を呼ぶ(シェルを通さない) | セキュリティの要件 NFR3.20 |
| 壊れない書き出しと Windows のやり直し | U4 の `internal/fileout` に「元のファイルを置き換える」書き方を足し、U6 の `internal/journal` の一時ファイルと名前の変更とやり直しの部品を `fileout` に寄せて、journal と iac の両方が使う。同じ役割の部品を別に作らない | 同じ問題をすでに解いている(U6 の NFR6.1、NFR9.9)。依存の向きを、記録(journal)から利用者のファイル(fileout)へ一方向にする。部品の分け方は NFR の設計で決める(セキュリティの要件 NFR6.5) |
| CloudFormation の Type と resourceType の対応表 | `internal/awsaccess` の書き換えの対象の種類の表(U6)に、CloudFormation の Type の列を足す | apply が書き換える種類と同じ範囲にでき、表を1つにできる(機能設計 BR3.2) |
| 表示 | U4 の言語・色・表の部品 | 機能設計 BR6.1 |

## 要件

| ID | 要件 | 合否の基準 |
|---|---|---|
| NFR5.25 | 10,000 リソースの変更案(変更 約 30,000。CloudFormation と Terraform に半分ずつ)と、`--dir` に 2,000 個のテンプレートと `.tf`(合わせて 100 MB)がある場合に、`iac` は差分の表示まで、`--write` では書き出しまでを 60 秒以内に終える(Q3)。測るのは `iac` の実行の始めから終わりまで(偽のファイルを作る時間は含めない) | CI の大きなテストで、上の件数を偽のファイルで作り、`--write` あり(git の呼び出しは差し替え)で3つの OS のそれぞれで 60 秒以内に終わる。`race` のビルドでは件数を10分の1にする(U6・U7 と同じ)。Code Generation の最初に、YAML(goccy/go-yaml)と HCL の解析の速さを小さく測り(例: 10 MB の YAML と `.tf`)、60 秒に収まる見込みを記録する。見込みが 30 秒を超えるなら、解析の前の絞り込み(セキュリティの要件 NFR3.19 (d))を強めるか、目標を人に相談する。手元で、実際の git を使って1回測り、記録する |
| NFR5.26 | ファイルを読む回数と解析する回数を抑える。候補のファイルはそれぞれ1回だけ読んで解析し、論理 ID とアドレスの索引を作ってから場所を決める(リソースごとにファイルを読み直さない)。書き換える対象のないファイルの解析木は、索引を作ったあと持ち続けない | 大きなテストで、ファイルを開いた回数が「候補のファイルの数 + 書き換えたファイルの数 × 3(書き出し前の確かめ、一時ファイルの確かめ、書き換えたあとの解析の確かめ)」以下であることを確かめる(ファイルの読み取りを数える差し替えで)。ヒープの最大はセキュリティの要件 NFR3.19 の基準で確かめる |
| NFR9.12 | 新しい依存 hcl/v2 も3つの OS で、CI の Go の2つの版(stable と oldstable)でビルドでき、CGO を使わない(単一の実行ファイルで配る。要件 NFR9) | CI のビルドとテストのジョブが、3つの OS と Go の2つの版で `CGO_ENABLED=0` で通る。`go.mod` の `go` の行を hcl/v2 が上げないことを確かめる(上げる場合は人に相談する) |
| NFR10.13 | 新しい依存 hcl/v2 も、既存の CI の `govulncheck` と Dependabot の対象になり、既知の脆弱性で呼ばれるものがない。足した間接の依存の数と、実行ファイルの大きさの増え方を記録する | CI の `govulncheck` のジョブが通る。`.github/dependabot.yml` が `gomod` を対象にしていることを確かめる。Code Generation の結果(`code-summary.md`)に、増えた間接の依存の一覧と、実行ファイルの大きさ(前と後)がある |
| NFR10.14 | 機能設計から送られた確かめをテストにする: (a) CloudFormation の Type と resourceType の対応表のすべての行を数えて確かめる(apply が書き換える種類と同じ数)。(b) `terraform show -json` の形は、Terraform の公式の文書の出力の例と、手元で terraform を使える場合は実物の出力から採った例(Terraform と AWS プロバイダーの版を記録する)をテストの入力にする。(c) `values.arn` を持つと期待する Terraform の種類(対応表の種類に対応する `aws_*`)を、その例で確かめる | (a)〜(c) のテストが通る。テストの入力のファイルに、採った元(文書の場所か、版)が書いてある |
| NFR12.1 | U8 が足した MPL-2.0 の依存の義務を、配布の作業に引き継ぐ。U8 では、README にライセンスの節を作り(なければ)、hcl/v2 が MPL-2.0 であること、このツールは hcl/v2 のソースを変えずにライブラリとして使うこと、hcl/v2 のソースの入手先(GitHub のリポジトリ)を書く。配るバイナリにライセンスの文を同梱することとソースの入手先の案内は、配布の作業(要件 NFR12、`v0.1.0` の前の作業)の持ち物とし、`unit-of-work.md` の「今回の作業単位に含めないもの」の配布の項目に書き足す(NFR 要件のステージで書き足し済み) | README にライセンスの節と上の3つの点がある(Code Generation で確かめる)。`unit-of-work.md` の配布の項目に、MPL-2.0 のライセンスの文の同梱とソースの入手先の案内がある |

### 測る条件(NFR5.25)

| 条件 | 値 |
|---|---|
| 変更案のリソース | 10,000(CloudFormation 5,000、Terraform 5,000) |
| 変更 | 約 30,000(リソースあたり 3。4種類を混ぜる) |
| テンプレート | 1,000 個(1つに 5 リソース。YAML 800、JSON 200)、合わせて約 60 MB |
| `.tf` | 1,000 個(1つに 5 ブロック)、合わせて約 40 MB。`--tf-state` は 5,000 リソース |
| 手で直すもの | 約 10%(式、アンカー、場所が決まらないもの) |
| 候補でないファイル | `.json` の設定ファイル 1,000 個(`Resources` を含まない。解析しないことを確かめる) |

## 当てはまらない要件

| 要件 | 理由 |
|---|---|
| NFR1(scan と plan の時間) | `iac` は scan と plan を含まない。時間は NFR5.25 で決める |
| NFR2(影響分析) | `iac` は影響分析をしない |
| NFR4(rollback の差分0) | `iac` は AWS のタグを変えない。IaC のファイルは、git が追跡していて変更のないファイルだけを書き換えるので、git で戻せる(セキュリティの要件 NFR3.20) |
| NFR5 の AWS の呼び出し(時間の上限、再試行) | `iac` は AWS を呼ばない(セキュリティの要件 NFR3.16)。git の呼び出しの時間の上限は NFR3.20 |
| NFR7(同時実行の印) | `iac` は記録も印も使わない。同じファイルを同時に書き換える2つの `iac` は、多くの場合、書き出し前の確かめ(NFR6.6)で後の方が止まる(確かめと名前の変更の間の短い窓は残るが、git で戻せる) |

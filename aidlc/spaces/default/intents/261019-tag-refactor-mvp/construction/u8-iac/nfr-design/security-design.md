# セキュリティと信頼性の設計: U8 IaC への反映

U8 の NFR 要件(`construction/u8-iac/nfr-requirements/`)を、どの仕組みで満たすかを決めます。部品の置き場所は `logical-components.md` にあります。

出典: U8 の NFR 要件(NFR3.16〜NFR3.21、NFR5.25、NFR5.26、NFR6.5、NFR6.6、NFR8.27、NFR9.11、NFR9.12、NFR10.12〜NFR10.14、NFR11.10、NFR12.1)、U8 の機能設計(`rules.md` BR1.1〜BR6.3)、`nfr-design-questions.md` Q1〜Q6 と、レビュー1回目のあとの人の判断(YAML の解析器、種類の表の置き場所)、U4 の `internal/fileout`、U6 の `internal/journal` の保存の部品。

## 0. NFR 要件からの変更(人の判断)

- **YAML の解析器:** NFR 要件の技術の選択では goccy/go-yaml としたが、goccy/go-yaml v1.19.2 のトークンの位置は、コメント・ブロックスカラー・二重引用符の中のエスケープのたびに1つずつずれ、行もずれるため、範囲の差し替えに使えない(レビュー1回目の実測)。10 MB の YAML の解析に約5秒、解析のあとに約 1 GB を使う。人の判断で `go.yaml.in/yaml/v3`(YAML の組織が保守する yaml.v3 の後継。MIT と Apache-2.0)を直接の依存にする。手元の実測で、行と桁(桁は文字の数、1始まり)はコメント・ブロックスカラー・エスケープ・日本語のあとでも正しく、10 MB の CloudFormation 風の YAML の解析は約 0.5 秒、解析のあとに残るのは約 190 MB(約 19 倍)だった。新しい依存は hcl/v2 と yaml/v3 の2つになる(NFR10.13 の記録と govulncheck の対象に yaml/v3 も含める)。
- **git の確かめ:** NFR 要件 NFR3.20 は `git status` で変更・未追跡・ignore を見るとしたが、`git status` はファイルのフィルター(clean のコマンド)を実行しうる(レビュー1回目)。設計では `git status` を使わず、`ls-files -s` のハッシュと手元のファイルのハッシュを自分で比べる(§6)。NFR3.20 の合否の基準(fsmonitor の印が作られない、`GIT_DIR` を無視する、特殊な名前、未追跡・ignore・変更ありで止まる、約 1,000 ファイル、時間切れ)はそのまま満たす。
- **種類の表:** `nfr-design-questions.md` Q3 の A(`internal/awsaccess` の表に列を足す)は、awsaccess が AWS SDK に依存して iac が AWS の部品を取り込むこと、今の表がサービスごとの行で resourceType を引けないことから、人の判断で、SDK に依存しない小さな新しいパッケージに resourceType ごとの行で置く形に改める(`logical-components.md`)。

## 1. AWS を呼ばないこと(NFR3.16)

- `internal/cli` の `iac` のコマンドは、AwsAccess の `Session` を作らず、AWS の設定(プロファイル、認証情報)も読まない。ほかのコマンドの共通の準備(アカウントの確かめなど)を通らない形でコマンドを組み立てる。コマンドの組み立ての口は、AwsAccess の接続と書き込みの口を受け取らない型にする(コンパイルの段階で渡せない)。
- `internal/iac` が直接取り込むこのツールのパッケージは、SDK に依存しない種類の表(`internal/restype`)、U4 の変更案の読み込み(`internal/planner`)、`internal/fileout`、`internal/errkind` だけで、`internal/awsaccess` は直接取り込まない。テストで、`go list -f '{{join .Imports "\n"}}' ./internal/iac` の直接の取り込みに `internal/awsaccess` と `github.com/aws/aws-sdk-go-v2` で始まるパッケージがないことを確かめる。
- `internal/planner` は `internal/inventory` を通して SDK を取り込む(間接の依存。レビュー2回目で確かめた)。実行ファイルは1つで、SDK はもともと全体に含まれるので、間接の依存は受け入れる。AWS を呼ばないことは、(1) 直接の取り込みの確かめ、(2) コマンドの組み立ての口の型、(3) 偽の AWS への要求が0件の実行のテスト、の3つで確かめる(NFR3.16 の合否の基準は (2) と (3))。変更案の読み込みを SDK に依存しないパッケージに切り出すことは、U8 では行わない(U4 の読み込みの作りを変えないため)。

## 2. ファイルの集め方と上限(NFR3.18、NFR3.19、機能設計 BR3.1)

1. `--dir` を `filepath.Abs` と `filepath.EvalSymlinks` で1回だけ実際の場所に直し、これを根とする。
2. 根から `filepath.WalkDir` で歩く。各項目は `Lstat` の種類で判断し、種類のビットが「フォルダー」だけのもの(`ModeDir` のほかに種類のビットがない)と「通常のファイル」だけのもの(種類のビットがない)だけを扱う。シンボリックリンク、Windows のジャンクションとそのほかの再解析ポイント(Go では `ModeIrregular` か `ModeSymlink` が付く)、そのほかの特殊なファイルは、たどらず読まない。
3. 名前が `.git`、`.terraform`、`node_modules`、`cdk.out` のフォルダーは入らない。根からの深さが 32 を超えるフォルダーは入らず、外した数を数える。
4. 候補の拡張子(CloudFormation: `.yaml`・`.yml`・`.json`・`.template`、Terraform: 根の直下の `.tf`)のファイルだけを数え、20,000 個を超えたら InvalidInput で止める。
5. 候補のファイルは `Lstat` の大きさが 10 MB を超えれば読まずに外す。読むときも 10 MB + 1 バイトまでしか読まない。読んだ合計が 500 MB を超えたら InvalidInput で止める。
6. 中身の確かめ: UTF-8 として正しくないもの、UTF-16 と UTF-32 の BOM で始まるものは外す。UTF-8 の BOM は覚えておき、解析には BOM を除いた中身を渡し、位置には BOM の3バイトを足す。CloudFormation の候補は、中身に `Resources` の文字列がなければ解析しない。
7. 入れ子の事前の確かめ(Q6): 形式ごとの字句の走査で、解析器が再帰する構造の深さを数え、どれかが上限を超えるファイルを外す。走査は1回で、ファイルの大きさに比例する時間で終わる。
   - YAML: 行ごとに、引用符(`'` の中の `''`、`"` の中の `\`)、コメント(`#` の前が空白か行頭)、ブロックスカラー(`|` か `>` で始まる値の次の行から、インデントがその行の始まりより深い行の終わりまで)を飛ばす。数えるのは、(a) `[` と `{` の深さ、(b) インデントの段の数(インデントが深くなるたびに1つ)、(c) 行の始まりの `- ` と `? ` の続く数(同じ行の `- - - x` は3段)を (b) に足したもの。どれかが 256 を超えれば外す。
   - JSON: 文字列(`\` のエスケープ)を飛ばし、`[` と `{` の深さが 256 を超えれば外す。
   - HCL: 文字列(`"` と `\`、`${` と `%{` の中の入れ子)、コメント(`#`、`//`、`/* */`)、ヒアドキュメント(`<<EOT` か `<<-EOT` から、終わりの印だけの行まで)を飛ばす。数えるのは、(a) `[`・`{`・`(`・`${`・`%{` の深さ(256 まで)、(b) 単項の演算子 `!` と `-` が空白をはさんで続く長さ(256 まで)、(c) 条件式の `?` の数(ファイル全体で 10,000 まで。条件式の連鎖の再帰のため)。
   - 上限の値は、Go のスタックの上限(既定 1 GB)に対して十分に小さい(1段あたり数 KB として数十 MB)。Go のスタックの使い切りは回復できない誤りなので、解析器に渡す前に必ずこの走査を通す。
8. 外したファイル・フォルダーの数は、理由ごとに標準エラーに1行ずつの警告で示す。名前は `--debug` で示す(ファイルの中身は出さない)。

変更案は 200 MB、`--tf-state` は 500 MB を超えれば読まずに止める(`Stat` の大きさと、読みの上限の両方)。変更案は U4 の読み込みを使う(ファイル全体を読むので、ピークはファイルの約2倍まで)。`--tf-state` は `encoding/json` の `Decoder.Token` で `values` の `root_module` と `child_modules` の中を流して読み、`resources` の要素を1つずつ小さな構造体(`address`、`mode`、`type`、`values.arn` だけ)に読み込み、ほかの値は捨てる(ピークは要素1つ分)。

## 3. 解析と位置(NFR3.17、機能設計 BR4.1、BR4.2、BR4.4)

形式ごとの読み取りは、同じ形の口で「リソースの索引」と「1つのリソースのタグの書き場所」を返す(`logical-components.md`)。位置はすべて、元のファイルのバイトの位置で持つ。

- **YAML(go.yaml.in/yaml/v3 の `Node`):** `yaml.Unmarshal` で `Node` の木を作る(Go の値には変換しない。別名は `AliasNode` のまま展開しない)。`Node` の `Line` と `Column`(1始まり、桁は文字の数)から、ファイルの行の始まりのバイトの位置の表と、その行の中の文字の数を使ってバイトの位置を求める。スカラーの範囲の終わりは、その行のテキストを自前で走査して求める: 引用符なしはスカラーの値と同じ文字の並びの終わり、`'` と `"` は閉じの引用符まで(`''` と `\"` を扱う)。求めた範囲の中の文字を、もう一度 YAML のスカラーとして読み直して `Node.Value` と同じであることを確かめ、違えばそのファイルを書き換えない(機能設計 BR4.4 の unreadableFile)。アンカー(`Node.Anchor`)、別名(`AliasNode`)、マージのキー(`<<`)、タグ(`Node.Tag` が `!!str` などの既定のもの以外。`!Ref` など)、ブロックスカラー(`Style` が `LiteralStyle` か `FoldedStyle`)、複数行のスカラー(範囲が1行に収まらない)は、`Node` の項目で見分ける。要素の範囲は、要素の始まり(並びの `- ` の位置、マッピングの最初のキー)から、要素の最後のスカラーの範囲の終わりまで(その行の終わりのコメントは要素に含める)。
- **JSON(`encoding/json` の `Decoder`):** トークンを順に読み、各トークンを読む前後の `InputOffset` から、キーと値の文字列の範囲(前の空白とカンマを除いたもの)を元のテキストから求める。範囲の中の文字を JSON の文字列として読み直して同じ値になることを確かめる。配列の要素の範囲(`{` から `}` まで)と、要素の間の区切り(カンマと空白)のテキストを持つ。
- **HCL(`hclsyntax`):** `hclsyntax.ParseConfig` の解析木から、`resource` ブロックの種類と名前、`tags` 属性の式、オブジェクトの書き方(`ObjectConsExpr`)の項目のキーと値の式の範囲(`hcl.Range` の `Byte`。もともとバイトの位置)を取る。値が `TemplateExpr` で、部分が文字列だけ1つ(補間なし)で、範囲が1行のものを literal とする。キーは `ObjectConsKeyExpr` が名前か文字列のものを literal とする。項目が別々の行にあるかは、項目の範囲の行で判断する。

解析の誤りは、ファイル名・行・桁・誤りの種類(このツールが決めた短い文字列)に直して持ち、解析器の誤りの文(ソースの抜粋を含みうる)は持ち続けない(NFR8.27)。

### メモリの予算(NFR3.19、NFR5.25)

- 同時に解析するファイルの大きさの合計を 32 MB までにする(解析の作業者は、解析を始める前に予算を取り、終えたら返す)。32 MB を超える予算は取れないので、1つのファイルは最大 10 MB で、大きなファイルどうしは同時に3つまでになる。yaml/v3 の約 19 倍で、解析中に持つのは約 600 MB まで。hcl/v2 の倍率は Code Generation の最初の計測で確かめ、30 倍を超えるなら予算を小さくする。
- `iac` の実行のあいだ、`debug.SetMemoryLimit` で Go の柔らかいメモリの上限を 1.5 GB にし(GC を早める)、終えたら元に戻す。
- 解析した結果は索引を作ったら手放し、書き換える対象のあるファイルだけを、あとでもう一度読んで解析する(NFR5.26)。2回目の解析の時間は、NFR5.25 の見込みに含める(YAML 約 50 MB × 2 で、yaml/v3 の実測から約 5 秒)。

## 4. Edit の作り方、当て方、確かめ(機能設計 BR4.3〜BR4.6)

1. リソースごとに、元のタグの並びをメモリの上で写し、変更を変更案の順に当てる(機能設計 BR4.3 の pre と post)。
2. 当てたあとの並びを元の並びと比べて、Edit を作る。
   - **削除も追加もないリソース:** 元の要素ごとに「キーの差し替え」と「値の差し替え」の Edit だけを作る(範囲は重ならない)。
   - **削除か追加があるリソース:** 要素ごとの Edit にし、要素に属さないテキスト(要素の間の行全体のコメント、コメントアウトしたタグ、空行)は元の位置のまま残す。
     - 残す要素: キーと値の差し替えの Edit だけ(上と同じ)。
     - 消す要素(YAML と HCL): その要素の行(要素の始まりの行の頭から、要素の最後の行の改行まで。その行の終わりのコメントを含む)を消す。要素の行に、ほかの要素や要素に属さないテキストがあれば(1行の書き方)、機能設計 BR4.4 のとおり削除しない(unsupportedTagShape)。
     - 消す要素(JSON): 最後の要素でなければ、その要素と、あとに続くカンマと、次の要素の前までの空白を消す。最後の要素なら、前の要素の終わりのすぐあとのカンマから、その要素の終わりまでを消す。
     - 足す要素: 残る元の要素のうち最後のものの終わりのすぐあとに、「区切り + 写した要素」を挿入する。区切りは、元の要素の間のテキストのうち、空白(と JSON のカンマ)だけからなる最初のもの。そのようなものがない(元の要素が1つ、またはすべての間にコメントがある)ときは、YAML と HCL は「改行 + 最後に残る要素の行のインデント」、JSON は「`,` + 改行 + 最後に残る要素の行のインデント」(要素が `[` と同じ行なら `, `)。改行の種類はファイルの改行の種類(最初の改行)に合わせる。
     - 同じ位置で始まる削除と挿入(JSON で、最後の要素を消し、そこへ足す場合)は、1つの Edit(範囲を「区切り + 写した要素」に置き換える)にまとめる。
   - **すべての元の要素を消すリソース:** 書き場所の値の範囲(YAML は `Tags:` のあとの空白から最後の要素の終わりまで、JSON と HCL は `[` か `{` から `]` か `}` まで)を、1つの Edit で置き換える。足すものがなければ空の書き方(YAML は ` []`、JSON は `[]`、HCL は `{}`)、あれば写した要素だけの並び(最初の要素の行のインデントで)。この範囲に要素に属さないテキスト(コメント、空行)があれば、置き換えずに、消す変更と足す変更を unsupportedTagShape にする(コメントを消さないため)。
   - どの Edit も要素の範囲か書き場所の値の範囲の中だけを変えるので、ファイルの終わりに改行がない場合も、範囲の外は変わらない。確かめの (c) に加えて、書き換えたあとの中身で、要素に属さないテキスト(コメントと空行)の並びが元と同じことを確かめる(§4 の 4 の (d))。
3. 1つのファイルのすべての Edit を、始まりの位置の大きい順に当てる。範囲が重なったら、このツールの不具合としてそのファイルを書き換えない。
4. 当てたあとの中身を、同じ読み取りでもう一度解析し、(a) 対象のリソースのタグの並びが、メモリの上で当てた並びと同じ、(b) ファイルのリソースの数と、対象でないリソースのタグの並びが元と同じ、(c) Edit の範囲の外のバイトが元と同じ(Edit を当てた位置から計算して比べる)、(d) 対象のリソースのタグの書き場所の中の、要素に属さない行(コメントと空行)の並びが元と同じ、ことを確かめる。違えばそのファイルの Edit をすべてやめ、ManualItem(unreadableFile)にする。

## 5. 引用符とエスケープ(機能設計 BR4.4)

| 書く場所 | 書き方 |
|---|---|
| YAML の引用符なし | 新しい文字列が「先頭が英字か数字で、英字・数字・`_`・`.`・`/`・`@`・`-` だけからなり、YAML 1.1 と 1.2 のどちらでも文字列に読める」ときだけ、そのまま書く。許す文字に `:` と空白がないので、60進(`1:20`)と時刻を含む日付の形は先に外れる。残りについて、真偽値(`y`・`n`・`yes`・`no`・`on`・`off`・`true`・`false` の大文字小文字のすべて)、null(`null`・`Null`・`NULL`)、数(10進、8進 `0o` と先頭の `0`、16進 `0x`、2進 `0b`、`_` の区切り、指数、`.inf`・`.nan` とその大文字小文字)、日付(`2026-10-31` の形)に当たらないことを確かめる。当たれば `"` で囲む |
| YAML の `'` | `'` を `''` にする。改行や制御文字を含む新しい文字列は `"` に変える |
| YAML の `"` | `\`、`"`、制御文字を YAML の `"` のエスケープにする |
| JSON | `encoding/json` の文字列の書き方(HTML のエスケープはしない) |
| Terraform | `"` で囲み、`\`、`"`、制御文字をエスケープし、`${` を `$${`、`%{` を `%%{` にする。キーは HCL の名前の形(英字か `_` で始まり、英字・数字・`_`・`-`)なら名前のまま、でなければ同じ書き方の文字列 |

タグのキーと値は AWS の上限(キー128文字、値256文字)を変更案の段階で満たしているので、ここでは長さを確かめない。

## 6. git の確かめ(NFR3.20、機能設計 BR5.2)

`git status` は、リポジトリの設定の fsmonitor やファイルのフィルター(`.gitattributes` の `filter` の clean のコマンド)を実行しうるので使わない。代わりに、インデックスに記録されたファイルのハッシュと、手元のファイルのハッシュを、このツールが自分で比べる。

- 呼ぶのは `git` だけで、`exec.LookPath("git")` で見つからなければ止める(終了コード 1)。
- 環境: 今の環境から、名前が `GIT_` で始まる変数(Windows では大文字小文字を問わない)をすべて除き、`GIT_OPTIONAL_LOCKS=0`、`GIT_LITERAL_PATHSPECS=1`、`GIT_TERMINAL_PROMPT=0` を足す。
- 引数: すべて `git -c core.fsmonitor=false -C <根> ...`。
  1. `rev-parse --is-inside-work-tree`: 標準出力の空白を除いたものが `true` でなければ止める。
  2. `rev-parse --show-object-format`: `sha1` か `sha256` を得る(どちらでもなければ止める)。
  3. `ls-files -s -z -- <ファイル>...`: 各行の「モード、オブジェクトのハッシュ、ステージ、パス」を読む。書き換えるファイルのうち、出力にないもの(追跡されていない、ignore されている)、ステージが 0 でないもの(衝突の途中)、モードが通常のファイル(`100644` か `100755`)でないものがあれば止める。
  4. `ls-tree -z HEAD -- <ファイル>...`: コミット済みの同じパスのハッシュを読む。HEAD がない(まだコミットがない)、出力にないファイルがあれば止める。
  5. 書き換えるファイルごとに、(a) インデックスのハッシュと HEAD のハッシュが同じ(`git add` 済みでコミットしていない変更がない)、(b) 手元の中身(最初に読んだもの)から計算した git の blob のハッシュ(`blob <長さ>\0<中身>` の SHA-1 か SHA-256)がインデックスのハッシュと同じ、の両方を確かめる。(b) が同じでなければ、CRLF を LF に直した中身でも計算し(Windows の `core.autocrlf` のため)、それも違えば「コミットしていない変更がある」として止める。フィルター(Git LFS など)を使うファイルは、ハッシュが合わないので止まる(安全な側)。
- パスの照合: `ls-files` が返すパスは、渡したパスと Unicode の正規化(macOS の NFC と NFD)が違うことがある。出力に見つからないパスは、そのパスだけで `ls-files -s -z -- <パス>` をもう一度呼び、1件だけ返ればそれを使う(git が自分の設定で正規化するため)。
- ファイルは根からの相対パスを `/` で区切って渡す。引数の長さを「固定の引数と根のパスの長さ + 各ファイルのパスの長さ + 3(引用符と区切り)の合計」で数え、30,000 を超えるときは何回かに分けて呼ぶ。
- 時間: 各呼び出しに 60 秒の `context` を付けた `exec.CommandContext` を使い、`cmd.WaitDelay` を 5 秒にして、時間切れのときに子のプロセスと入出力の待ちを打ち切る。時間切れ・終了コードが 0 でない・出力が読めないときは止める(終了コード 1。git の標準エラーは `--debug` で示す)。
- 呼び出しは差し替えられる関数にし、テストで時間切れや出力を作る。
- 残るリスク: `rev-parse`・`ls-files`・`ls-tree` は、リポジトリの設定のプログラムを実行しないが、利用者の git そのもの(`PATH` の `git`)は信用する。README に書く。

## 7. 書き出し(NFR6.5、NFR6.6、NFR9.11、機能設計 BR5.3、Q2)

`internal/fileout` に、元のファイルを置き換える書き方と、名前の変更のやり直しの部品を足す。

- **やり直しの部品:** `RetryRename(old, new string, waits []time.Duration, retryable func(error) bool, rename func(string, string) error, sleep func(time.Duration))`。失敗し、`retryable` が真を返すたびに、`waits` の数だけ待ってやり直す。偽ならすぐ返す。
  - `journal` は、今のパッケージの変数 `rename`・`renameAttempts`・`renameWait`・`sleep` をそのまま持ち、これらから `waits`(100 ミリ秒 × 4)と関数を作って渡し、`retryable` にはすべての誤りで真を返す関数を渡す(今の動きのまま。journal のテストの差し替えと期待はそのまま通る)。
  - 利用者のファイルは、`retryable` に「Windows の一時的な失敗(`syscall.Errno` の共有違反 32、ロック違反 33、アクセス拒否 5)なら真」を渡す。この関数は Windows のビルドだけで番号を見て、ほかの OS では常に偽を返す(Linux と macOS ではやり直さない)。待ちは 100・200・400・800・1,600・1,600 ミリ秒(合わせて 4.7 秒、6回のやり直し)。
- **置き換え(`Replace`):**
  1. **すべてを先に確かめる(NFR6.6):** git の確かめ(§6)のあと、書き出しの直前に、書き換えるすべてのファイルを読み直し、最初に読んだときの中身の SHA-256 と同じかを確かめる。1つでも違えば、どれも書かずに止める。読み取り専用のファイル(Windows の読み取り専用の属性、Linux と macOS で持ち主に書く権限がない)があれば、どれも書かずに止める。
  2. **1つずつ書く:** ファイルごとに、同じフォルダーに `.<元の名前>.tag-refactor-<乱数>.tmp` の一時ファイルを、利用者だけが読める権限(0600)で `O_EXCL` で作り、新しい中身を書いて `Sync` して閉じる。
  3. **一時ファイルを確かめる:** 一時ファイルを読み直し、書くべき中身とバイト単位で同じかを確かめる。違えば一時ファイルを消して止める(元のファイルは変わらない)。
  4. **権限を合わせる:** 元のファイルの権限(Linux と macOS の `Mode().Perm()`)を一時ファイルに付ける。
  5. **名前を変える:** やり直しの部品で、一時ファイルの名前を元のファイルの名前に変える。
  6. **失敗したら:** 一時ファイルを消し、書いたファイルと書いていないファイルを結果に示して止める(終了コード 1)。
- **途中の取り消し(Ctrl+C):** 書き出しの途中で `context` が取り消されたら、書いているファイルの 2〜5 を終えてから(名前の変更は一瞬で終わり、途中の状態がないため)止め、残りのファイルは書かない。結果に書いたファイルと書いていないファイルを示し、終了コード 1。書き出しの前(解析や git の確かめの間)の取り消しは、何も書かずに止める。
- 改行の種類と BOM は、Edit の範囲の外を変えないことで保つ(§4 の (c))。利用者のフォルダーでは、古い一時ファイルを消す処理は行わない(`journal` の記録のフォルダーだけに残す)。

## 8. 出さないもの(NFR8.27)

| もの | 扱い |
|---|---|
| 差分の外のファイルの中身 | 持つのはファイルの中身全体だが、出力するのは差分(Edit のある行と前後3行)だけ。`--debug` でも出さない |
| 解析の誤り | ファイル名・行・桁・誤りの種類だけ(§3) |
| `--tf-state` の中身 | 読むときに `address`、`mode`、`type`、`values.arn` だけを取り出し、ほかの値は捨てる(§2) |
| 変更案のタグの値 | 差分に出る値と、手で直す一覧のキーだけを出す。手で直す一覧には値を出さない |
| 環境変数、git の環境 | 出さない。git の標準エラーだけを `--debug` で出す |

## 脅威と対策(U8 で足すもの)

| 脅威 | 対策 |
|---|---|
| 他人のリポジトリの git の設定で、任意のコマンドを実行させる | `git status` を使わず、`rev-parse`・`ls-files`・`ls-tree` だけを `core.fsmonitor=false` で呼び、ハッシュは自分で比べる(フィルターを動かさない)。`GIT_` の環境変数を除く(§6)。利用者の git そのものは信用する(残るリスク) |
| ファイル名で git に別のファイルを見させる | `GIT_LITERAL_PATHSPECS=1`、`--` のあとに相対パス(§6) |
| 深い入れ子で解析器のスタックを使い切る | 解析器が再帰する構造(括弧、インデント、行の始まりの `- `、単項の演算子、条件式)を事前の走査で数えて外す(§2) |
| YAML の別名の爆弾 | `Node` の木だけを使い、Go の値に変換しない(§3) |
| 大きなファイルでメモリを使い切る | 大きさと合計の上限、同時に解析する合計 32 MB の予算、柔らかいメモリの上限(§2、§3) |
| リンクで `--dir` の外を書き換えさせる | 種類のビットが通常のファイルとフォルダーだけのものを扱う(§2) |
| 位置のずれで別の文字を書き換える | 範囲の中の文字の読み直しの確かめと、書き換えたあとの解析の確かめ(§3、§4) |
| 書き出しの途中の停止 | 一時ファイルの確かめと名前の変更、取り消しは1つのファイルを終えてから(§7) |
| 解析の誤りの文で秘密の値が出る | 誤りの文をそのまま持たない(§3、§8) |

# 機能設計 — 質問(U5 影響分析)

U5 は、U1 で作った影響分析の最小版(利用者が作った管理ポリシーの `<前置>:ResourceTag/<キー>` だけを、キー名の変更について照合)を完成させます。読むポリシーを IAM のインラインポリシーと5種類のリソースポリシーに広げ、タグに関する条件キーのすべての種類と、値の変更、タグの削除を扱います。入出力は契約 C9(`Analyze(ctx, []TagChangeInput) -> ImpactResult`)と C2 の `impactFindings`、`unreadPolicies` のままです。

決まっていること(質問しません):

- 読むポリシーの種類は、IAM のユーザー・ロール・グループに付いた、利用者が作った管理ポリシーとインラインポリシー(FR4.1)と、S3 バケット、KMS キー、SQS キュー、SNS トピック、Secrets Manager のシークレットのリソースポリシー(FR4.2)。`sourceKind` は C2 の7つ(`iamManaged`、`iamInline`、`s3Bucket`、`kmsKey`、`sqsQueue`、`snsTopic`、`secretsManagerSecret`)。
- 対象外: SCP と RCP、AWS Backup、DLM、SSM、Resource Groups、Auto Scaling のタグ指定(CON3)。KMS は利用者が作ったキーだけを読む(AWS が管理するキーのポリシーは利用者が変えられず、タグの条件を持たないため)。
- 照合する条件キーは、前置(`aws` かサービス名)のあとが `ResourceTag/<キー>`、`RequestTag/<キー>`、`PrincipalTag/<キー>`、`TagKeys` のもの(FR4.4)。前置と、`ResourceTag` などの綴りは大文字・小文字を区別せずに比べる(U1 BR5.2 を広げる)。S3 のオブジェクトのタグ(`s3:ExistingObjectTag/`、`s3:RequestObjectTag/`)は、このツールが変えないため対象外。
- 演算子の前に付く `ForAnyValue:`、`ForAllValues:` と、後ろに付く `IfExists` は、照合では外して考え、表示には書いたまま残す。
- キー名の変更(`renameKey`)とタグの削除(`removeKey`)は、条件のタグのキーが変更のキーに当てはまれば、値に関係なく影響あり(`affected`)。大文字・小文字だけの名前の変更を影響なしとするのは、AWS のドキュメントで大文字・小文字を区別しないと書かれている `aws:ResourceTag` だけ(U1 BR5.3 のまま。ほかは見逃さない側に倒す)。
- 条件のタグのキーにポリシー変数(`${...}`)があれば判定できない(`undecided`)。ワイルドカード(`*`、`?`)はパターンとして当てはめる(U1 BR5.4 のまま)。
- 指摘は(ポリシー、ステートメント、演算子、条件キー)ごとに1件で、当てはまる変更の `changeId` をすべて持つ(U1 BR5.6 のまま)。
- ポリシーが無い(バケットにポリシーが付いていないなど)ことは「読めなかった」ではない。権限がない、一時的な失敗が続いたなどで読めなかったものは `unreadPolicies` に入れ、影響分析を不完全にする(FR4.7、U1 BR5.5)。読めたものの照合は続ける。
- 呼ぶ API はすべて読み取りだけ(NFR3)。読み取り用の IAM ポリシーの例(README)に、足した操作を書き足す。

## Q1. リソースポリシーを読むリソースの見つけ方

S3、KMS、SQS、SNS、Secrets Manager のリソースポリシーを、どのリソースについて読みますか?

A. 5つのサービスの一覧の API(`s3:ListBuckets`、`kms:ListKeys`、`sqs:ListQueues`、`sns:ListTopics`、`secretsmanager:ListSecrets`)で、`scan` が調べたリージョンのすべてのリソースを探し、それぞれのポリシーを読む。`scan` の結果(タグの付いたリソース)に頼らないため、タグが一度も付いていないリソースのポリシーも読める
B. `scan` で集めたリソースのうち、5つの種類のものだけを読む。一覧の API を呼ばないため呼び出しは少ないが、AWS Config も Resource Explorer も使えないと、タグが一度も付いていないリソースのポリシーは読めない
C. 変更案で変更のあるリソースのポリシーだけを読む

## Q2. IAM のどのポリシーを読むか

FR4.1 のとおり、ユーザー・ロール・グループに付いた、利用者が作った管理ポリシーとインラインポリシーを読みます。次の2つも読みますか?

- ロールの信頼ポリシー(誰がロールを引き受けられるか。`aws:PrincipalTag` や、セッションタグの `aws:RequestTag` を条件に使うことがある)
- AWS が管理するポリシー(利用者は中身を変えられない)

A. どちらも読まない。要件どおりの範囲にし、読まないことを README に書く(`sourceKind` の種類も C2 のまま)
B. ロールの信頼ポリシーも読む。`sourceKind` に `iamTrust` を足す(列挙の値を足すため、C2 の `version` を 2 に上げる)。AWS が管理するポリシーは読まない
C. 両方とも読む(`sourceKind` を2つ足し、`version` を 2 に上げる)

## Q3. 条件が、どのリソースの変更に関係するか

同じキーの変更が多くのリソースにあるとき、1つの条件をどの変更に結び付けますか?

A. ポリシーの種類と条件キーで分ける。IAM のポリシーの `ResourceTag`、`RequestTag`、`TagKeys` は、そのキーのすべての変更に結び付ける(どのリソースに対する権限にも使えるため)。リソースポリシーの `ResourceTag`、`RequestTag`、`TagKeys` は、そのポリシーが付いたリソース自身の変更だけに結び付ける。`PrincipalTag` は、どちらのポリシーでも、IAM のユーザーとロールの変更だけに結び付ける(呼び出し元のタグは、ユーザーとロールのタグのため)
B. 分けない。どのポリシーのどの条件キーも、そのキーのすべての変更に結び付ける(結び付きすぎることはあるが、見逃しはない)
C. A に加えて、IAM のポリシーのステートメントの `Resource` を変更のリソースの ARN に当てはめ、当てはまらないものは結び付けない
X. Other (please specify)

[Answer]: A

## Q4. 値の変更(`changeValue`)と条件の値

`env` の値を `Prod` から `prod` に変えるとき、`env` を使う条件はどう判定しますか?

A. 条件の値を比べる。条件の値のどれかが変更前か変更後の値に当てはまれば影響あり。大文字・小文字の区別は演算子に合わせる(`StringEquals` などは区別し、`IgnoreCase` の付くものは区別しない。`StringLike` などはパターンとして当てはめる)。否定の演算子(`StringNotEquals` など)も同じに扱う。値にポリシー変数があれば判定できない。`Null` は値の変更では影響なし。どの値にも当てはまらなければ影響なし
B. 条件の値は比べない。キーが当てはまれば、値の変更はすべて影響あり
X. Other (please specify)

[Answer]: A

## Q5. 必須タグの追加(`addRequired`)

FR4.3 は、キー名の変更、値の変更、タグの削除を影響分析の対象としています。必須タグを付ける変更(`addRequired`)も調べますか?(タグが無かったリソースに付くと、`Null` の条件や、付けた値を使う条件の結果が変わることがあります)

A. 調べる。「タグが無い状態から、付ける値への変更」として扱う。付けるキーの条件のうち、`Null` と、条件の値が付ける値に当てはまるもの(Q4 と同じ比べ方)を影響ありとする
B. 調べない。要件どおり3種類だけにし、必須タグの追加は影響分析の対象外と README に書く

## Consolidated Summary Confirmation

回答をまとめると、U5 の影響分析は次のとおりに設計します。

1. **読むポリシー:** IAM のユーザー・ロール・グループに付いた、利用者が作った管理ポリシー(U1 のまま)とインラインポリシーに加え、S3、KMS(利用者が作ったキー)、SQS、SNS、Secrets Manager のリソースポリシーを読む。リソースは5つのサービスの一覧の API で、`scan` が調べたリージョンのすべてを探す(Q1 A)。ロールの信頼ポリシーと AWS が管理するポリシーは読まず、そのことを README に書く。`sourceKind` と C2 の `version` は変えない(Q2 A)。
2. **照合する場所:** 条件キー(`ResourceTag/`、`RequestTag/`、`PrincipalTag/`、`TagKeys`。前置は `aws` かサービス名)に加え、条件の値と `Resource`、`NotResource` の中のポリシー変数(`${aws:PrincipalTag/team}` など)も調べる(Q6 A)。
3. **条件と変更の結び付け:** IAM のポリシーの `ResourceTag`、`RequestTag`、`TagKeys` はそのキーのすべての変更に、リソースポリシーのそれらはそのリソース自身の変更だけに、`PrincipalTag` は IAM のユーザーとロールの変更だけに結び付ける(Q3 A)。
4. **変更の種類ごとの判定:**
   - キー名の変更と削除: キーが当てはまれば影響あり(大文字・小文字だけの変更を影響なしとするのは `aws:ResourceTag` だけ)。
   - 値の変更: 条件の値が変更前か変更後の値に当てはまれば影響あり。比べ方は演算子に合わせ、否定の演算子も同じに扱う。値にポリシー変数があれば判定できない。`Null` は影響なし(Q4 A)。
   - 必須タグの追加: 「タグが無い状態から付ける値へ」として、`Null` と、値が付ける値に当てはまる条件を影響ありとする(Q5 A)。
   - 条件の値や `Resource` の中の変数: キー名の変更と削除は影響あり、値の変更は判定できない(Q6 A)。
   - 条件のキーにポリシー変数があれば判定できない。ワイルドカードはパターンとして当てはめる(U1 のまま)。
5. **読めなかったとき:** ポリシーが無いことは読めなかったことにしない。権限がない、一時的な失敗が続いたなどで読めなかったものは種類と理由を示し、影響分析を不完全にする。読めたものの照合は続ける。

# NFR の要件 — 質問(U5 影響分析)

U5 は、影響分析で読むポリシーを、IAM のインラインポリシーと5種類のリソースポリシーに広げます(機能設計 BR1.1〜BR1.3)。U1 では管理ポリシーの数に比例する呼び出しだけでしたが、U5 ではユーザー・ロール・グループの数と、5種類のリソースの数に比例して呼び出しが増えます。scan と plan を合わせて1万リソースで10分以内(NFR1)を守るための読み方と、ポリシーの文書を安全に読むための決まりを決めます。

決まっていること(質問しません):

- 呼ぶ操作はすべて読み取り(NFR3)。足す操作(機能設計 BR5.3)は、読み取り用の IAM ポリシーの例(`docs/iam/readonly-policy.json`)と、検証用アカウントの読み取り用ロール R2 に足し、U1・U2 の例の検査(`*` を含まない、`Get`・`List`・`Describe` で始まる、コードの操作の表と一致)を通す。R2 を変えるのは検証用アカウントの変更なので、そのときに人の許可を得る。
- 再試行、時間の上限、呼び出し回数の上限に当たったときの待ちは、U2 の AwsAccess のまま(NFR5)。
- ポリシーの中身は `--debug` にも出さない(NFR8.2)。指摘の条件の値は、U1 と同じく表示の前の置き換えを通して表示する(NFR8.6)。
- 結果の順は毎回同じ(機能設計 BR5.2)。同時に読んでも、標準出力は実行のたびに同じにする(U2 NFR5.7 と同じ確かめ方)。
- 文書は照合が終われば捨て、指摘だけを覚えておく(U1 と同じ)。

参考の見積もり(Q2 の A の規模、1回の呼び出しを0.2秒とする。検証用アカウントでの U2 の実測は `iam:GetPolicyVersion` が約0.2秒): IAM の読み取りは約2,500回、リソースポリシーの読み取りは約2,400回です。すべてを1つずつ読むと約16分で、10分を超えます。

## Q1. ポリシーを同時に読む数

ポリシーを同時にいくつ読みますか?(固定の数。利用者は変えられません。IAM はアカウント全体で1つの呼び出し回数の上限を持ち、リソースポリシーはリージョンごとに上限を持ちます)

A. IAM の読み取りは同時に4つまで。リソースポリシーは、scan と同じくリージョンを同時に8つまで読み、1つのリージョンの中は順に読む。IAM とリソースポリシーは並行して読む(見積もり: 約2分)
B. すべて1つずつ順に読む(見積もり: 約16分。10分を超える)
C. IAM の読み取りは同時に8つまで。リソースポリシーはリージョンを同時に8つ、1つのリージョンの中でも同時に4つまで(見積もり: 約1分。IAM の呼び出し回数の上限に当たりやすくなる)

## Q2. 性能を確かめる規模

影響分析の性能(呼び出しの回数、ツール自身の処理の時間、10分の見積もり)を、どの規模で確かめますか?(偽の AWS を使ったテストと、検証用アカウントでの実測からの見積もり)

A. ユーザー・ロール・グループ合わせて1,000(それぞれインラインポリシー1つ)、付いている管理ポリシー500、リソースポリシーを持つリソース2,000(S3 200、KMS 300、SQS 500、SNS 500、Secrets Manager 500。17リージョンに分ける)、変更5,000件。呼び出しの回数が式の上限以下、ツール自身の処理の時間(遅れなしの偽の AWS)が10秒以内、検証用アカウントの実測から求めた scan と plan の合計の見積もりが10分以内
B. U1 と同じ規模(管理ポリシー500、変更1,000件)に、インラインポリシーとリソースポリシーを少し足すだけにする
C. A の5倍(ユーザー・ロール・グループ合わせて5,000、リソース1万)

## Q3. ポリシーの文書の大きさと、壊れた文書

AWS が返すポリシーの文書は、通常は数 KB から数十 KB です(AWS の上限は種類ごとに 6 KB〜32 KB 程度)。想定外に大きい文書や、壊れた文書をどう扱いますか?

A. 1 MiB を超える文書は、読まずに「読めなかった」(理由は大きすぎる)にし、影響分析を不完全にする。文書の読み取りの関数を Go のファジングで確かめ(1回の読み取りが1秒を超えたら失敗)、手元で5分走らせた結果をチェックポイントの記録に残す(U4 の保存した変更案の読み込みと同じ)
B. 大きさの上限は設けない。ファジングだけを行う
C. 上限もファジングも設けない(U1 と同じく、JSON として読めなければ「読めなかった」にするだけ)

## Consolidated Summary Confirmation

回答をまとめると、U5 の NFR の要件は次のとおりです。

1. **同時に読む数(Q1 A):** IAM の読み取りは同時に4つまで。リソースポリシーはリージョンを同時に8つまで読み、1つのリージョンの中は順に読む。IAM とリソースポリシーは並行して読む。数は固定で、利用者は変えられない。同時に読んでも、結果は毎回同じ順にする。
2. **性能(Q2 A):** ユーザー・ロール・グループ合わせて1,000(インラインポリシー1つずつ)、付いている管理ポリシー500、リソースポリシーを持つリソース2,000(17リージョン)、変更5,000件の規模で、(1) 呼び出しの回数が式の上限以下、(2) 遅れなしの偽の AWS でツール自身の処理の時間が10秒以内、(3) 検証用アカウントの実測から求めた scan と plan の合計の見積もりが10分以内、を確かめる。
3. **文書の安全(Q3 A):** 1 MiB を超える文書は読まずに「読めなかった」(大きすぎる)にし、影響分析を不完全にする。文書の読み取りをファジングで確かめ(1回1秒以内)、手元で5分走らせた結果をチェックポイントの記録に残す。
4. **そのほか(決まっていること):** 呼ぶ操作は読み取りだけで、足した操作を読み取り用の IAM ポリシーの例と検証用アカウントのロール R2 に足す(R2 の変更は人の許可を得てから)。再試行と待ちは U2 のまま。ポリシーの中身は `--debug` に出さない。

# 性能と品質の要件: U5 影響分析

U1〜U4 の性能の要件(scan と plan を合わせて1万リソースで10分以内、呼び出し回数の上限、時間の上限、変更案の作成と出力の時間)は、U5 でもそのまま守ります。U5 は影響分析で読むポリシーを広げるため、呼び出しの回数と、同時に読む数、影響分析の正確さ(NFR2)の要件を定めます。

出典: 要件 NFR1、NFR2、NFR5、NFR10、機能設計 `construction/u5-impact/functional-design/`(BR1.1〜BR1.3、BR3.1〜BR3.3、BR4.1〜BR4.7、BR5.1、BR5.2、functional-spec.md の「検出率100%のテスト用の参照」)、U1 の NFR1.5、U2 の NFR1.6〜NFR1.9、NFR5.7、`nfr-requirements-questions.md` Q1、Q2。

## 測る条件(Q2)

ユーザー・ロール・グループを合わせて1,000(それぞれインラインポリシー1つ)、利用者が作った管理ポリシー600(うち付いているもの500)、リソースポリシーを持つリソース2,000(S3 200、KMS 300、SQS 500、SNS 500、Secrets Manager 500。17リージョンに分け、1つのリージョンに偏ったものを含める)、変更5,000件(4種類を含む)。ポリシーには、機能設計の「検出率100%のテスト用の参照」の参照と演算子を散らして入れます。AWS の呼び出しは HTTP の層の偽の AWS で置き換えます。`race` のビルドタグのときは、U2〜U4 と同じく件数を10分の1にし、時間の上限を10倍にします。

## 呼び出しの回数の式

記号: P = 利用者が作った管理ポリシーの数、p = そのうち付いているか権限の上限として使われているもの、U・R・G = ユーザー・ロール・グループの数、i(x) = ユーザー・ロール・グループ x のインラインポリシーの数、B = バケットの数、b = 変更案のリージョンにあるバケットの数、b' = 一覧の答えにリージョンが無いバケットの数、k(r)・q(r)・t(r)・s(r) = リージョン r のキー・キュー・トピック・シークレットの数、k'(r) = そのうち利用者が作ったキーの数。1ページの件数は、各 API が許す最大(NFR の設計で確かめる。IAM は1,000)とし、`Lp` で表します。

- IAM の管理ポリシーとインラインポリシー: max(1, ⌈(U + R + G + P) ÷ Lp⌉)(`GetAccountAuthorizationDetails` の1ページは、ユーザー・ロール・グループ・管理ポリシーを合わせて最大 Lp 件。p と i(x) は回数に入らない)
- S3: max(1, ⌈B ÷ Lp⌉) + b' + b
- リージョンごと(変更案のリージョンのすべて): max(1, ⌈k(r) ÷ Lp⌉) + k(r) + k'(r) + max(1, ⌈q(r) ÷ Lp⌉) + q(r) + max(1, ⌈t(r) ÷ Lp⌉) + t(r) + max(1, ⌈s(r) ÷ Lp⌉) + s(r)

再試行の分は数えません(U2 と同じ)。上の条件では合わせて約2,400回です(IAM は2回)。

**IAM の読み方を改めた(2026-10-28):** はじめは、管理ポリシーを `ListPolicies` と `GetPolicyVersion` で、インラインポリシーをユーザー・ロール・グループの一覧と `List*Policies`・`Get*Policy` で読む式(IAM だけで約2,500回、全体で約4,900回)でした。U5 のチェックポイントで、検証用アカウントの IAM の1回の時間(L95)が 600〜800 ms あり、同時の数を4から10に上げても1回の時間が延びて、NFR1.19 の見積もりが10分を超えました(791〜869 秒、10にして 626〜670 秒)。人の判断で、IAM のポリシーのすべてを `GetAccountAuthorizationDetails` でまとめて読むことにし、IAM の式を上のとおり改めました。

## 要件

| ID | 要件 | 合否の基準 |
|---|---|---|
| NFR1.16 | 影響分析の呼び出しの回数が、上の式の上限以下である。同じポリシーを2回読まない | 上の条件の偽の AWS で、影響分析の呼び出しの回数を操作ごとに数え、式の上限以下であることを確かめる。件数が0のリージョンと、ページが3つに分かれる一覧を含める |
| NFR1.17 | ツール自身の処理の時間(AWS の待ち時間を除いたもの)が短い | 上の条件の偽の AWS(遅れなし)で、影響分析が CI の各 OS で10秒以内に終わる |
| NFR1.18 | ポリシーを同時に読む数は、ツールが決めた固定の数で、利用者は変えられない。IAM は1つの読み取り(`GetAccountAuthorizationDetails`)のページを順に読み(同時に1つ。Q1 では同時に4つだったが、U5 のチェックポイントで IAM の読み方を改めた。2026-10-28)、リソースポリシーはリージョンを同時に8つまで(1つのリージョンの中は順に)読み、IAM とリソースポリシーは並行して読む(Q1)。数は、呼び出し回数の上限にも収まるようにする | オプションの一覧に同時に読む数を変えるものがない。偽の AWS で、同時に動いている IAM の呼び出しが1を超えず、同時に読んでいるリージョンが8を超えないことを数えるテストが通る |
| NFR1.19 | 検証用アカウントで、U5 で足した操作の1回の呼び出しの時間の95パーセンタイル(L95)を測り(U2 の NFR1.8 と同じく `--debug` の行から求める)、次の式で上の条件の影響分析の時間を見積もる。IAM の分 = IAM の呼び出しの回数(ページの数。順に読む)× L95(IAM)。リソースポリシーの分 = リージョンの回数の合計 ÷ 8 × L95(リソースポリシー)× 1.5(リージョンの偏りの安全率)。影響分析の時間 = 2つの大きい方。U2 の NFR1.8 の scan と plan の見積もりの IAM の分を、この影響分析の時間に置き換えたものが10分以内であることを、U5 のチェックポイントの記録に残す | 見積もりが10分以内で、測った値と式と結果が記録にある。10分を超えたときは、NFR1.18 の数を見直し、測り直してから人の承認を得る |
| NFR2.1 | 影響分析は、機能設計の「検出率100%のテスト用の参照」(ポリシーの種類7 × 参照7 × 変更4、演算子8)のすべてで、期待する判定(affected、undecided、影響なし)と一致する。affected か undecided が期待されるもので「影響なし」を返すもの(見逃し)は1つもない | テスト用の参照ごとに期待する判定を表にしたテストが、CI の各 OS で通る(検出率100%)。表の行の数と、組み合わせの数が一致することもテストで確かめる(表から組み合わせが抜けないように) |
| NFR2.2 | 検証用アカウントに置いたテスト用のポリシー(IAM のロールのインラインポリシー、利用者が作った管理ポリシー、少なくとも1つのリソースポリシー)と、それを参照するタグの変更で、plan が期待する指摘を出す | 検証用アカウントでの結合テスト(手元だけ。CI からは呼ばない)が通る。テスト用のリソースの置き方は、インフラの設計で決め、検証用アカウントへの変更は人の許可を得てから行う |
| NFR5.11 | 同時に読んでも、指摘と読めなかったものの順、標準出力、保存した変更案(`planId` と `createdAt` を除く)は、実行のたびに同じになる(機能設計 BR5.2) | ポリシーの種類とリージョンごとの応答の遅れを乱数で入れ替える偽の AWS で、乱数の種を変えて10回動かし、標準出力と保存した変更案が同じになる。CI の Linux のジョブでは `-race` 付きでも動かす |
| NFR10.9 | U5 のテストを足しても、カバレッジは `cmd` と `internal` のすべてで80%以上のまま。U5 で足す大きな偽の AWS のテスト(NFR1.16、NFR1.17、NFR5.11)は、CI の各 OS で合わせて2分以内に終わる | CI のカバレッジのジョブと、テストの時間で確かめる |

# セキュリティと信頼性の要件: U6 書き換えと記録

U6 は、本番のタグを書き換える最初の作業単位です。書き込みの権限を使う範囲、書き換えの記録と印の守り方、途中で止まっても記録が壊れないことを要件にします。ID は要件(`inception/requirements-analysis/requirements.md`)の NFR の番号に、枝番を付けたものです。

出典: 要件 NFR3〜NFR8、NFR11、機能設計(`construction/u6-apply/functional-design/` の `rules.md` BR3.1〜BR5.5、`functional-spec.md`)、契約 C4・C6・C10・C12、`nfr-requirements-questions.md` Q1〜Q5。

## U6 で使う AWS の操作

| 用途 | API(IAM の操作) | 機能設計 |
|---|---|---|
| タグを付ける | `TagResources`(`tag:TagResources` と、種類ごとのタグの操作。例: `ec2:CreateTags`、`s3:PutBucketTagging`) | BR4.1 |
| キーを消す | `UntagResources`(`tag:UntagResources` と、種類ごとのタグの操作。例: `ec2:DeleteTags`、`s3:PutBucketTagging`) | BR4.1 |
| 今のタグを読む、読み直す、読み戻す | `GetResources`(`tag:GetResources`。ARN を指定) | BR3.3、BR4.3、BR4.7 |
| 記録を S3 に置く | `PutObject`、`GetObject`、`DeleteObject`(`s3:PutObject`、`s3:GetObject`、`s3:DeleteObject`) | BR5.2 |
| S3 の印を作る | `PutObject` の条件付きの書き込み(同じ名前がなければ作る。`s3:PutObject`) | BR3.1 |
| アカウントを確かめる、変更案を作る | U1〜U5 の操作のまま(`--rules` のとき) | BR1.2、BR1.3 |

## 要件

| ID | 要件 | 合否の基準 |
|---|---|---|
| NFR3.10 | 書き込みの操作(`TagResources`、`UntagResources`、S3 への書き込みと削除)は `apply` と `rollback`(U7)だけが呼ぶ。`scan`、`rules suggest`、`plan` には書き込みの口(TagWriter、ObjectStore)を渡さない(NFR3 を守る) | 偽の AWS で `scan`、`rules suggest`、`plan` を動かし、記録された操作に書き込みがないことを確かめるテスト(U1 の NFR3.1 の確かめ)が通る。3つのコマンドに渡す AWS の口が TagWriter と ObjectStore を満たさないことを、型の確かめで調べる単体テストが通る |
| NFR3.11 | 書き換え用の IAM ポリシーの例 `docs/iam/apply-policy.json` を作る(Q1)。正本は、NFR の設計で作る「書き換えの対象の種類の表」(種類、付ける操作、消す操作、`Resource` の形)。表には少なくとも、検証用アカウントの確認用のスタックにある種類(S3 のバケット、SQS のキュー、SNS のトピック、Secrets Manager のシークレット、IAM のロール)を入れ、各操作を AWS の Service Authorization Reference で確かめる。例の中身は、読み取り用の例のすべて、`tag:TagResources`・`tag:UntagResources`(タグの API の操作はリソースの範囲を指定できないため `"*"`。NFR の設計で Service Authorization Reference と照らして確かめる)、表の操作(ARN の形に絞れるものは絞る)、記録を S3 に置く場合の `s3:GetObject`・`s3:PutObject`・`s3:DeleteObject`(例のバケットと前置きの下に絞る) | 例の操作の集まりが、「読み取り用の例 + `tag:TagResources`・`tag:UntagResources` + 表の操作 + S3 の3つ」の許可の一覧と完全に一致することを確かめるテストが通る(足りない操作も、余計な操作もない)。表の各種類のリソースを、U6 のチェックポイントで検証用アカウントの書き換え用のロールで1件ずつ書き換えて戻し、権限が足りることを確かめる |
| NFR3.12 | TagWriter は、`aws:` で始まるキー(大文字と小文字を区別しない。`AWS:`、`Aws:` も)を渡されたら、AWS を呼ばずに InvalidInput を返す(契約 C6 の念のための防御。機能設計 BR3.5 のもう一段の守り) | `aws:`、`AWS:`、`Aws:` のキーを含む呼び出しで AWS が呼ばれず、InvalidInput になる単体テストが通る |
| NFR4.1 | 記録には、U7 が書き換え前のタグに完全に戻すのに必要なもの(`touchedKeys`、書き換える直前に読んだ `beforeTags`(`aws:` を含む全体)、`plannedAfterTags`)を、書き換えより先に保存する(NFR4 の前提) | 偽の AWS で apply したあと、記録の `beforeTags` が書き換え前のタグと一致し、`touchedKeys` が付けた・消したキーと一致することを確かめるテストが通る。rollback で完全に戻ること(NFR4)は U7 で確かめる |
| NFR6.1 | 記録は、書き換えより先に、途中で壊れない方法で保存する。手元のファイルは同じフォルダーの一時ファイルに書き、ディスクへの書き出しを終えてから名前を変えて置き換える。S3 は1回の書き込みでオブジェクト全体を置き換える(機能設計 BR3.7、BR5.3) | 保存の途中(一時ファイルへの書き込みの途中、名前を変える前)で処理を止める差し替えのテストで、記録のファイルが前の版か新しい版のどちらかとして読めることが通る(AC4.2.6) |
| NFR6.2 | 書き換えの途中は、記録を5秒ごとと、止めたとき・終わったときに保存する(手元のファイルでも S3 でも同じ。Q4)。5秒ごとの保存は書き込みと並行して行い、書き込みを待たせない。前の保存が終わっていなければ、その回は飛ばして次の回にする(保存を重ねない)。5秒ごとの保存の失敗は次の回にやり直し、3回続けて失敗したら新しい書き込みを止める(機能設計 BR4.4。書く前の記録は保存済みなので、やり直しても取り消しの安全性は変わらない)。止めたとき・終わったときの保存の失敗は、その場で記録の保存の失敗として終える | 時計を差し替えたテストで、5秒ごとに保存されることと、止めたとき・終わったときに保存されることが通る。保存に時間のかかる差し替えで保存が重ならないこと、保存の失敗を2回返してから成功する差し替えで書き込みが続くこと、3回続けて失敗すると新しい書き込みが止まることが通る |
| NFR7.1 | 同じアカウントの apply と rollback の同時実行を、印で防ぐ。手元の印は「なければ作る」(作るときに、すでにあれば失敗する)方法で作り、S3 の印は条件付きの書き込みで作る。印を取ったあとは、どの終わり方でも印を消す(機能設計 BR3.1、BR3.8)。手元の印は同じ端末の中の同時実行だけを防ぐ。別の端末からの同時実行を防げるのは、記録を S3 に置く(`--record-to s3://...`)場合だけで、この限界を README に書く | 同じアカウントで2つの apply を同時に動かすテストで、後の方が Conflict で止まり、先の方の記録が壊れないことが通る(AC4.2.7)。偽の S3 が条件付きの書き込みに 412 か 409 を返すと Conflict になることが通る。確認の取り消し、途中の誤り、Ctrl+C、想定外のエラーのそれぞれで印が消えることが通る |
| NFR8.23 | 認証情報を、記録、ログファイル、印、表示、`--debug` の行に出さない。ログファイルには、ARN、リージョン、status、理由、誤りの種類、操作の名前だけを書き、AWS のエラー文とタグの値は書かない(機能設計 BR5.5。タグの値が入るのは記録だけ) | 偽の認証情報と、エラー文に秘密に見える文字列を含む偽の答えを使って apply を動かし、記録・ログファイル・印・標準出力・標準エラーにそれらが含まれないこと、ログファイルにタグの値が含まれないことを確かめるテストが通る |
| NFR8.24 | 記録(ARN とタグの値が入る)と、ログファイル、印、一時ファイルを置く手元のフォルダーは、その利用者だけが読み書きできる権限にする(Q5)。Linux と macOS は、ツールが作るフォルダー(既定の `<ホーム>/.tag-refactor/runs/<accountId>/`、`--record-to` に手元のフォルダーを指定したときの `<そのフォルダー>/<accountId>/`)を 0700、ファイルを 0600 で作る。そのフォルダーがすでにあり、ほかの利用者が読める権限なら警告を出す(権限は変えない)。Windows は、作ったフォルダーがその場所の権限を引き継ぐ(Go からは 0700 を指定できない)。プロファイルの外を `--record-to` に指定するとほかの利用者が読める場合があることを、限界として README に書く | Linux と macOS の CI で、作ったフォルダーとファイルの権限と、ほかの利用者が読めるフォルダーで警告が出ることを確かめるテストが通る。Windows では作れることだけを確かめる |
| NFR8.25 | S3 に置く記録と印には、公開の ACL を付けない。暗号化はバケットの既定の設定に任せ、ツールからは指定しない。S3 のオブジェクトの名前は、`--record-to` の前置きと `<accountId>/` の下だけを使う(Q5、機能設計 BR5.2) | 偽の S3 に届いた要求に ACL の指定がなく、オブジェクトの名前が前置きと `<accountId>/` の下にあることを確かめるテストが通る |
| NFR11.8 | apply の確認画面と結果は、色がなくても意味が分かる。影響のある変更は `!`(影響あり)と `?`(判定できない)の記号と文字で、飛ばしと失敗は理由の文字で示す(機能設計 BR2.1、BR6.1) | `NO_COLOR` と、リダイレクトしたときの確認画面と結果の期待の出力のファイルを、英語と日本語で比べるテストが通る |

## 脅威と対策

| 脅威 | 対策 |
|---|---|
| 意図しない書き換え(間違った変更案、別のアカウント、影響のある変更) | 確認(`yes` だけ)、アカウントの一致の確認、`--yes` だけでは影響のある変更で止まる(機能設計 BR1.2、BR2.2〜BR2.6) |
| 他人が変えたタグを上書きする | 書き換える直前と、書き込みのまとまりごとに今のタグを読み、変わっていれば飛ばす(機能設計 BR3.3、BR4.7) |
| AWS が管理するタグを壊す | `aws:` のキーを書かない(機能設計 BR3.5)。TagWriter でも拒む(NFR3.12) |
| 書き換えの途中で止まり、元に戻せなくなる | 書く前に全件を記録し(NFR4.1、NFR6.1)、途中も5秒ごとに保存する(NFR6.2)。U7 が今のタグと記録で判定する |
| 同時の apply で記録が壊れる | 印で防ぐ(NFR7.1) |
| 記録やログから情報が漏れる | 認証情報とエラー文を書かない(NFR8.23)。手元は利用者だけの権限(NFR8.24)。S3 は公開しない(NFR8.25) |
| 強すぎる書き込みの権限 | 例のポリシーは操作をタグと記録に絞り、ARN の形に絞れるものは絞る(NFR3.11) |

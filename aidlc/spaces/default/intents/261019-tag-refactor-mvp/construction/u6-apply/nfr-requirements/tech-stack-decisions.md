# 技術の選択と、性能・移植性・保守性の要件: U6 書き換えと記録

U1〜U5 の技術の選択(Go、AWS SDK for Go v2、cobra、`golang.org/x/sync`、`golang.org/x/term`)はそのまま使います。U6 で新しく足すライブラリはありません。ここでは、U6 で使う部品の選び方と、書き込みの速さ、3つの OS で動くこと、テストの要件を決めます(U6 は `library` の作業単位で、性能の要件のファイルを別に作らないため、ここに置きます)。

出典: 要件 NFR1、NFR5、NFR9、NFR10、機能設計(`construction/u6-apply/functional-design/`)、契約 C6・C10・C12、`nfr-requirements-questions.md` Q2〜Q4。

## 技術の選択

| 用途 | 選ぶもの | 理由 |
|---|---|---|
| タグの書き込みと読み取り | AWS SDK for Go v2 の `resourcegroupstaggingapi`(`TagResources`、`UntagResources`、`GetResources`。U2 から使っているモジュール) | 1つの API で多くの種類のリソースのタグを扱え、1回の呼び出しで最大20個のリソースを書ける。`GetResources` は ARN を最大100個まで指定して読める。U2 の読み取りと同じ接続と再試行の仕組みを使える |
| S3 の記録と印 | AWS SDK for Go v2 の `s3`(U5 から使っている v1.114.3。`PutObjectInput.IfNoneMatch` を持つことを確かめた)。印は `IfNoneMatch: "*"` | S3 の条件付きの書き込みで、別の端末からの同時実行も防げる(S3 に記録するときだけ。セキュリティの要件 NFR7.1)。新しいモジュールは要らない。`go.mod` の `s3` をこれより古い版に下げない |
| 手元の印 | Go の標準の `os.OpenFile` の「作るときにすでにあれば失敗する」指定 | 3つの OS で同じに動き、ほかのプロセスとの競争でも1つだけが作れる |
| 壊れない保存 | Go の標準の一時ファイル(同じフォルダー)、ファイルのディスクへの書き出し、`os.Rename` での置き換え | Windows でも既存のファイルを置き換えられる(置き換え先が開かれているときの扱いは NFR9.9)。U4 の変更案の保存(`internal/fileout`)と同じ作り |
| 端末かどうか、確認の入力 | `golang.org/x/term`(U4 から使っている) | 端末でないときに止める(機能設計 BR2.3) |
| Ctrl+C | Go の標準の `os/signal` と `context` | 1回目で新しい書き込みを止め、2回目で待たずに終える(機能設計 BR4.5) |
| ホームのフォルダー、ホスト名、プロセスID | Go の標準(`os.UserHomeDir`、`os.Hostname`、`os.Getpid`) | 印の中身(機能設計 LockInfo) |

## 書き込みの進め方(要件の前提)

- **書き込みのまとまり:** 同じリージョンで、付けるタグの組み合わせと消すキーの組み合わせがまったく同じリソースを、20個までまとめたもの。1つのまとまりに、付ける呼び出し1回と、消す呼び出し1回(それぞれ、あれば)を使う。
- **読み直しの単位:** 同じリージョンの続くまとまりを、リソースの合計が100を超えない範囲で束ねたもの。単位ごとに、書く直前に `GetResources` を1回呼んで読み直し(機能設計 BR4.7)、書いたあとに `GetResources` を1回呼んで読み戻す(機能設計 BR4.3)。まとまりは20以下なので、最後の単位を除き、1つの単位には81以上のリソースが入る。
- **同時の数:** リージョンは同時に4つまで。1つのリージョンの中の読み直しの単位とまとまりは順に処理する。数は固定で、利用者は変えられない(Q2)。

## 要件

| ID | 要件 | 合否の基準 |
|---|---|---|
| NFR5.12 | 書き込みの呼び出しも、U2 の AwsAccess の時間の上限、待ち時間を延ばしながらの再試行、呼び出し回数の上限に当たったときの待ちを通す。呼び出し側は再試行しない(契約 C6)。`TagResources`・`UntagResources` の答えのリソースごとの失敗の一覧のうち、再試行できる誤り(内部エラー、回数の上限)のリソースだけを、同じ再試行の回数の上限の中で書き直す。そのほかの誤りは契約 C12 の種類(AccessDenied、InvalidInput など)に変えて、そのリソースの失敗にする | 偽の AWS が書き込みに回数の上限の答えを返すと待ってから再試行され、上限の回数を超えると Transient になる単体テストが通る。リソースごとの失敗の一覧に内部エラーと権限不足を混ぜた答えで、内部エラーのリソースだけが書き直され、権限不足のリソースが AccessDenied の失敗になる単体テストが通る |
| NFR5.13 | 書き込みは、上の「書き込みの進め方」のとおりに、まとまり(20以下)、読み直しの単位(100以下)、リージョン4つまでの同時、リージョンの中は順で行う(Q2) | 偽の AWS で、1回の書き込みのリソースが20を超えないこと、組み合わせの違うリソースが同じ呼び出しに入らないこと、1回の `GetResources` の ARN が100を超えないこと、同時に動くリージョンが4を超えないこと、1つのリージョンの中で呼び出しが重ならないことを数えるテストが通る |
| NFR5.14 | apply の呼び出しの回数は、次の式の上限以下である。記号: N(r) = リージョン r の変更のあるリソースの数、R(r) = リージョン r の読み直しの単位の数(R(r) ≤ ⌈N(r) ÷ 81⌉)、a(g)・d(g) = まとまり g に付けるタグ・消すキーがあれば1、なければ0。リージョン r の回数 = ⌈N(r) ÷ 100⌉(最初の読み取り。機能設計 BR3.3)+ 2 × R(r)(読み直しと読み戻し)+ Σg (a(g) + d(g))(書き込み)。合計は全リージョンの和。再試行の分は数えない | 偽の AWS に置いた件数とまとまりから式で上限を計算し、操作ごとの回数が上限以下であることを確かめるテストが通る(数を手で書かない) |
| NFR5.15 | 測る条件の「よくある変更」(下の表)で、1アカウント・全リージョン・1万リソースの apply の見積もりが30分以内。「値がばらばらなキー名の変更」(下の表。まとまりがほぼ1リソースになる、最悪に近い場合)の見積もりも記録するが、合否には使わない(Q3)。見積もりは、リージョンの中は順に処理されるため、最も時間のかかるリージョンで決まる: T = max_r(⌈N(r) ÷ 100⌉ × L95(GetResources) + 2 × R(r) × L95(GetResources) + W_t(r) × L95(TagResources) + W_u(r) × L95(UntagResources))× 1.2 + 待ちの時間 + 最後の記録の保存の時間。W_t(r)・W_u(r) はリージョン r の付ける・消す呼び出しの数。1.2 は、検証用アカウントの小さなページで測った L95 と、1万件の大きな呼び出しの時間の違いの余裕(U5 の IAM の見積もりと同じ)。待ちの時間 = 測定で回数の上限に当たって再試行した回数を1万件の回数に比例させたもの × AwsAccess の最大の待ち時間。5秒ごとの保存は書き込みと並行して行う(セキュリティの要件 NFR6.2)ので、見積もりに入れない | 検証用アカウントで apply を `--debug` 付きで動かし、操作ごとの1回の時間の L95 を測る(U2 の NFR1.8、U5 の NFR1.19 と同じ求め方)。上の式で、2つの分布の見積もりを U6 のチェックポイントの記録に残し、「よくある変更」が30分以内であることを確かめる。30分を超えたら、NFR5.13 の数を見直して測り直し、人の承認を得る |
| NFR5.16 | 偽の AWS(遅れなし)で、測る条件の「よくある変更」と「値がばらばらなキー名の変更」の1万リソースの apply を動かしたとき、ツール自身の処理の時間(まとまりの計算、記録の保存を含む)が、それぞれ CI の各 OS で30秒以内 | 大きな偽の AWS のテストが30秒以内に終わる。`race` のビルドタグのときは、U2〜U5 と同じく件数を10分の1にし、時間の上限を10倍にする |
| NFR5.17 | 書き込みの途中で認証情報の誤り(期限切れのトークンを含む。契約 C12)を受けたとき、新しい書き込みを止める。また、書き込みの呼び出し(`TagResources`・`UntagResources` の1回)が、再試行を使い切っても Transient で終わることが、全リージョンを通して10回続いたとき、新しい書き込みを止める。「続いた」は、どのリージョンでも書き込みの呼び出しが1回成功すれば0に戻す。リソースごとの失敗の一覧の誤りは数えない(機能設計 BR4.2 の「10件」は、この書き込みの呼び出しの数) | 偽の AWS が途中から認証情報の誤りを返すテストで、それ以降の書き込みが呼ばれないことが通る。Transient で終わる呼び出しを9回続けたあと1回成功させると止まらず、10回続けると止まり、記録が保存されて終了コード1になるテストが通る。1回の呼び出しの20個のリソースの失敗だけでは止まらないことも確かめる |
| NFR9.8 | 手元の印、壊れない保存、ホームのフォルダー、Ctrl+C、確認の入力は、Linux、macOS、Windows で同じに動く | 3つの OS の CI で、印の競争、保存の途中で止めたときの読み戻し、ホームの下の記録の場所、端末でないときの停止のテストが通る |
| NFR9.9 | Windows で、名前を変えて置き換える先のファイルを別のプロセス(読み取り中の rollback、ウイルス対策のソフトなど)が開いていて失敗したときは、100ミリ秒おいて最大5回やり直す。それでも失敗したら保存の失敗として扱う。Windows ではフォルダーのディスクへの書き出しができないため、電源断のときに名前の変更が残らないことがある(限界として受け入れる。前の版か新しい版のどちらかは残る) | 名前の変更の失敗を4回返してから成功する差し替えのテストで保存が成功し、5回失敗し続けると保存の失敗になるテストが通る(3つの OS で動く) |
| NFR10.10 | U6 のテストを足しても、カバレッジは `cmd` と `internal` のすべてで80%以上のまま。U6 のテストは偽の AWS で動き、AWS の認証情報なしで CI で実行できる。実際のアカウントを使う確かめは手元だけ(U6 のチェックポイント) | CI のカバレッジのジョブで80%以上。U6 の大きな偽の AWS のテスト(NFR5.13、NFR5.14、NFR5.16)は、CI の各 OS で合わせて2分以内に終わる |

## 測る条件(NFR5.14〜NFR5.16)

| 項目 | 値 |
|---|---|
| リソース | 1万。17リージョンのうち1つ(偏ったリージョン)に2,000、残りの16リージョンに500ずつ |
| よくある変更 | 全リソースで `env` → `Environment`(元の値は `dev`、`stg`、`Prod` の3つ)と、値 `Prod` → `prod` の変更、全リソースで必須タグ `CostCenter` の追加(値は5つ)。付けるタグの組み合わせは3 × 5 = 15で、まとまりの多くが20個になる |
| 値がばらばらなキー名の変更 | 全リソースで `Owner` → `owner`(値はリソースごとに違う)。まとまりはほぼ1リソースになる(最悪に近い場合) |
| 見積もりの例(1回0.3秒とする) | よくある変更の偏ったリージョン(2,000件): 最初の読み取り20回、読み直しと読み戻し約50回、書き込み約210回(まとまり約105 × 付ける・消す)で、約1.4分(1.2倍で約1.7分)。値がばらばらな場合の偏ったリージョン: 最初の読み取り20回、読み直しと読み戻し約50回、書き込み約4,000回で、約20分(1.2倍で約24分) |

値がばらばらなキー名の変更では、1リソースごとに付ける呼び出しと消す呼び出しが要るため、偏ったリージョンの件数が多いほど時間が延びます。この場合は合否に使わない(Q3)ことを受け入れ、README に「値がリソースごとに違うキーの名前を変えると、書き込みの呼び出しがリソースの数の2倍になる」ことを書きます。

## 当てはまらない要件

| 要件 | 理由 |
|---|---|
| NFR1(scan と plan の10分) | U6 は scan と plan の速さを変えない。`apply --rules` は、その場で plan と同じ手順を動かすので、その部分は NFR1 のまま。apply の書き込みの時間は NFR5.15 で決める |
| NFR2(影響分析の検出率) | U6 は影響分析を変えない。変更案の `impacted` をそのまま使う |
| NFR12(配布) | 配布の仕組みは作業単位に含めず、別の作業で行う |

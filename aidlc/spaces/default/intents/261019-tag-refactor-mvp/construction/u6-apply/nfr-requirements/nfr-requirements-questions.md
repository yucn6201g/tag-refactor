# NFR の要件 — 質問(U6 書き換えと記録)

U6 は、本番のタグを書き換える最初の作業単位です。書き込みの権限、書き込みの速さと呼び出し回数の上限、記録の保存の頻度と守り方を決めます。

決まっていること(質問しません):

- 時間の上限、待ち時間を延ばしながらの再試行、呼び出し回数の上限に当たったときの待ちは、U2 の AwsAccess のまま(NFR5)。書き込みの呼び出しも同じ仕組みを通す。
- 認証情報は表示にも記録にもログにも出さない(NFR8)。`--debug` の行は操作の名前、リージョン、時間、再試行の回数だけ(U1)。タグの値は秘密情報ではないとみなし、記録とログファイルに書く(要件 AS2)。ログファイルにはエラー文を書かない(機能設計 BR5.5)。
- 記録は途中で壊れない方法で保存し(NFR6)、同じアカウントの同時実行は印で防ぐ(NFR7、機能設計 BR3.1、BR3.8)。
- 3つの OS で動く(NFR9)。カバレッジは80%以上(NFR10)。色がなくても意味が分かる(NFR11)。
- 書き込みの API は、Resource Groups Tagging API の `TagResources` と `UntagResources`(1回の呼び出しで最大20個のリソース、同じタグの組み合わせだけ)。リソースごとの成否は答えの中の失敗の一覧で分かる。

## Q1. 書き換えに必要な権限と、権限の例

`TagResources` と `UntagResources` は、`tag:TagResources` などの権限に加えて、リソースの種類ごとのタグの操作(例: `ec2:CreateTags`、`s3:PutBucketTagging`)の権限も要ります。apply に必要な権限をどう示しますか?

A. 書き換え用の IAM ポリシーの例(`docs/iam/apply-policy.json`)を作る。中身は、読み取り用の例のすべてと、`tag:TagResources`・`tag:UntagResources`、ツールが書き換えられる種類ごとのタグの操作(リソースの ARN の形に絞れるものは絞る)、S3 に記録する場合の `s3:GetObject`・`s3:PutObject`・`s3:DeleteObject`(記録の前置きの下に絞る)。例と、コードの操作の表が一致することをテストで確かめる
B. README に必要な操作の一覧だけを書き、ポリシーの例は作らない
C. A と同じ例を作るが、種類ごとのタグの操作は `*`(例: `ec2:CreateTags` を全リソースに)にして短くする

## Q2. 書き込みのまとめ方と同時の数

1万件を書き換えるとき、呼び出しの数を減らし、呼び出し回数の上限に当たりにくくするには、書き込みをどうまとめますか?

A. 同じリージョンで、付けるタグの組み合わせ(と消すキーの組み合わせ)がまったく同じリソースを、1回の呼び出しで最大20個にまとめる。リージョンは同時に4つまで、1つのリージョンの中は順に書く。書く直前の読み直し(機能設計 BR4.7)も、このまとまりごとに行う
B. 1つのリソースを1回の呼び出しで書く。リージョンは同時に4つまで、1つのリージョンの中は順に書く
C. 1つのリソースを1回の呼び出しで、すべて順に書く(最も遅いが、呼び出し回数の上限に最も当たりにくい)
X. Other (please specify)

[Answer]: A

## Q3. 書き換えの時間の目標

1アカウント・全リージョン・1万リソースの書き換え(apply)の時間に、目標を置きますか?(検証用アカウントで `--debug` の行から1回の呼び出しの時間を測り、見積もります。U5 と同じ確かめ方)

C. 時間の目標は置かず、進み具合の表示(残りの件数)だけを確かめる

## Q4. 記録を保存する頻度

書き換える前に全件を pending で保存してあるため(機能設計 BR3.7)、書き換えの結果は途中で保存しなくても取り消せます。ただし、保存の間が長いと、止まったときに「結果が分からない」項目が増え、U7 が今のタグで判定する件数が増えます。1万件の記録は約10 MB になります。どの頻度で保存しますか?

A. 5秒ごとと、止めたとき・終わったとき。手元のファイルでも S3 でも同じ
B. 書き込みのまとまりごと(手元のファイル)。S3 は30秒ごと
C. 終わったときと止めたときだけ
X. Other (please specify)

[Answer]: A

## Q5. 記録とログファイルの守り方

記録とログファイルには、ARN とタグの値が入ります(タグの値は秘密情報ではないとみなす。要件 AS2)。どう守りますか?

A. 手元では、フォルダーをその利用者だけが読み書きできる権限(Linux と macOS は 0700、ファイルは 0600。Windows は利用者のプロファイルの既定の権限)にする。S3 では、公開の ACL を付けず、サーバー側の暗号化はバケットの既定の設定に任せる(ツールからは指定しない)
B. A に加えて、S3 に置くときの KMS のキーを指定するオプション(例: `--record-kms-key`)を持つ
C. 特に守らない(既定の権限のまま)

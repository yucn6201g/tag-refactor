# 論理的な部品: U6 書き換えと記録

U6 の部品の置き場所、書き換えの流れの中での同時の動き、まとまりの作り方、テストの設計を決めます。セキュリティと信頼性の作りは `security-design.md` にあります。

出典: NFR の要件(`construction/u6-apply/nfr-requirements/`)、機能設計(`construction/u6-apply/functional-design/`)、契約 C4・C6・C10・C11・C12、`nfr-design-questions.md` Q2。

## パッケージごとの変更(Q2 A)

| パッケージ | U6 で足すもの、変えるもの | 契約 |
|---|---|---|
| `internal/journal`(新規) | 記録(RunRecord、JournalEntry)の読み書き、壊れない保存、5秒ごとの保存の役、印(手元と S3)、runId、ログファイル。U7 も使う | C4、C10 |
| `internal/apply`(新規) | 書き換えの流れ(機能設計 W1 の手順 7〜13)、ApplyTarget の計算(期待するタグ、付けるタグ、消すキー、50の上限)、変化の確かめ、まとまりと読み直しの単位の作り方、リージョンの役、止める条件、結果(ApplyResult) | C10、C11、C12 |
| `internal/awsaccess` | TagWriter と ObjectStore の実装、操作の表に書き込みの操作と種類ごとのタグの操作を足す、ARN を指定した `GetResources` | C6 |
| `internal/cli` | `apply` のサブコマンド(オプション、入力の確かめ、変更案の用意、端末の確かめ、確認の入力、Ctrl+C、終了コード)。`--rules` のときは plan と同じ部品で変更案を作る | C5 |
| `internal/display` | 確認画面、結果の一覧、案内の文言(英語と日本語)。U4 の言語と色の部品を使う | C5 |
| `docs/iam/apply-policy.json`、`README.md` | 書き換え用の権限の例、apply の節(使い方、記録の場所、印、限界) | — |

依存の向き: `cli` → `apply` → `journal`、`awsaccess`(口だけ)、`planner`(変更案の型と U4 の規則 1.9 の部品)。`journal` は `awsaccess` の ObjectStore の口だけを使う。`apply` と `journal` は `display` に依存しない(進み具合は C11 の ProgressSink で知らせる)。循環はない。

## 書き換えの流れの中の同時の動き(NFR5.13)

| 役 | 数 | すること |
|---|---|---|
| 指揮役(Applier) | 1 | 印、確認のあとの手順を順に進める。最初の読み取り(機能設計 BR3.3)をリージョンごとに行い、まとまりを作り、記録を始めてから、リージョンの役を配る |
| リージョンの役 | 同時に4つまで(`errgroup` の上限) | 自分のリージョンの読み直しの単位を順に処理する: 読み直し → まとまりごとに書き込み → 読み戻し → 結果を Journal に渡す |
| 保存の役(Journal) | 1 | 5秒ごとに記録を保存する(`security-design.md` §3) |
| 合図の役 | 1 | 1回目の Ctrl+C で「止める合図」を立て、2回目で実行の `context` を取り消す(`security-design.md` §5 の2段の止め方) |

- どの役も入口で `recover` を置き、パニックを Internal の誤りに変えて指揮役に返す(`security-design.md` §3)。

- 最初の読み取りは、リージョンごとに `GetResources`(ARN 100個ずつ)を、同じくリージョン4つまで同時に行う。
- 数(4、20、100)は `internal/apply` の変数で、テストからだけ差し替えられる。

## まとまりと読み直しの単位の作り方(NFR5.13、NFR5.14)

1. 書き換えるリソースを、リージョンごとに分ける。
2. リソースごとに「まとまりの鍵」を作る。鍵は、付けるタグ(キーの順に並べた [キー, 値] の組の列)、消すキー(順に並べた列)、消すのを先にするか(機能設計 BR3.6)の3つを持つ構造を、JSON に符号化した文字列にする(`encoding/json` の出力。キーと値に `=`、`,`、改行、空白、引用符があっても、違う組み合わせが同じ文字列にならない)。`=` や区切りの文字を含むキーと値の組み合わせで、鍵が一致しないことを単体テストで確かめる。
3. 同じ鍵のリソースを ARN の順に並べ、20個ずつに分けてまとまりにする。まとまりの並びは、鍵の文字列の順、同じ鍵の中は ARN の順(毎回同じ並び)。
4. まとまりを並びの順に、リソースの合計が100を超えない範囲で束ねて、読み直しの単位にする。
5. 読み直しで変わっていたリソース(機能設計 BR4.7)は、そのまとまりから外して書く。まとまりが空になれば、その書き込みは呼ばない。

呼び出しの回数の式と見積もりは、NFR の要件 NFR5.14・NFR5.15 のとおり。

## 30分の見積もりの測り方(NFR5.15)

- U6 のチェックポイントの検証コマンドで、確認用のスタックのリソースに対して `apply --yes --debug` と、その取り消し(U7 ができるまでは、検証のスクリプトが変更前の変更案を逆に当てる apply)を5回くり返し、`--debug` の行から `tag:GetResources`、`tag:TagResources`、`tag:UntagResources` の操作ごとの L95 と、再試行が起きた呼び出しの数を求める(U5 の `verify.sh` の測り方と同じ)。
- 測る条件の2つの分布(NFR の要件の表)について、偏ったリージョンの回数を NFR5.14 の式で計算し、NFR5.15 の式で見積もる。計算は検証のスクリプトが行い、結果(2つの見積もり、L95、再試行の数)をチェックポイントの記録に残す。スクリプトの形と確認用のスタックは、インフラの設計で決める。

## 障害の範囲と隔て方

| 障害 | 範囲 | 隔て方 |
|---|---|---|
| 1つのリソースの書き込みの失敗 | そのリソース | 失敗として記録し、次に進む(機能設計 BR4.2) |
| 1回の書き込みの呼び出しの失敗 | そのまとまり(最大20) | まとまりのリソースを失敗か結果が分からないものにし、次のまとまりに進む |
| 1つのリージョンの障害が続く | そのリージョン | ほかのリージョンの書き込みが成功している間は止めない。障害のリージョンのリソースは、呼び出しごとに再試行を使い切ってから、失敗か結果が分からないものになる。すべてのリージョンで一時的な失敗が10回続けば全体を止める(`security-design.md` §5) |
| 認証情報の期限切れ | 全体 | すぐ止める |
| 記録の保存の失敗 | 全体 | 5秒ごとの保存は3回まで、止めるとき・終わるときはすぐ止める |
| プロセスの強制終了 | 全体 | 書く前の記録(pending)で U7 が取り消せる。印が残り、`--force-unlock` で外す |

## テストの設計(NFR5.13〜NFR5.17、NFR6.1、NFR6.2、NFR7.1、NFR9.8、NFR9.9、NFR10.10)

| テスト | 作り | 確かめること |
|---|---|---|
| 受け入れ条件(AC4.1.1〜AC4.2.7、AC6.1.1) | HTTP の層の偽の AWS(`internal/testutil` に `TagResources`、`UntagResources`、ARN を指定した `GetResources`、S3 の `PutObject`・`GetObject`・`DeleteObject` と条件付きの書き込みを足す)で `apply` を動かす | 機能設計の業務の場面のとおり |
| まとまりと同時の数 | 大きな偽の AWS(測る条件の2つの分布)。偽の AWS が同時に受けている要求の数を数える(U5 と同じ仕組み) | NFR5.13 の上限、NFR5.14 の式、NFR5.16 の30秒 |
| 失敗の分け方 | 偽の AWS の答えに、リソースごとの失敗の一覧(状態 403・404・400・429・500 と、サービス固有のコード、状態のない項目)と、呼び出し全体の誤りを入れる | NFR5.12 の分け方と書き直し、読み戻しで決めること、NFR5.17 の止める条件(9回で止まらない、10回で止まる、成功で0に戻る) |
| まとまりの鍵 | `=`、`,`、改行、引用符を含むキーと値 | 違う組み合わせの鍵が一致しない |
| 壊れない保存 | `internal/journal` のファイルの操作(一時ファイル、書き出し、名前の変更)を差し替えられるようにし、途中で失敗させる。Windows の名前の変更の失敗を4回・5回返す | NFR6.1、NFR9.9(合計5回の試行) |
| 5秒ごとの保存 | 時計を差し替える。保存に時間がかかる差し替え、失敗を返す差し替え、変更のない回 | NFR6.2、3回続けて失敗したら `RecordAfter` が StorageFailed を返す、最後の保存のあとの `RecordAfter` を拒む |
| 印と止め方 | 2つの Applier を同じ一時のホームで同時に動かす。偽の S3 が 412・409・501 を返す。印のあとに誤り、1回目と2回目の Ctrl+C、指揮役と各 goroutine のパニックを起こす。`--force-unlock` で取り直された印 | NFR7.1、機能設計 BR3.8、BR4.5(取り消しのあとも最後の保存と印を消すことが成功する、他人の印を消さない) |
| 一度もタグのないリソース | 偽の AWS の `GetResources` が、タグのないリソースを答えに出さない | 空のタグとして書き換え、消えていれば 404 で `resourceNotFound` になる |
| 権限 | Linux と macOS で、作ったフォルダーとファイルの権限、ほかの利用者が読めるフォルダーの警告 | NFR8.24 |
| 出さないもの | 偽の認証情報と、秘密に見える文字列を含む AWS のエラー文の答え | NFR8.23 |
| 権限の例 | 例の JSON と、コードの操作の表と種類の表から作った許可の一覧の一致 | NFR3.11 |
| 表示 | 確認画面と結果の期待の出力のファイル(英語と日本語、`NO_COLOR`) | NFR11.8 |

- すべて AWS の認証情報なしで動く。実際のアカウントでの確かめ(種類ごとの書き換えと戻し、L95 の測定)は、U6 のチェックポイントの検証コマンドの中で、手元だけで行う(インフラの設計で決める)。
- `race` のビルドタグのときは、大きなテストの件数を10分の1にし、時間の上限を10倍にする(U2〜U5 と同じ)。

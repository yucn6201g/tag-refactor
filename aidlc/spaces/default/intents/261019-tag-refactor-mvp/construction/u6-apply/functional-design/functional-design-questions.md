# 機能設計の質問: U6 書き換えと記録(u6-apply)

U6 では `apply` と、書き換えの記録(Journal)を作ります。本番のタグを書き換える最初の作業単位です。

## すでに決まっていること(質問しません)

- **ストーリー:** US4.1(確認してから書き換える。AC4.1.1〜AC4.1.7)、US4.2(途中の問題で被害を広げない。AC4.2.1〜AC4.2.7)。要件 FR5.1〜FR5.11、NFR6、NFR7。
- **記録の形(契約 C4):** `runId`(UTC の秒までと乱数の接尾辞)、`touchedKeys`・`beforeTags`・`plannedAfterTags` を書き換えより先に保存し、項目ごとに `pending`・`applied`・`skipped`・`failed` を持ちます。rollback(U7)はこの記録を読みます。
- **記録の口(契約 C10):** `Lock` → `Begin` → `RecordBefore` → 書き換え → `RecordAfter` → `Complete` → `Release`。`RecordBefore` に失敗したら何も書き換えません。保存は途中で壊れない方法で行います(NFR6)。
- **キー名の変更:** 新しいキーを付けてから、古いキーを消します(契約 C4)。
- **`aws:` のタグ:** 書き換えも削除もせず、変化の確認とタグ数の上限の数え方から除きます(全体の決まり)。
- **終了コード(契約 C5):** 0 は問題なし(確認でやめた場合も 0)。1 はエラー、一部の失敗、アカウントの不一致、記録の保存の失敗。2 は飛ばしあり、確認を省いたときに影響のある変更で止まった場合です。
- **影響の扱い(契約 C5):** 影響には affected と undecided の両方を含めます。`--yes` だけのときに影響のある変更があれば止め、`--yes` と `--allow-impact` の両方で進めます。`--yes` なしの `--allow-impact` は何も変えず、案内を出します。
- **アカウントの確認:** 保存した変更案のアカウントと今のアカウントが違えば、何も書き換えずに止めます(契約 C2)。
- **書き込みの口:** U1 で定めた `TagWriter`(`TagResources`、`UntagResources`)を、U6 で実装します。

## Q1. apply のオプション名

モックアップの案は、`--plan <ファイル>`(保存した変更案)、`--rules <ファイル>`(その場で変更案を作る)、`--yes`(確認を省く)、`--allow-impact`(影響を承知で進める)、`--record-to <場所>`(記録の保存先)です。名前はどうしますか?

A. 案のとおりにする。`--plan` と `--rules` はどちらか1つだけを指定する(両方も、どちらもなしも使い方の誤り)
B. 案のとおりにするが、`--rules` は持たず、`apply` は必ず保存した変更案(`--plan`)から実行する
C. 名前を変える(例: `--yes` を `--auto-approve` にするなど。具体的に書いてください)
X. Other (please specify)

[Answer]: A

## Q2. 変更案の作成後の変化の確かめ方(FR5.6)

書き換える直前に、それぞれのリソースの今のタグを読み、変更案を作った時点のタグ(`beforeTags`)と比べます。どの範囲が違ったら、そのリソースを飛ばしますか?(どちらも `aws:` のキーは除きます)

A. タグ全体(`aws:` を除く)のどれかが違えば飛ばす。必須タグの追加やタグ数の上限は、タグ全体をもとに計算しているため
B. 変更案が書き換えるキー(`touchedKeys`)と、その書き換え先のキーだけを比べ、ほかのキーの変化は気にしない
C. A の範囲で比べるが、変わったのが書き換えに関係しないキーだけなら、飛ばさずに警告を出して書き換える
X. Other (please specify)

[Answer]: A

## Q3. 不完全な変更案と古い変更案

保存した変更案に、収集が不完全(`inventoryComplete: false`)または影響分析が不完全(`impactAnalysisComplete: false`)の印があるとき、また作成から時間がたっているときは、どうしますか?

A. どちらの不完全も、確認画面で目立たせて書き換えは許す。影響分析が不完全なら「影響あり」として扱う(`--yes` だけでは止まる)。作成からの時間では止めない(Q2 の確かめで守る)
B. A に加えて、作成から24時間を超えた変更案は確認画面で警告する
C. 不完全な変更案では書き換えない(作り直しを案内する)
X. Other (please specify)

[Answer]: A

## Q4. 記録の既定の保存先と、同時実行を防ぐ印(手元のファイル)

既定では、記録を手元のファイルに置きます(実行ごとに1ファイル)。どこに置きますか?(契約 C4・C10 の未決事項)

A. 利用者のホームの下(`~/.tag-refactor/runs/<アカウントID>/<runId>.json`)。同時実行を防ぐ印は `~/.tag-refactor/runs/<アカウントID>/.lock`。どのフォルダーから実行しても同じ記録を見つけられる
B. 実行したフォルダーの下(`./.tag-refactor/runs/...`)。印も同じフォルダー
C. OS ごとの決まった場所(Windows は `%LOCALAPPDATA%`、macOS は `~/Library/Application Support`、Linux は `$XDG_STATE_HOME`)
X. Other (please specify)

[Answer]: A

## Q5. 記録を S3 に置く場合の同時実行の防ぎ方

`--record-to s3://<バケット>/<前置き>` を指定したとき、同じアカウントで2つの apply が同時に動くことをどう防ぎますか?(契約 C10 の未決事項)

A. S3 の条件付きの書き込み(同じ名前のオブジェクトがなければ作る)で、`<前置き>/<アカウントID>/.lock` を印にする。手元の印も取る
B. S3 では防がず、手元の印だけを取る(別の端末からの同時実行は防げないことを README に書く)
C. S3 への保存は U6 では作らず、手元のファイルだけにする(FR5.8 の S3 は後の作業にする)
X. Other (please specify)

[Answer]: A

## Q6. 残ってしまった印の扱い

apply が強制的に止められると、同時実行を防ぐ印が残り、次の apply や rollback が「実行中」として止まります。どう扱いますか?

A. 印に、作った時刻・ホスト名・プロセスID・runId を書く。止まったときは、それを示して「実行中でないことを確かめてから `--force-unlock` で外す」と案内する。自動では外さない
B. A に加えて、同じホストで、そのプロセスがもう動いていなければ自動で外す
C. 印に有効期限(例: 12時間)を付け、期限を過ぎたものは自動で外す
X. Other (please specify)

[Answer]: A

## Q7. タグ数の上限(FR5.10)

書き換えたあとのタグの数(`aws:` を除く)が上限を超えるリソースは、書き換えずに一覧に出します。上限はどう決めますか?

A. すべての種類で50とする。上限が違う種類が見つかったら、AWS が返す誤り(タグが多すぎる)を「失敗」として理由つきで出す
B. 種類ごとの上限の表を持つ(既定は50、違う種類だけ表に書く)。表にない違いは A と同じく AWS の誤りで扱う
C. 上限を前もって判定せず、AWS が返す誤りだけで判断する
X. Other (please specify)

[Answer]: A

## Q8. 端末でないときの確認

標準入力が端末でない(パイプやスクリプトから動かしている)ときに、`--yes` がなければどうしますか?

A. 確認を求めずに止める(終了コード 1)。スクリプトでは `--yes` を使うよう案内する(`echo yes |` で確認を通すことはできない)
B. 標準入力から1行読み、`yes` なら進める

## Consolidated Summary Confirmation

回答をまとめると、U6 の機能設計は次の内容になります。

1. **オプション(Q1 A):** `apply` は `--plan <ファイル>`(保存した変更案)か `--rules <ファイル>`(その場で変更案を作る)のどちらか1つを必ず指定します。ほかに `--yes`(確認を省く)、`--allow-impact`(影響を承知で進める)、`--record-to <場所>`(記録の保存先)と、Q6 の `--force-unlock` を持ちます。

# セキュリティの要件: U1 最小の一本

出典: 要件 NFR3、NFR8、FR7.6〜FR7.8、機能設計 `rules.md`(BR1.2〜BR1.6)、契約 C6、`nfr-requirements-questions.md` Q3・Q4、構築のフェーズの規則(認証情報を書かない、境目で入力を確かめる)。

## 守るもの

| 守るもの | なぜ大事か |
|---|---|
| 利用者の AWS の認証情報 | 漏れると、利用者のアカウントを他人に使われる |
| 利用者の AWS アカウントのタグとリソース | U1 は読むだけだが、書き込みの権限を求めないことが、利用者が安心して試す前提になる(US1.2) |
| ポリシーの中身 | 表示はするが、ツールの外に送らない |

## 要件

| ID | 要件 | 合否の基準 |
|---|---|---|
| NFR3.1 | scan と plan は、読み取りの口(タグの読み取り、ポリシーの読み取り、リージョンと呼び出し元の確認)だけを使い、書き込みの口を作らない(BR1.5) | scan と plan を組み立てる部分が受け取る型は、読み取り用のインターフェースだけである。書き込みの操作が呼ばれたらテストを失敗させる差し替えを渡して、scan と plan のすべてのテストが通る |
| NFR3.2 | U1 が呼ぶ API だけを並べた「読み取り用の IAM ポリシーの例」をリポジトリに置く。U1 では、タグの読み取り(`tag:GetResources`)、リージョンの確認(`ec2:DescribeRegions`)、付いている IAM のポリシーの一覧と、既定の版の中身の読み取りを含める(付いているものだけを一覧にする指定を使う。呼び出し元の確認は権限が要らない)。U2・U5 で API を足すたびに更新する(Q4) | (1) 検証用アカウントで、この例だけを付けたロールで scan と plan が動く。(2) 例に含まれる操作がすべて読み取り(`Get`、`List`、`Describe` で始まる)で、`*` を含まないことを、自動テストで確かめる |
| NFR8.1 | 認証情報(アクセスキー、シークレット、セッショントークン)を、標準出力、標準エラー、`--debug` の表示のどこにも出さない。AWS の SDK のエラー文をそのまま出さず、エラーの種類と API の名前だけを出す(BR1.4) | 偽の認証情報を設定してエラーを起こすテストで、出力に認証情報の文字列が含まれない |
| NFR8.2 | `--debug` の表示は、API の名前、リージョン、かかった時間、再試行の回数だけとし、タグの値やポリシーの中身を出さない(Q3) | `--debug` のテストで、タグの値が出力に含まれない |
| NFR8.3 | 認証情報はツールが保存せず、AWS の標準の設定(環境変数、プロファイル、SSO)から AWS の SDK が読む。ツールは認証情報を受け取るオプションを持たない | オプションの一覧に、認証情報を受け取るものがない |
| NFR8.4 | 外から受け取る入力(オプション、ルールファイル、AWS の応答のポリシー文書)は、境目で確かめる。ルールファイルは YAML の安全な読み方(別名の展開の上限、深い入れ子の拒否など)で読み、大きすぎるファイル(64 KiB を超えるもの。コードのレビュー R-01 を受けて 1 MiB から下げた)は読まない | 64 KiB を超えるルールファイル、別名を大量に展開する YAML、深さ32を超える入れ子の YAML で、数秒以内に InvalidInput になる |
| NFR8.5 | 依存ライブラリの既知の脆弱性を、CI で `govulncheck` を使って確かめ、見つかればマージしない(チームの進め方 §Code Style) | CI に govulncheck の手順があり、失敗でマージが止まる |
| NFR8.6 | AWS から読んだ文字列(タグのキーと値、ARN、ポリシーの文字列)を端末に出す前に、制御文字(ANSI のエスケープを含む)を見える形(例 `\x1b`)に置き換える。他人がタグに仕込んだ文字で、端末の表示を書き換えられないようにする | エスケープ文字や改行を含むタグを返す差し替えのテストで、出力に制御文字がそのまま含まれない |
| NFR8.7 | CI と依存の供給元を固定する。GitHub Actions はコミットの SHA で固定し、Dependabot は Go の依存と GitHub Actions の両方を対象にする。`golangci-lint` と `govulncheck` の版を固定する。ビルドとテストは `go.sum` を書き換えない設定(`-mod=readonly`)で行う。マージの後に見つかる脆弱性を拾うため、`govulncheck` を週1回の定期実行でも動かす | CI の設定ファイルで、5点すべてが確かめられる |
| NFR8.8 | ツールは、AWS の API と、AWS の SDK の標準の認証情報の解決が使う宛先(SSO、STS、EC2 のメタデータなど)以外へ通信しない(利用の統計や更新の確認をしない)。AWS の SDK の、リクエストと応答のログの出力は有効にしない(`--debug` の表示は NFR8.2 のとおりツールが自分で出す) | テストで、SDK のログの設定が無効であることを確かめる。依存の一覧に、統計を送るような通信の部品がないことを、レビューで確かめる |

## 脅威と対策

| 脅威 | 対策 |
|---|---|
| エラー文や `--debug` から認証情報が漏れる | NFR8.1、NFR8.2 |
| 利用者が書き込みの権限を渡すことを求められる | NFR3.1、NFR3.2 |
| 悪意のあるルールファイル(巨大なファイル、YAML の爆発) | NFR8.4 |
| 依存ライブラリの脆弱性、CI の供給元のすり替え | NFR8.5、NFR8.7、Dependabot |
| タグに仕込まれた制御文字で端末の表示を書き換える | NFR8.6 |
| ポリシーの中身や認証情報が、ツールの外や SDK のログに出る | NFR8.2、NFR8.8 |
| ポリシー文書の想定外の形(条件の値が配列、文字列が URL エンコード) | 機能設計 BR5.2〜BR5.6 で扱い、読めないものは「判定できない」か「不完全」にする。影響なしにしない |

## 認可の考え方

ツールは独自の利用者や権限を持ちません。何ができるかは、利用者が使う AWS の認証情報の権限で決まります。ツールの側では、scan と plan が書き込みの口を持たないことで、読み取りに限ります。

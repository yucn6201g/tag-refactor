# 観測のしやすさの要件: U1 最小の一本

出典: 要件 FR1.4、FR7.5、NFR8、NFR11、機能設計 `rules.md`(BR6.1、BR6.2)、`nfr-requirements-questions.md` Q3。

tag-refactor は利用者の端末で動く CLI で、サーバーの監視、警報、ダッシュボードはありません。観測のしやすさとして求めるのは、利用者が「何が起きたか」を標準エラーの表示から分かることです。

| ID | 要件 | 合否の基準 |
|---|---|---|
| NFR11.1 | 結果の意味は、記号(`~`、`!`、`?`)と文字で表す。U1 は色を使わない(BR6.2) | 色のない端末で、すべての結果の意味が分かる |
| NFR11.2 | 進み具合(リージョンの読み始めと読み終わり、件数)と、アカウント、リージョン、終了コードの行を標準エラーに出す(BR6.1) | 標準出力をファイルに保存したとき、ファイルにこれらの行が含まれない |
| NFR11.3 | `--debug` を付けると、呼んだ AWS の API の名前、リージョン、かかった時間、再試行の回数を、1回の呼び出しにつき1行で標準エラーに出す(Q3)。認証情報、タグの値、ポリシーの中身は出さない(NFR8.2) | `--debug` のテストで、API の名前と時間の行が出て、タグの値が出ない |
| NFR11.4 | エラーは2行(何が起きたか、どう直すか)で標準エラーに出す(機能設計 W3) | 各エラーの種類のテストで、2行の案内が出る |

かかった時間と件数の表示は、性能の要件 NFR1.1 で定めています。

## SLI と SLO

サーバーではないため、SLI と SLO は定めません。品質は、CI のテスト(3つの OS、カバレッジ80%以上)と、検証用アカウントでのチェックポイントで確かめます。

# 性能の設計: U1 最小の一本

出典: `nfr-requirements/performance-requirements.md`(NFR1.1〜NFR1.3)、`scalability-requirements.md`(NFR1.4、NFR1.5)。

## 測り方(NFR1.1、NFR1.2)

- `cli` が、コマンドの始まりと終わりの時刻を取り、終わりに「かかった時間と調べたリソースの件数」を標準エラーに1行で出す(例: `Done in 00:12 · 412 resources`)。
- U1 のチェックポイントでは、検証用アカウントでの実行の、リージョン、件数、かかった時間を記録に残す。U2 が NFR1 を見積もる材料にする。

## 読み方(NFR1.3)

- タグの読み取りは、1回の呼び出しで返せる最大の件数を指定し、続きの印(ページの印)が空になるまで読む。結果が空のページでも、印があれば読み続ける(`reliability-design.md` の「ページ読み」)。リソースごとに取り直さない。
- IAM の管理ポリシーは、付いているものだけの一覧を最後まで読み、各ポリシーの既定の版の中身を読む。U1 では、ポリシーの中身の読み取りは1つずつ順番に行う(並列にするのは U2・U5 で必要になってから)。

## 計算の手間(NFR1.4、NFR1.5)

- キーのまとまりは、正規化したキーを鍵にした表で数える(リソースの件数に比例する手間)。
- 名前の変更は、リソースごとに正しいキーの規則を見る(リソースの件数 × 規則の数に比例)。別名から正しいキーを引く表を先に作る。
- 影響分析は、条件キーを先に取り出して「タグのキー(小文字)→ 条件の一覧」の表にし、変更ごとに fromKey と toKey で引く。ワイルドカードを含む条件だけは、変更ごとにパターンで照合する。パターンは、入力の長さに比例する時間で動く正規表現に変えて照合する(`security-design.md` §4)。
- 性能のテスト(HTTP の層の差し替え): 1万件のリソースの scan と plan、ポリシー500件と変更1,000件の影響分析を、CI の各 OS で10秒以内に終わることを確かめる。`a*a*a*a*a*b` のような病的なワイルドカードのパターンを含むテストも、同じ時間内に終わることを確かめる。

## 使わないもの

キャッシュ、接続のプール、非同期の処理は U1 では使いません。1回の実行で同じものを2回読まないため、必要がありません。

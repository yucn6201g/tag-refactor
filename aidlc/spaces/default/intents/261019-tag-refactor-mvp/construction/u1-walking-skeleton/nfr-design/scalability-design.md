# 規模の設計: U1 最小の一本

出典: `nfr-requirements/scalability-requirements.md`(NFR1.4、NFR1.5)、`performance-design.md`。

tag-refactor は1人が端末で動かす CLI で、台数を増やす、負荷を分ける、データを分割するといった仕組みはありません。規模の設計は、1回の実行で扱う件数が増えても、メモリと時間が無理なく伸びるようにすることです。

| 対象 | 設計 | 伸び方 |
|---|---|---|
| リソース(NFR1.4) | リソースは ARN、種類、タグだけを持つ小さな形でメモリに置く。AWS の応答の他の項目は持たない | リソースの件数に比例 |
| キーのまとまり | 正規化したキーごとに、書き方ごとの件数だけを持つ(リソースの一覧は持たない) | キーの種類の数に比例 |
| ポリシー(NFR1.5) | 照合に使う条件だけを、表示に要る最小の形(ポリシーの ARN、ステートメントの Sid か番号、条件の演算子、条件キー、値)で取り出して持ち、ポリシーの文書全体は照合の後に捨てる(BR5.6) | 条件の数に比例 |
| 変更 | 変更ごとに1つの小さな形を持つ | 変更の数に比例 |

## 上限と、超えたときの扱い

- 件数の上限は設けません(NFR1.4)。1万件で数十 MB 程度に収まる見込みで、CI の性能のテストで確かめます。
- 全リージョンの並列の読み取りと、AWS の呼び出し回数の上限への本格的な対応は U2 で設計します。

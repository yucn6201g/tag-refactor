# 信頼性の設計: U1 最小の一本

出典: `nfr-requirements/reliability-requirements.md`(NFR5.1〜NFR5.3、NFR9.1、NFR9.2、NFR10.1、NFR10.2)、`nfr-design-questions.md` Q2・Q4、契約 C6・C12。レビュー(`reviews/review-01.md`)の R-01、R-05、R-08、R-11 を受けて改訂しました。

## 時間の上限と再試行(NFR5.1、NFR5.2)

- **1回の試行の上限:** AWS の呼び出しの1回の試行(HTTP の要求1回)ごとに30秒。これを NFR5.1 の「1回の呼び出しにつき30秒」とする。
- **操作全体の上限:** 1回の API の呼び出し(1ページ分)について、再試行を含めた全体に120秒の上限をかける。超えたら `Transient`。ページをまたいだ読み取り全体には上限をかけない(件数に比例して長くなるため。全体の時間は NFR1 として U2 で扱う)。
- **再試行:** AWS の SDK の標準の再試行(標準のモード、既定の回数)をそのまま使う(Q2)。使い切った失敗は `Transient`。他の部品は再試行しない(契約 C6)。
- **時計の差し込み:** 時間の上限と、かかった時間の計測は、`awsaccess` が受け取る時計(と待ち)の口を通す。テストでは、実時間を待たずに上限の超過を起こす。
- U2 で、待ち時間を延ばす再試行と、呼び出し回数の上限への対応を強める。
- コードの生成で確かめること: 試行ごとの上限を SDK のどの設定でかけるか(HTTP の要求ごとの上限か、試行ごとの文脈か)。再試行の回数を SDK から取り出す方法(取れなければ `--debug` に `retries=n/a` と出す)。

## テストの差し込み口(R-01)

テストで AWS を差し替える位置を、2つの層に分けます。

| 層 | 差し替えるもの | 使うテスト | 確かめられること |
|---|---|---|---|
| HTTP の層 | `awsaccess` が作る SDK の設定に渡す HTTP の送り先を、テスト用の偽の AWS(決まった応答を返し、受け取った操作の名前を記録する)にする。SDK の設定の作り方、時間の上限、再試行、ページ読み、エラーの変換、`--debug` の記録は、本物がそのまま動く | 受け入れ条件のテスト(コマンドの入口から流す)、`awsaccess` の単体テスト、性能のテスト | NFR1.3(ページ読み)、NFR3.1(読み取りの操作だけ)、NFR5.1・NFR5.2(上限と再試行)、NFR8.1(認証情報を出さない)、NFR8.8(SDK のログが無効)、NFR11.3(`--debug` の行) |
| 契約のインターフェースの層 | 契約 C6 の読み取りのインターフェース(TagReader、PolicyReader、AccountResolver)を、メモリの中の差し替えにする | `inventory`、`rules`、`planner`、`impact` の単体テスト | 規則(BR)ごとの判断 |

### 環境の隔離

- HTTP の層を使うテストは、テストごとに一時ディレクトリに作った AWS の設定ファイルと認証情報ファイルを指す環境変数を設定し、利用者の本物の設定(`~/.aws`)を読まない。
- AWS のプロファイルや認証情報を表す環境変数は、テストの中で上書きするか消す。
- EC2 のメタデータを無効にする環境変数を設定し、メタデータを探しに行って待たされないようにする。
- これらの準備は、テスト用の共通の手助けの関数にまとめ、HTTP の層を使うすべてのテストが通す。

## ページ読み(NFR1.3、R-08)

- タグの読み取り(`tag:GetResources`)は、続きの印が空になるまで読む。結果が空のページでも印があれば読み続ける。1ページの件数は API が許す最大にする(値はコードの生成で確かめる)。
- IAM の一覧(`iam:ListPolicies`)は、続きがあることを示す印と、次の位置の印で読む。
- テスト: HTTP の層の差し替えで、ページが3つに分かれた応答と、「空のページ + 続きの印あり」の応答を、最後まで読むことを確かめる。

## 不完全を正しく知らせる(NFR5.3)

- `impact` は、ポリシーの一覧の読み取りが拒否されたら、そこで照合をやめて UnreadPolicy(種類と理由)を記録し、`complete = false` で返す。個別のポリシーの読み取りが拒否されたら、そのポリシーの ARN を記録して残りを続ける。
- `cli` は、`impactAnalysisComplete` が false なら、結果の先頭に「! Impact analysis is incomplete」を出し、終了コードを 1 にする(BR6.3)。

## エラーの種類と終了コード

| 種類(C12) | 主に起きる場所 | 終了コード |
|---|---|---|
| InvalidInput | `cli`(オプション、リージョン)、`rules` | 1 |
| UnsupportedVersion、NotFound、StorageFailed | `rules` | 1 |
| CredentialsMissing | `awsaccess`(認証情報なし、期限切れ、解決の時間切れ) | 1 |
| AccessDenied | `awsaccess`(タグの読み取り) | 1 |
| Transient | `awsaccess`(再試行を使い切った、時間の上限を超えた) | 1 |
| Internal(U1 で契約 C12 に追加) | どこでも(想定外のエラー、`security-design.md` §5) | 1 |

エラーの種類は `internal/errkind` で定め、終了コードへの変換は `cli` だけが行う。入口では想定外の停止(パニック)を受け止めて、固定の1行と終了コード 1 にする。

## 3つの OS で同じに動く(NFR9.1、NFR9.2)

- ルールファイルは、CRLF と LF のどちらでも同じに読む(大きさの判定の後に、改行をそろえる)。行番号は改行の種類に関係なく数える。
- パスは OS の区切り文字に任せ、文字列の連結で作らない。
- `CGO_ENABLED=0` でビルドする。CI の3つの OS で、ビルドした実行ファイルを空のディレクトリにコピーして `--help` を動かす。

## テストの組み立て(NFR10.1、NFR10.2)

| 種類 | 動かす場所 | 中身 |
|---|---|---|
| 受け入れ条件のテスト | CI、手元 | U1 の受け入れ条件(機能設計 `traceability.json` の OK の項目)を、HTTP の層の差し替えと環境の隔離を使って、コマンドの入口から流す。実装より先にコミットする |
| 単体テスト | CI、手元 | 各パッケージの規則(BR)ごとのテスト。実装の後に書く |
| 性能のテスト | CI、手元 | `performance-design.md` のとおり |
| 出力の守りのテスト | CI、手元 | `display` と `cmd` の外から標準出力・標準エラーに直接書いていないことを、ソースを読んで確かめる(`security-design.md` §4) |
| 検証用アカウントのテスト | 手元だけ | ビルドタグ `integration` と、環境変数 `TAG_REFACTOR_IT_PROFILE`(プロファイル名)があるときだけ動く。scan と plan を実際のアカウントに対して動かし、終了コードと出力の形を確かめる(Q4) |

- カバレッジは、すべてのパッケージを計測の対象にする指定(`-coverpkg=./...`)で、Linux のジョブで測り、80%未満なら失敗させる。他の2つの OS は、テストが通ることだけを確かめる。
- NFR10.2 は、U1 のチェックポイントで、プルリクエストのコミットの一覧を見て確かめる。

## チェックポイントでの確認

U1 のチェックポイントでは、検証コマンドの実行に加えて、次を確かめます。

1. 検証用アカウントで、`docs/iam/readonly-policy.json` だけを付けたロールで scan と plan が動く(NFR3.2)。
2. 同じアカウントで、`aws:ResourceTag/env` の条件が `Env` のタグにも当てはまるかを、実際の呼び出しで確かめる(手順はインフラの設計 `infrastructure-specification.md` の「確認2の確かめ方」)。`ec2:ResourceTag/env` のようなサービス固有の条件キーは確かめず、機能設計 BR5.3 の見逃さない側の扱いのまま残す。
3. GitHub のブランチの保護で、CI の必須のジョブが設定されている(`security-design.md` §6)。
4. プルリクエストのコミットの順(NFR10.2)。
5. かかった時間と件数の記録(NFR1.2)。

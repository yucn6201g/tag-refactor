# 観測のしやすさの設計: U2 収集

U1 の観測の設計(`construction/u1-walking-skeleton/nfr-design/observability-design.md`: 標準出力は結果だけ、進み具合とエラーと `--debug` は標準エラー)は、そのまま使います。

出典: `nfr-requirements/performance-requirements.md`(NFR9.3、NFR11.5、NFR11.6)、`nfr-requirements/tech-stack-decisions.md`(`golang.org/x/term`)、機能設計 BR6.1、契約 C11。

## 1. 進み具合の表示(NFR11.5)

- 進み具合の通知口(契約 C11、`inventory` の `ProgressSink`)に、U2 で次を足す: リージョンが待ちになった、検出の段階が始まった、検出のリージョンの状態が決まった。経過時間は `display` が自分の時計(差し込み口)で測る。
- 書き手は `display` の1つの部品だけにする。読み取りの処理(複数のゴルーチン)は通知口を呼ぶだけで、端末には書かない。通知口の実装は1つの鍵で守り、書き換えと追記が混ざらないようにする。
- 表示の形は2つ。

| 形 | 使うとき | 振る舞い |
|---|---|---|
| 書き換え | 標準エラーが端末で、`TERM` が `dumb` でなく、Windows では仮想端末の処理を有効にできたとき | リージョンごとに1行の表を、カーソルを戻して書き直す。状態が変わったときと、最大で0.2秒に1回だけ書く。終わったら最後の状態を残して改行する |
| 追記 | それ以外のすべて | 状態が変わるたびに1行を足す(例 `us-east-1: done 1,204 so far (12s)`)。経過時間の行は足さない |

- 判定は標準エラーだけで行い、標準出力が端末かどうかは見ない(標準出力をファイルに向けても、端末の進み具合は書き換える)。
- 判定の部品は `display` の中の差し込み口(「端末か」「仮想端末の処理を有効にできるか」を返す関数)にする。テストでは差し込み口で「端末である」とし、書き換えの出力(制御の文字列を含む)を固定する。`TERM=dumb`、標準出力だけが端末、の組み合わせで追記になることもテストで確かめる。
- 書き換えに使う制御の文字列は、ツールが固定で持つものだけ。AWS から読んだ文字列は U1 の置き換えを通してから行に入れるので、表示を壊せない(`security-design.md` §3)。

## 2. Windows(NFR9.3)

- `golang.org/x/term` で標準エラーが端末かを判定し、Windows ではさらに、コンソールの設定に仮想端末の処理を足す。足せなかったら追記にする。
- Git Bash(mintty)などで、標準エラーが端末と判定されないときは、追記にする(安全な側)。
- CI の3つの OS では、標準エラーは端末でないため、追記の形のテストが通ることを確かめる。実際の書き換えの見え方は、U2 のチェックポイントで人が手元の Windows Terminal と Git Bash で確かめる。

## 3. `--debug`(NFR11.6)

- U1 の1行の形(`debug: <操作> <リージョン> <時間> retries=<回数>`、失敗のときはエラーの種類)のまま、Config と Resource Explorer の呼び出しも出す。`<操作>` は操作の表の `API` の名前(例 `resource-explorer-2:ListResources`)。
- 問い合わせの文、フィルタの文字列、応答の中身は出さない(U1 の方針のまま)。
- チェックポイントでは、この行の時間から操作ごとの L95 を求める(`performance-design.md` §4)。

## 4. 結果の「調べた範囲」

- 調べた範囲の行(`Checked:`)、検出の状態(`complete`、`partial`、`unavailable`)と理由、タグを変更できない種類は、機能設計(BR3.2、BR5.7)の形で出す。理由の文は「エラーの種類」と「操作の IAM の名前」(AccessDenied のとき)または「既定のビューがない」「既定のビューに条件がある」などの固定の文言で作り、AWS のエラー文は使わない。

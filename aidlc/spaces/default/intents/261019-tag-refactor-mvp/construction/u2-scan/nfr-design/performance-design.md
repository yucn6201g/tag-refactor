# 性能の設計: U2 収集

出典: `nfr-requirements/performance-requirements.md`(NFR1.6〜NFR1.10、NFR10.3)、`nfr-design-questions.md` Q1〜Q3、`security-design.md` §1(操作の表)、AWS のドキュメント(`API_ListResources.html`、`API_SelectResourceConfig.html`、`querying-AWS-resources.html`)。

## 1. 決めた値

| 値 | 決めたもの | 根拠 |
|---|---|---|
| リージョンを同時に読む数 | 8(固定) | Q1。呼び出し回数の上限はリージョンごとにかかるので、リージョンを同時に読んでも1つのリージョンの上限には近づかない |
| タグの取得の1ページ(P_tag) | 100 | U1 のまま(`GetResources` の上限) |
| Config の問い合わせの1ページ(P_cfg) | 100 | `SelectResourceConfig` の `Limit` の上限 |
| Resource Explorer の一覧の1ページ(P_re) | 500 | Q2。1,000 では `NextToken` が返らない |
| リージョンごとの決まった回数(k) | 4 | `DescribeConfigurationRecorders`、`DescribeConfigurationRecorderStatus`、`GetDefaultView`、`GetView` が各1回。どれも使わない経路では呼ばない |
| アカウントで1回の索引の一覧 | max(1, ⌈索引の数 ÷ 100⌉) | `ListIndexes`。全リージョンの索引を返す。1ページは最大100件なので、`NextToken` がなくなるまで読む(索引はリージョンに1つまでなので、ふつうは1回) |

同時に読む数と各ページの大きさは、`internal/awsaccess` と `internal/inventory` の定数として持ち、オプションや環境変数では変えられない(NFR1.9)。テストだけは、定数を差し替える口(パッケージの中の変数)を使って小さな値にできる。

## 2. 読み方

1. タグの付いたリソース: リージョンごとに、ページを順に読む。リージョンは `errgroup` の `SetLimit(8)` で同時に8つまで。
2. 一度もタグが付いていないリソース: 1. がすべて終わってから始める(進み具合の段階を分けるため。BR6.1)。`ListIndexes` を `MaxResults` 100 で最後まで読み、集約の索引があれば、そのリージョンで1回だけ `ListResources` を最後まで読む。集約の索引がない、または集約の索引に含まれないリージョンは、リージョンごとに Config、Resource Explorer の順で試す(Q3)。リージョンごとの検出も同時に8つまで。
3. Config の経路: 問い合わせの文は `SELECT arn, resourceType, resourceId, awsRegion, tags` とし、条件を付けない(Config はタグの中身や NULL を条件にできないため)。記録されたすべてのリソースをページで読み、ツールの側で利用者のタグがないものを選ぶ。
4. Resource Explorer の経路: `Filters.FilterString` に `tag:none` を入れ、`MaxResults` 500 で `NextToken` がなくなるまで読む。API の `Search` は呼ばない。

各リージョンの中のページは前のページの `NextToken` が要るので、順にしか読めない。そのため全体の時間は「全体の呼び出しの数 ÷ 8」と「最も呼び出しの多いリージョンの数」の大きいほうで決まる。

## 3. 呼び出し回数の上限(NFR1.6)

リージョン r の呼び出しの上限:

- タグの取得: max(1, ⌈n(r) ÷ 100⌉)
- 検出の決まった回数: 4
- Config の経路: max(1, ⌈c(r) ÷ 100⌉)。c(r) は Config が記録しているすべての件数(タグの付いたものを含む)
- Resource Explorer の経路: max(1, ⌈u(r) ÷ 500⌉)
- 両方を使うリージョン(Config が一部の種類だけを記録): 両方の和

これに、アカウントで1回の `ListIndexes` の max(1, ⌈索引の数 ÷ 100⌉) と、plan の IAM の読み取り ⌈p ÷ 1,000⌉ + p を足す。

CI のテスト(NFR1.6)の偽の AWS は、17リージョンに合わせて1万件のタグの付いたリソース、1,000件の一度もタグが付いていないリソース、100件のポリシーを置く。17リージョンのうち、Config の経路のリージョン、Resource Explorer の経路のリージョン、両方を使うリージョン、件数が0のリージョンを含める。テストは、偽の AWS が数えた回数と、上の式で計算した上限を比べる。

## 4. 時間の見積もり(NFR1.8)

- 見積もり = max(全体の呼び出しの上限 ÷ 8, 最も多いリージョンの呼び出しの上限) × L95 × 1.5 + plan の IAM の読み取りの回数 × L95 + NFR1.7 の時間。NFR1.8 の式に「最も多いリージョン」の項を足した、より厳しい式とする(件数が1つのリージョンに偏ると、同時に読んでも速くならないため)。
- 仮の L95 は0.5秒とする。AWS の読み取りの API の応答は、ふつう数百ミリ秒であるという仮定による [assumption]。
- 仮の値での見積もり(最も偏った場合: タグの付いた1万件と一度もタグが付いていない1,000件がすべて1つのリージョンにあり、Config がすべてを記録している): そのリージョンはタグの取得100回、Config 110回(1.1万件 ÷ 100)、決まった回数4回で214回。214 × 0.5 × 1.5 ≈ 161秒。plan の IAM の読み取り101回 × 0.5 ≈ 51秒。合わせて約3分半で、10分に収まる。
- 質問の Q1 で示した「約1分」は、件数が17リージョンに均等に分かれた場合の見積もりで、上の値は最も偏った場合の見積もりである。チェックポイントの判定には、最も偏った場合の式を使う。
- U2 のチェックポイントで、検証用アカウントで操作ごとの L95 を測り、この式で見積もり直して記録に残す。件数が少ないアカウントではページが小さく、L95 が短く出るおそれがある。この過小の分は安全率1.5で扱う。見積もりが10分を超えたら、同時に読む数を見直して測り直し、人の承認を得る。

## 5. ツール自身の処理(NFR1.7、NFR10.3)

- ARN での重複の除去、表記ゆれのまとめ、必須タグの数え上げは、すべて ARN やキーを鍵にした対応表で行い、件数に比例する手間に抑える(U1 の NFR1.4、NFR1.5 の方針のまま)。
- Config の結果の JSON は1件ずつ読み、全件を一度に文字列として持たない。
- 進み具合の書き換えは、状態が変わったときと、最大で0.2秒に1回に限る(`observability-design.md`)。端末への書き込みが処理を遅らせないようにするため。
- NFR1.6、NFR1.7、NFR5.7 の大きな偽の AWS のテストは、偽の AWS の応答を事前に作っておき、遅れを入れない(NFR5.7 の乱数の遅れは最大でも数ミリ秒)。CI の各 OS で合わせて2分以内に収める。

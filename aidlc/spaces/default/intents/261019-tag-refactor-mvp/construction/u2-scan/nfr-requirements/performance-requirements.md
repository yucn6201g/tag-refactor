# 性能と信頼性と観測のしやすさの要件: U2 収集

U2 は性能の目標 NFR1(1アカウント・全リージョン・1万件で、scan と plan を合わせて10分以内)を受け持ちます。U1 の要件(標準出力と標準エラーの分け方、`--debug` など)は、ここで書き換えない限り U2 でも守ります。

出典: 要件 NFR1、NFR5、NFR9、NFR10、NFR11、機能設計 `construction/u2-scan/functional-design/`(BR2.4、BR3.1、BR3.2、BR4.1〜BR4.3、BR6.1)、`nfr-requirements-questions.md` Q1・Q2、AWS のドキュメント(Resource Explorer の `API_ListResources.html`)。

## 性能(NFR1 の確かめ方)

時間を縮めて測るのではなく、「呼び出しの回数」と「1回の呼び出しの実際の時間」に分けて確かめます(Q1 の2つの組み合わせ)。

呼び出し回数の式で使う記号:

- n(r): リージョン r のタグの付いたリソースの件数。P_tag = 100(タグの取得の1ページの件数)
- c(r): リージョン r で Config が返す件数(Config の経路のとき)。P_cfg = Config の問い合わせの1ページの件数(NFR の設計で決める)
- u(r): リージョン r で Resource Explorer が返す件数(Resource Explorer の経路のとき)。P_re = Resource Explorer の一覧の1ページの件数(1,000 未満の固定の値。NFR の設計で決める。NFR1.10)
- k: リージョンごとの決まった回数(記録の状態と索引の確認。NFR の設計で数を決める)
- p: plan で読む IAM のポリシーの数

| ID | 要件 | 合否の基準 |
|---|---|---|
| NFR1.6 | 1万件のときの AWS の呼び出しの回数が、決まった上限以下である。上限は、リージョンごとに max(1, ⌈n(r) ÷ P_tag⌉) + k + (Config の経路なら max(1, ⌈c(r) ÷ P_cfg⌉)、Resource Explorer の経路なら max(1, ⌈u(r) ÷ P_re⌉)) を足し、plan の IAM の読み取り ⌈p ÷ 1,000⌉ + p を足したもの。Config の問い合わせで「利用者のタグがない」を条件に書けない場合(NFR の設計の前に確かめる)は、c(r) を Config が記録しているすべての件数として数える | CI で、偽の AWS に17リージョン・合わせて1万件(タグの付いたもの)、1,000件(一度もタグが付いていないもの)、ポリシー100件を返させ、scan と plan の呼び出しの回数を数える。Config の経路のリージョンと Resource Explorer の経路のリージョン、件数が0のリージョンを含める。回数が式の上限以下である |
| NFR1.7 | ツール自身の処理の時間(AWS の待ち時間を除いたもの)が短い | NFR1.6 と同じ偽の AWS(遅れなし)で、scan と plan の合計が CI の各 OS で30秒以内に終わる |
| NFR1.8 | 検証用アカウントで、1回の呼び出しの時間の95パーセンタイル(L95)を、操作ごとに測る(`--debug` の行の時間から求める)。次の式で1万件の時間を見積もり、U2 のチェックポイントの記録に残す。見積もり = (NFR1.6 の回数の上限のうちリージョンごとの分 ÷ 同時に読む数) × L95 × 1.5(安全率) + plan の IAM の読み取りの回数 × L95 + NFR1.7 の時間。検証用アカウントは件数が少なく、ページが小さいぶん L95 が1万件のときより短く出る恐れがある。この過小の分は安全率で扱い、記録にその旨を書く | 見積もりが10分以内で、測った値と式と結果が記録にある。呼び出し回数の上限に当たった場合の待ち時間は、NFR5.4 の上限の待ち時間を、測定で上限に当たった回数だけ足して見積もる。見積もりが10分を超えたときは、NFR1.9 の同時に読む数を見直し、測り直してから人の承認を得る |
| NFR1.9 | リージョンを同時に読む数は、ツールが決めた固定の数とし、利用者は変えられない(Q2)。L95 の実測はコードの生成のあとでしか得られないため、NFR の設計では、仮の1回の呼び出しの時間と、その根拠(U1 の検証での実測など)を明記して数を決める。数は、呼び出し回数の上限にも収まるようにする。U2 のチェックポイントで NFR1.8 の実測で確かめ、合わなければ見直す | オプションの一覧に同時に読む数を変えるものがない。NFR の設計に、数と、仮の値と根拠がある。チェックポイントの記録に、NFR1.8 で確かめた結果がある |
| NFR1.10 | 一度もタグが付いていないリソースの検出は、件数の上限なく最後まで読む。Resource Explorer では、件数に上限のない一覧の操作 `ListResources` を使い、1,000件までに限られる API の `Search` は呼ばない(BR3.1)。`ListResources` の1ページの件数 `MaxResults` は 1,000 未満の固定の値にし、続きの印 `NextToken` がなくなるまで読む。AWS のドキュメントのとおり、`MaxResults` を 1,000 にすると `NextToken` が返らず1,000件で打ち切られるため | (1) 偽の AWS で、`tag:none` の結果2,500件を、ツールが指定したページの大きさで返し、すべてを読むテストが通る。(2) 偽の AWS は「`MaxResults` が 1,000 のときは `NextToken` を返さない」振る舞いを再現し、ツールが 1,000 を指定したらテストが失敗する。(3) 検証用アカウントの結合テストでは、ページの大きさを小さくして(テストだけの設定)、`NextToken` で複数のページを最後まで読めることを実機で確かめる。1,000件を超える結果の実機での確認は、検証用アカウントの件数が足りないため行わず、そのことをチェックポイントの記録に書く |

## 信頼性

| ID | 要件 | 合否の基準 |
|---|---|---|
| NFR5.4 | すべての AWS の呼び出し(タグの取得、AWS Config、Resource Explorer、IAM)で、呼び出し回数の上限の応答のとき、待ち時間を延ばしながら(揺らぎを入れて)再試行する。最大の試行の回数は10回、1回の待ち時間の上限は20秒とする | (1) 上限の応答を3回返してから成功する偽の AWS で、処理が完了する。(2) 上限の応答を返し続ける偽の AWS で、10回試行したあと、そのリージョンが「失敗」(タグの取得)か「partial」(検出)になる。(3) 記録した待ち時間が、回数とともに上限の20秒まで増える(揺らぎの範囲の中で) |
| NFR5.5 | 時間の上限は、1回の試行に30秒(U1 の NFR5.1 のまま)、再試行を含めた1回の呼び出しに5分とする。U1 の NFR の設計(`construction/u1-walking-skeleton/nfr-design/reliability-design.md`)で決めた「再試行を含めた1回の呼び出しに120秒」を、U2 でこの値に置き換える(NFR5.4 の再試行が収まるように)。この変更は U1 で作った `internal/awsaccess` の設定の変更になるので、U1 のテストも合わせて直す | 応答しない偽の AWS で、30秒(テストでは短くした値)で試行が打ち切られ、再試行のあと、呼び出し全体の上限で失敗になる。`internal/awsaccess` の U1 のテストが、新しい値で通る |
| NFR5.6 | 1つのリージョンの失敗は、他のリージョンの収集を止めない(BR4.1)。一度もタグが付いていないリソースの検出の失敗は、タグの取得の結果を不完全にしない(BR3.2)。Resource Explorer の一覧が 401 を返したとき(既定のビューがない、または使えない)は、そのリージョンの Resource Explorer を「使えない」とし、理由に既定のビューがないことを出す(BR3.1) | 1つのリージョンだけ拒否する偽の AWS で、他のリージョンの結果が出て、終了コードが 1 になる。検出だけ拒否する偽の AWS で、終了コードが変わらず、「partial」と理由が出る。一覧が 401 を返す偽の AWS で、そのリージョンが「使えない」になり、理由が出て、終了コードが変わらない |
| NFR5.7 | 同時に読んでも、標準出力の結果は実行のたびに同じになる。表と Summary の並びは決まった鍵で並べ、Config と Resource Explorer が同じ ARN を返したときは Config の結果を残す | リージョンごとの応答の遅れを乱数で入れ替える偽の AWS で、乱数の種を変えて10回実行し、標準出力がすべて同じになる。標準エラーの進み具合は対象外。Go のレース検出(`-race`)は cgo が要るため、CI の Linux のテストのジョブだけで cgo を有効にして `-race` 付きで実行する。ほかの OS のジョブと、配るバイナリは `CGO_ENABLED=0` のまま |
| NFR5.8 | 認証情報の誤り(なし、期限切れ)は、どの段階(タグの取得、検出、plan の IAM の読み取り)で起きても全体を止め、ほかのリージョンの読み取りも取り消し、標準出力に何も出さない(BR4.3)。取り消したあと、読み取りの処理がすべて終わってから終了する | 3つの段階それぞれで期限切れを返す偽の AWS のテストで、標準出力が空で、終了コードが 1 になる。期限切れとして扱うエラーの種類の一覧(セキュリティの NFR8.11)をすべて使う。終了の時点で、読み取りの処理(goroutine)が残っていないことをテストで確かめる |

## 観測のしやすさ

| ID | 要件 | 合否の基準 |
|---|---|---|
| NFR11.5 | リージョンごとの状態(済み、実行中、待ち、失敗)と経過時間、検出の段階を、標準エラーに出す。標準エラーが端末で、かつ書き換えの表示が使えるときだけ同じ場所を書き換え、それ以外は1行ずつ追記する(BR6.1)。判定は標準エラーだけで行い、標準出力が端末かどうかは見ない。`TERM=dumb` のときは追記にする | 端末でないときの行の形を、テストで固定する。端末かどうかの判定を差し込み口にし、「端末である」と差し込んだテストで、書き換えの表示の出力も CI で確かめる。`TERM=dumb` と、標準出力だけが端末の組み合わせで追記になることをテストで確かめる。実際の端末での見え方は、U2 のチェックポイントで人が手元の端末で確かめる |
| NFR11.6 | `--debug` の1行に、AWS Config と Resource Explorer の呼び出しも含める(U1 の NFR11.3 の形のまま) | Config と Resource Explorer を呼ぶテストで、`debug:` の行に操作の名前が出る |

## 3つの OS とテスト

| ID | 要件 | 合否の基準 |
|---|---|---|
| NFR9.3 | Windows では、書き換えの表示に必要な端末の設定(仮想端末の処理)を有効にできたときだけ書き換え、できなければ追記に戻る。Git Bash などで端末と判定できないときも追記にする(安全な側) | 端末でない場合のテストが3つの OS の CI で通る。Windows の書き換えの表示は、U2 のチェックポイントで手元の Windows Terminal と Git Bash で確かめる |
| NFR10.3 | U2 で足す大きな偽の AWS のテスト(NFR1.6、NFR1.7、NFR5.7)は、CI の各 OS で合わせて2分以内に終わる。カバレッジは U1 と同じく `cmd` と `internal` のすべてで80%以上 | CI の実行時間とカバレッジのジョブで確かめる |

U1 の NFR9.1、NFR9.2、NFR10.1、NFR10.2 も、そのまま守ります。

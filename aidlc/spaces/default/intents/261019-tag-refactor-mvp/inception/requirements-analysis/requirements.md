## 1. 意図の分析

### 目的

AWS のタグを後から**安全に**統一できるようにする(意図 §問題)。利用者が困っているのは「統一の作業そのもの」より、「タグを変えると何が壊れるか分からないので手を付けられない」ことです(意図 §問題 Q1-B、Q1-D)。そのため、このツールの価値の中心は次の3つです。

1. 表記ゆれや必須タグの欠落を、件数つきで見える化する
2. 変更する前に、壊れる参照元(IAM ポリシー、リソースポリシー)を示す
3. 書き換えたあとでも、確実に元に戻せる

### 種類と規模

- 種類: 新規開発(コードはまだない)
- 範囲: 単一のコマンドラインツール。複数の機能(scan、rules、plan、apply、rollback、IaC への書き戻し)を持つ
- 複雑さ: 標準。AWS の多数の API と、ポリシーの条件の解析を扱う
- 詳しさ: Standard

### 段階と完成の定義

| 段階 | 内容 | 優先度 | 出典 |
|---|---|---|---|
| 第1弾 | scan、rules suggest、plan(影響分析つき) | Must | 範囲 §最初のバージョンの出し方 |
| 第2弾 | apply、rollback | Must | 同上 |
| 第3弾 | IaC への書き戻し、GitHub へのプルリクエスト作成 | Should / Could | 同上、S-Q8 |

最初のバージョンの完成は、第1弾と第2弾がそろった時点です(範囲 §最初のバージョンの出し方)。

## 2. 機能要件

### FR1. タグの収集(scan)【第1弾・Must】

出典: IB-01、IB-03、S-Q6、R-Q11、M-Q6、画面1・2

| ID | 要件 | 合否の基準 |
|---|---|---|
| FR1.1 | システムは、実行に使う AWS アカウントで有効になっているすべてのリージョンについて、リソースとそのタグを集めること | 有効なリージョンの数と、調べたリージョンの数が一致して表示される |
| FR1.2 | システムは、一度もタグが付いたことのないリソースも集めること。AWS Config が有効なら AWS Config を使い、無効なら Resource Explorer を使うこと | テスト用アカウントで、タグなしで作ったリソースが結果に含まれる |
| FR1.3 | AWS Config も Resource Explorer も使えない場合、システムは「一度もタグが付いたことのないリソースは見つけられなかった」ことと、その理由を示し、残りの処理は続けること | 両方が無効な環境で実行すると、その旨が表示され、終了コードはエラー(1)にならない |
| FR1.4 | システムは、リージョンごとの進み具合(済み、実行中、待ち)と経過時間を標準エラーに表示すること | 実行中に、リージョンごとの状態が文字で表示される |
| FR1.5 | 一部のリージョンを調べられなかった場合、システムは調べられなかったリージョンと理由を結果の先頭に示し、結果が不完全であることを明記すること | 権限のないリージョンを含めて実行すると、該当リージョンと「結果は不完全」の表示が出る |
| FR1.6 | システムは、同じ意味で書き方が違うタグキー(表記ゆれ)を、件数つきで一覧にすること | テストデータの `env` / `Env` / `environment` が1つのグループとして、それぞれの件数とともに表示される |
| FR1.7 | システムは、ルールファイルで必須とされたタグが付いていないリソースの件数を、タグごとに示すこと | 必須タグが欠けたリソースの件数が、テストデータと一致する |
| FR1.8 | 問題が見つからなかった場合、システムは「問題なし」と、調べたリソースの件数を示すこと | 問題のないテストデータで「問題なし」と件数が表示される |

### FR2. 統一の基準とルールファイル(rules)【第1弾・Must】

出典: IB-02、S-Q7、R-Q1、R-Q2、R-Q3、画面3

| ID | 要件 | 合否の基準 |
|---|---|---|
| FR2.1 | システムは、既存のタグから、同じ意味と思われるキーや値をまとめ、正しいキー名・値の候補を含むルールファイルの下書きを出力すること | `rules suggest` の出力が、そのまま FR2.2 の形式として読み込める |
| FR2.2 | ルールファイルでは、正しいキー名と別の書き方(別名)、正しい値と別の書き方を指定できること | 別名を指定したキーが、plan でキー名の変更として扱われる |
| FR2.3 | ルールファイルでは、必須タグを指定できること。値は、全リソース共通の固定値と、条件(リソースの種類、リージョン、既に付いている他のタグ)ごとの値の両方で指定できること | 条件ごとの値が固定値より優先され、どちらにも当てはまらない場合は FR3.3 になる |
| FR2.4 | ルールファイルでは、消すタグのキーを指定できること | 指定したキーだけが plan で削除として扱われる |
| FR2.5 | ルールファイルに誤りがある場合、システムは誤りの場所(行、キー)と直し方を示して終了すること | 書式の誤ったファイルを読み込ませると、行番号つきのエラーが表示され、終了コードは1になる |

### FR3. 変更案の作成(plan)【第1弾・Must】

出典: IB-06、R-Q2、R-Q3、R-Q10、M-Q3、画面4〜6

| ID | 要件 | 合否の基準 |
|---|---|---|
| FR3.1 | システムは、ルールファイルに沿って、キー名の変更、値の変更、必須タグの追加、タグの削除の変更案を作ること | テストデータに対して、4種類の変更が正しい件数で示される |
| FR3.2 | システムは、変更の種類ごとの件数と、変更されるリソースの総数を示すこと。1つのリソースに複数の変更が重なる場合も、総数は重複して数えないこと | 2つの変更が重なるリソースが、総数で1件と数えられる |
| FR3.3 | ルールファイルで値を決められなかった必須タグは、「値が未指定」として一覧で示し、変更案に含めないこと。他の変更は変更案に含めること | 条件に当てはまらないリソースが「値が未指定」に表示され、そのリソースの他の変更は残る |
| FR3.4 | システムは、ルールファイルにないキーを「消す候補」として示すこと。消す候補は、ルールファイルで消すキーとして指定されるまで、変更案に含めないこと | ルールにないキーが候補として表示され、削除の変更案には入らない |
| FR3.5 | システムは、変更案を、端末向けの一覧(既定)、差分の形、JSON、Markdown の4つの形式で出力できること | 4つの形式で、変更の件数と影響の件数が一致する |
| FR3.6 | システムは、変更案をファイルに保存できること。保存するファイルには、作成日時、対象のアカウント、変更前のタグ、変更内容を含めること | 保存したファイルから、apply が FR5.2 を実行できる |
| FR3.7 | IaC で管理されていると分かるリソース(CloudFormation のスタックに属するリソースなど)は、変更案で「IaC で管理されている」と警告すること | CloudFormation で作ったリソースに警告が表示される |
| FR3.8 | システムは、変更案に影響分析(FR4)の結果を含めること | 影響のある変更に `!`、判定できない変更に `?` が付く |

### FR4. 影響分析【第1弾・Must】

出典: IB-04、IB-05、意図 §成功の基準、R-Q4、C-T3、実現性 §前のステージからの範囲の変化

| ID | 要件 | 合否の基準 |
|---|---|---|
| FR4.1 | システムは、IAM のユーザー、ロール、グループに付いたポリシー(利用者が作った管理ポリシーとインラインポリシー)の条件から、変更の影響を受ける箇所を見つけること | テスト用のポリシーに含めた参照がすべて検出される(NFR2) |
| FR4.2 | システムは、S3 バケット、KMS キー、SQS キュー、SNS トピック、Secrets Manager のシークレットのリソースポリシーの条件から、変更の影響を受ける箇所を見つけること | 同上 |
| FR4.3 | 影響分析の対象は、キー名の変更、値の変更、タグの削除のすべてとすること | 値だけを変える変更でも、その値を条件にした参照が検出される |
| FR4.4 | タグに関する条件キー(リソースのタグ、リクエストのタグ、タグキーの一覧、呼び出し元のタグ、サービス固有のリソースタグ)を、検出の対象とすること | 各種類の条件キーを含むテスト用ポリシーで、すべて検出される |
| FR4.5 | ワイルドカードやポリシー変数を含むなど、影響があるかを機械的に判定できない条件は、「判定できない」(`?`)として示すこと | ワイルドカードを含む条件が `?` として表示され、影響なしとは表示されない |
| FR4.6 | 影響を受ける参照元ごとに、ポリシーの名前(または ARN)、該当するステートメント、条件を示すこと | 表示から、どのポリシーのどの条件かが特定できる |
| FR4.7 | ポリシーを読む権限がない場合、システムは読めなかったポリシーの種類と理由を示し、影響分析の結果が不完全であることを明記すること | 権限のない状態で実行すると、「影響分析は不完全」と表示される |

### FR5. タグの書き換え(apply)【第2弾・Must】

出典: IB-07、S-Q5、M-Q4、R-Q5〜R-Q10、R-Q14、画面7・8

| ID | 要件 | 合否の基準 |
|---|---|---|
| FR5.1 | apply は、実行時に変更の要約(件数、影響のある変更、IaC で管理されているリソース)を示し、利用者が `yes` と入力したときだけ書き換えること | `yes` 以外を入力すると、何も書き換えずに終了する |
| FR5.2 | apply は、保存した変更案のファイルを指定して実行できること | 保存したファイルの内容どおりに書き換えられる |
| FR5.3 | apply は、確認を省くオプションを持つこと | オプションを付けると、確認の入力なしで実行される |
| FR5.4 | 影響のある変更が含まれる場合、apply は確認画面でそれを目立たせ、`yes` の入力で実行できること | 影響のある変更が、確認画面で記号と文字で示される |
| FR5.5 | 確認を省くオプションで実行したときに影響のある変更が含まれる場合、apply は何も書き換えずに止まること。影響を承知で進めるための別のオプションを付けたときだけ実行すること | 確認を省くオプションだけでは止まり、終了コードは2になる。両方のオプションで実行される |
| FR5.6 | 保存した変更案を作った後にタグが変わっていたリソースは、書き換えずに飛ばし、最後に一覧で示すこと | 変更案の作成後に手で変えたリソースが、飛ばした一覧に出る |
| FR5.7 | 一部のリソースの書き換えに失敗した場合も、残りのリソースの書き換えを続け、最後に成功と失敗の件数と一覧を示すこと。失敗の詳細はログファイルにも残すこと | 権限のないリソースを含めて実行すると、残りは書き換えられ、失敗の一覧が表示される |
| FR5.8 | apply は、書き換える前のタグの状態を、書き換えより先に記録すること。記録の保存先は既定で手元のファイル(実行ごとに1ファイル)とし、S3 バケットも指定できること | 実行ごとに記録ができ、FR6 の rollback で使える |
| FR5.9 | apply は、`aws:` で始まるタグ(AWS が管理するタグ)を書き換えたり消したりしないこと | `aws:` で始まるタグを対象にしたルールでも、変更されない |
| FR5.10 | 書き換えると1つのリソースのタグの上限数を超える場合、そのリソースは書き換えずに、理由とともに一覧で示すこと | 上限を超えるテストデータで、そのリソースが一覧に出る |
| FR5.11 | apply は、実行の終わりに、取り消すためのコマンド(実行IDつき)を示すこと | 表示されたコマンドで rollback できる |

### FR6. 取り消し(rollback)【第2弾・Must】

出典: IB-08、R-Q8、R-Q9、画面9

| ID | 要件 | 合否の基準 |
|---|---|---|
| FR6.1 | rollback は、apply の実行IDを指定して、その実行で書き換えたリソースのタグを、記録した状態に戻すこと | apply と rollback を続けて実行すると、タグが apply の前と一致する(NFR4) |
| FR6.2 | rollback は、戻す件数と、apply の後に別の変更が入ったリソースの件数を示し、`yes` の入力で実行すること | `yes` 以外では何も戻さない |
| FR6.3 | apply の後に別の変更が入ったリソースは、既定では戻さずに飛ばし、一覧で示すこと。上書きのオプションを付けたときだけ戻すこと | 既定では飛ばされ、オプションを付けると戻される |
| FR6.4 | rollback は、戻した件数、飛ばした件数、失敗した件数を示すこと | 実行後に3つの件数が表示される |
| FR6.5 | 途中で止まった apply(強制終了など)についても、記録が残っている範囲で rollback できること | apply を途中で止めた後、書き換えた分だけが戻される |

### FR7. コマンド全体の振る舞い【第1弾から・Must】

出典: M-Q2、M-Q5、M-Q6、M-Q7、R-Q12、R-Q13

| ID | 要件 | 合否の基準 |
|---|---|---|
| FR7.1 | 機能ごとにサブコマンド(`scan`、`rules suggest`、`plan`、`apply`、`rollback` など)で呼び出せること | 各サブコマンドのヘルプが表示される |
| FR7.2 | 表示は英語と日本語を切り替えられること。設定がないときは OS の言語設定に合わせ、どちらでもない場合は英語にすること | 日本語の OS では日本語、それ以外では英語で表示される |
| FR7.3 | 色は補助として使い、意味は必ず記号と文字でも表すこと。`NO_COLOR` 環境変数が設定されていれば色を出さないこと | `NO_COLOR` を設定すると色が出ず、意味は記号で分かる |
| FR7.4 | 終了コードは、0 = 問題なし、1 = エラー、2 = 問題や影響が見つかった、とすること | scan で問題が見つかると2、認証情報がないと1 |
| FR7.5 | 進み具合や案内は標準エラーに、結果(一覧、JSON、Markdown)は標準出力に出すこと | 標準出力をファイルに保存しても、案内のメッセージが混ざらない |
| FR7.6 | AWS の認証情報とリージョンは、AWS の標準の設定(環境変数、プロファイル)から読み、プロファイルはオプションでも指定できること | `--profile` で指定したプロファイルが使われる |
| FR7.7 | 権限が足りないときは、足りない操作(API)の名前を示すこと。必要な権限の一覧(IAM ポリシーの例)は、読み取り用と書き込み用に分けてドキュメントで提供すること | 権限のない状態で実行すると、足りない API の名前が表示される |
| FR7.8 | 認証情報が見つからないときは、何が足りないかと設定方法を示して終了すること | 認証情報なしで実行すると、設定方法が表示され、終了コードは1 |

### FR8. IaC への書き戻し【第3弾】

## 3. 非機能要件

| ID | 種類 | 要件 | 合否の基準 | 出典 |

| NFR2 | 正確さ | 影響分析(FR4)は、テスト用に用意した参照を100%検出すること。テスト用の参照は、FR4.1・FR4.2 の参照元と FR4.4 の条件キーのすべての組み合わせを含むこと | 自動テストで検出率100% | 意図 §成功の基準 |

| NFR4 | 安全性 | apply のあと、別の変更が入っていなければ、rollback でタグが apply の前と完全に一致すること | 自動テストと検証用アカウントで、差分が0 | 意図 §対象となる利用者(Q13)、前ステージのレビュー |

| NFR6 | 信頼性 | 書き換える前の状態の記録は、書き換えより先に、途中で壊れない方法(書き込んでから名前を変えるなど)で保存すること | 記録の保存中に処理を止めても、記録が壊れない | FR5.8 |
| NFR7 | 信頼性 | 同じアカウントで apply や rollback が同時に動いた場合に、記録が壊れないこと | 2つの apply を同時に実行するテストで、記録が壊れない | コーナーの洗い出し |
| NFR8 | セキュリティ | 認証情報を表示、記録、ログに出さないこと | ログと出力に認証情報が含まれないことをテストで確かめる | 進め方 §Code Style、構築フェーズの規則 |
| NFR9 | 移植性 | Linux、macOS、Windows で動くこと。単一の実行ファイルで配れること | 3つの OS の CI でテストが通る | M-Q7、進め方 §Testing Posture |
| NFR10 | 保守性 | テストのカバレッジ(Go の文単位)が80%以上であること | CI で計測して80%以上 | 進め方 §Testing Posture |
| NFR11 | 使いやすさ | 色が見えなくても、すべての結果の意味が分かること | `NO_COLOR` 環境で、すべての画面の意味が記号と文字で分かる | M-Q6 |
| NFR12 | 配布 | GitHub Releases と `go install` で入手できること。配るバイナリにはチェックサムを付けること | リリースにチェックサムのファイルが含まれる | 進め方 §Deployment |

## 4. 制約

| ID | 制約 | 出典 |
|---|---|---|
| CON1 | 実装言語は Go | C-T1 |
| CON2 | 対象は1アカウント。複数アカウント(Organizations)の横断はしない | C-T2 |
| CON3 | 影響分析の対象は IAM ポリシーとリソースポリシー。SCP と RCP、AWS Backup、DLM、SSM、Resource Groups、Auto Scaling は対象外 | C-T3、実現性 §前のステージからの範囲の変化 |

| CON5 | 検証は個人の検証用アカウントで行う | C-O4 |
| CON6 | 開発の進め方(プルリクエストでのマージ、マージ前の CI、カバレッジ80%など)は、`team-practices.md` に従う | 進め方 |

## 5. 前提

| ID | 前提 | 理由 |
|---|---|---|
| AS1 | タグのキーは大文字と小文字を区別して扱う。表記ゆれ(大文字と小文字の違いなど)をまとめるかどうかは、ルールファイル(別名)で利用者が決める | AWS のタグのキーは大文字と小文字を区別するため |
| AS2 | タグの値は秘密情報ではないとみなし、そのまま表示する | タグはコンソールなどで誰でも見られる情報として扱われることが多いため。秘密情報を入れている利用者向けの対応は今回は行わない |
| AS3 | タグ用の共通 API に対応していないリソースの種類は、対応できた種類だけを処理し、対応できなかった種類と件数を示す | すべてのリソースの種類に個別に対応するのは、最初のバージョンでは作る量が大きすぎるため |
| AS4 | 変更案、ルールファイル、記録のファイルは UTF-8 で読み書きし、改行の違い(CRLF と LF)を区別せずに読む | Windows でも動かすため |
| AS5 | 日時は UTC の ISO 8601 形式で記録し、表示は利用者の環境の時刻で行う | 複数の環境で記録を比べられるようにするため |
| AS6 | リソースは ARN で識別し、ARN は文字列としてそのまま扱う | ARN の形はサービスごとに違うため |
| AS7 | IaC で管理されているかの判定(FR3.7)は、第2弾では CloudFormation のスタックに属するリソースだけを対象とする | Terraform で管理されているかは、リソースだけからは分からないことが多く、state を読む必要があるため(第3弾で扱う) |

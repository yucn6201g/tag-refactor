# 作業単位の分割 — 質問

ドメイン設計で決めた11個の部品を、実装の作業単位(Unit)にまとめます。チームの進め方で、最初の作業単位は「端から端まで動く最小の一本」(`scan` と `plan` の最小版に、ビルド、テスト、lint、CI を加えたもの)にすると決まっています。また、配布は単一の実行ファイル(GitHub Releases と `go install`)と決まっているため、すべての作業単位は最終的に1つの実行ファイルにまとまります。

このステージでは「どの作業単位がどれに依存するか」だけを決め、作る順番は次の「作業計画」のステージで決めます。

## Q1. 作業単位の切り方

部品をどう作業単位にまとめますか?

A. 機能ごとにまとめる(9単位程度): 最小の一本、収集、ルール、変更案、影響分析、配布、書き換えと記録、取り消し、IaC への反映
B. 部品ごとに1単位にする(11単位): Cli、Display、AwsAccess など部品と同じ数
C. 段階ごとにまとめる(3〜4単位): 最小の一本、第1弾の残り、第2弾、第3弾
D. Not yet defined
X. Other (please specify)

[Answer]: A

## Q2. 依存のない作業単位の進め方

互いに依存しない作業単位がある場合、どう扱いますか?

A. 並行して進めてよい(依存関係さえ守れば、どれから作ってもよい)
B. 1人で進めるため、並行はせず1つずつ進める
C. Not yet defined
X. Other (please specify)

[Answer]: A

## Q3. 配布(リリース)の作業単位

GitHub Releases への公開、`go install` への対応、チェックサムの作成といった配布の仕組みを、どう扱いますか?

A. 独立した作業単位にする(第1弾の公開 `v0.1.0` までに必要)
B. 最小の一本に含める
C. Not yet defined
X. Other (please specify)

[Answer]: C

## Q4. 配布の扱いを決めない場合の置き方(Q3の補足)

Q3は「まだ決めない」でした。作業単位の依存関係を描くために、配布をどこに置くかを仮に決める必要があります。どうしますか?

A. 仮に独立した作業単位として置き、扱いは次の「作業計画」のステージで決める
B. 今回の作業単位には含めず、配布は別の作業として後で行う
C. 最小の一本に含める
X. Other (please specify)

[Answer]: B

## Consolidated Summary Confirmation

回答のまとめ:

- 作業単位の切り方(Q1): 機能ごとにまとめる

# 設計の判断の記録(ADR): tag-refactor

ドメイン設計で決めた、重要な設計の判断です。出典は `domain-design-questions.md`(DD-Q1〜DD-Q6)と、`inception/requirements-analysis/requirements.md`(FR・NFR)です。

---

## ADR-001: 部品を細かめに分ける

- **状態:** 採用(2026-10-20)

### Context

要件は、収集(FR1)、ルール(FR2)、変更案(FR3)、影響分析(FR4)、書き換え(FR5)、取り消し(FR6)、コマンド全体(FR7)、IaC への反映(FR8)に分かれています。開発は1人で、Go の経験は少なく、カバレッジ80%以上と、受け入れ条件を先にテストにする進め方を決めています。部品の粗さは、テストのしやすさと、1人で理解できる大きさに直接影響します。

### Decision

要件のまとまりに沿って、11個の部品(Cli、Display、AwsAccess、Inventory、RuleEngine、Planner、ImpactAnalyzer、Applier、Rollbacker、Journal、IacWriter)に分けます(DD-Q1、DD-Q2)。

### Consequences

- 良い点: 部品ごとに受け入れ条件を対応させやすく、単独でテストできます。部品の境目がはっきりするため、後で作業の単位に分けやすくなります。
- 悪い点: 部品の数が多く、部品の間のデータの受け渡し(インターフェース)を多く決める必要があります。
- セキュリティ: 書き換えを行う部品(Applier、Rollbacker)が限られるため、書き込みの権限が必要なコードの範囲を絞れます。

### Alternatives Rejected

- **粗めに分ける(4個程度):** CLI と表示、収集、分析(ルール、変更案、影響分析)、書き換え(書き換えと記録)。部品の数は少なくなりますが、「分析」の中に影響分析が埋もれ、検出率100%の確認を単独で行いにくくなるため採りませんでした。

## ADR-002: apply、rollback、記録を別々の部品にする

- **状態:** 採用(2026-10-20)

### Context

apply(FR5)と rollback(FR6)は、どちらもタグを書き換えますが、判断が違います。apply は変更案の作成後の変化を確かめ、rollback は apply の後の変化を確かめます。記録(FR5.8、NFR6、NFR7)は両方が使い、保存先は手元のファイルと S3 の2種類です。

### Decision

apply を Applier、rollback を Rollbacker、記録を Journal として、3つの部品に分けます(DD-Q2)。Applier と Rollbacker は、Journal と AwsAccess を呼びます。

### Consequences

- 良い点: 「書き換える前に記録を必ず保存する」「後から変えられたリソースは既定で飛ばす」といった安全上の決まりを、部品ごとに独立して確かめられます。記録の保存の壊れにくさと同時実行の防止は Journal だけで扱えます。
- 悪い点: Applier と Rollbacker で、タグを読み書きする処理が似た形になり、重複が生まれる可能性があります。
- セキュリティ: 記録には書き換える前のタグが含まれます。S3 に保存する場合、バケットの権限は利用者の設定に依存します。

### Alternatives Rejected

- **apply と rollback を1つの「書き換え」部品にし、記録だけ分ける:** 重複は減りますが、apply と rollback の判断が1つの部品の中で混ざるため採りませんでした。
- **書き換えと記録をすべて1つの部品にする:** 記録の壊れにくさを単独で確かめにくく、部品が大きくなりすぎるため採りませんでした。

## ADR-003: 影響分析を独立した部品にし、変更案から呼ぶ

- **状態:** 採用(2026-10-20)

### Context

影響分析(FR4)は、このツールの価値の中心で、検出率100%(NFR2)を求めています。ポリシーの条件の照合は最も複雑な処理です。

### Decision

影響分析を ImpactAnalyzer として独立させ、Planner が変更の一覧を渡して同期的に呼びます(DD-Q3)。

### Consequences

- 良い点: テスト用のポリシーと変更の一覧だけで、ImpactAnalyzer を単独でテストできます。検出率100%の確認がしやすくなります。
- 悪い点: Planner と ImpactAnalyzer の間で、変更の一覧と指摘の受け渡しの形を決める必要があります。
- セキュリティ: ImpactAnalyzer はポリシーを読むだけで、書き込みは行いません。読み取りの権限だけで動きます(NFR3)。

### Alternatives Rejected

- **変更案の部品の中に含める:** 部品の数は減りますが、影響分析だけを単独でテストしにくくなるため採りませんでした。

## ADR-004: AWS の呼び出しを共通の部品(AwsAccess)にまとめる

- **状態:** 採用(2026-10-20)

### Context

AWS を呼ぶ部品は5つあります(Inventory、ImpactAnalyzer、Applier、Rollbacker、Journal)。どの呼び出しにも、時間の上限と再試行(NFR5)、権限不足のエラーの案内(FR7.7)、認証情報を出力しないこと(NFR8)が求められます。チームの進め方では、単体テストで AWS の呼び出しを差し替えます。

### Decision

AWS の呼び出しを AwsAccess にまとめ、他の部品はこれを通して呼びます(DD-Q4)。

### Consequences

- 良い点: 再試行、時間の上限、権限不足のエラーの整形を一か所で実装できます。テストでは AwsAccess を差し替えるだけで済みます。
- 悪い点: AwsAccess に多くのサービスの呼び出しが集まり、大きくなる可能性があります。
- セキュリティ: 認証情報を扱うコードが一か所に集まるため、記録や出力に含めないことを確かめやすくなります。

### Alternatives Rejected

- **各部品が AWS を直接呼ぶ:** 部品ごとに再試行やエラーの扱いがばらつき、テストでの差し替えも部品ごとに必要になるため採りませんでした。

## ADR-005: 表示を1つの部品(Display)にまとめる

- **状態:** 採用(2026-10-20)

### Context

結果は4つの形式(一覧、差分、JSON、Markdown)と2つの言語で出し、形式によって件数が変わってはいけません(FR3.5、AC3.1.5)。結果は標準出力、案内は標準エラーに分けます(FR7.5)。

### Decision

表示を Display にまとめ、各機能の部品は結果のデータだけを返します(DD-Q6)。

### Consequences

- 良い点: 同じデータから4つの形式を作るため、件数が一致します。言語や色の扱いを一か所で決められます。
- 悪い点: 各機能の結果のデータの形を、Display が理解できる形で決める必要があります。

### Alternatives Rejected

- **各サブコマンドが自分で表示する:** 形式や言語の扱いがサブコマンドごとにばらつき、件数の一致を確かめにくくなるため採りませんでした。

## ADR-006: 部品の呼び出しを Cli にまとめる

- **状態:** 採用(2026-10-20)

### Context

scan、plan、apply などのサブコマンドは、複数の部品を決まった順に使います(例: plan は、収集 → ルールの読み込み → 変更案の作成)。部品どうしが互いを呼ぶと、依存関係が複雑になり、循環も起きやすくなります。

### Decision

Cli が部品を順に呼び出し、部品の間でデータを受け渡します。部品どうしの呼び出しは、Planner → ImpactAnalyzer、Applier・Rollbacker → Journal、AWS を呼ぶ部品 → AwsAccess だけにします。

### Consequences

- 良い点: 部品の依存関係に循環がなく、各部品を単独でテストできます。
- 悪い点: Cli がサブコマンドごとの手順を多く持ち、大きくなる可能性があります。

### Alternatives Rejected

- **各部品が前の段階の部品を呼ぶ(例: Planner が Inventory を呼ぶ):** Cli は小さくなりますが、部品の間の依存が増え、単独のテストで差し替える部品が増えるため採りませんでした。

## ADR-007: IaC への反映を部品として置いておく

- **状態:** 採用(2026-10-20)

### Context

IaC への反映(FR8)は第3弾で、詳しい振る舞いは未決です(要件 OQ3)。

### Decision

IacWriter を部品として置き、受け持つことだけを決めます。中身は第3弾に取りかかる前に設計します(DD-Q5)。

### Consequences

- 良い点: 全体の部品の構成が最初から見え、第3弾で他の部品を作り直す必要が少なくなります。
- 悪い点: 中身が決まっていないため、第3弾の設計で受け持つことが変わる可能性があります。
- セキュリティ: プルリクエストを作る場合、GitHub の認証情報を扱う必要があります。第3弾の設計で扱いを決めます。

### Alternatives Rejected

- **今は置かず、第3弾の前に改めて設計する:** 第3弾で部品の構成が大きく変わる可能性があるため採りませんでした。

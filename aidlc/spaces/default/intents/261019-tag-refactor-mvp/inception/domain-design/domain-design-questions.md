# ドメイン設計 — 質問

このステージでは、tag-refactor を「自分たちが書くコードの部品(コンポーネント)」に分け、それぞれが何を受け持ち、どのデータを持つかを決めます。どの部品をまとめて1つの実行ファイルにするか、どの技術を使うかは、後のステージで決めます。

要件定義とユーザーストーリーから、次の部品の候補を出しました。

| 候補 | 受け持つこと | 主なストーリー |
|---|---|---|
| CLI | サブコマンドとオプションの受け付け、確認の入力、終了コード | US6.1 |
| 表示 | 一覧、差分、JSON、Markdown の出力、言語、色、進み具合 | US6.1、US3.1 |
| AWS アクセス | 認証情報、アカウントの確認、リージョンの一覧、再試行と時間の上限 | US1.2、US1.1 |
| タグの収集 | 全リージョンのリソースとタグの収集、一度もタグが付いていないリソースの検出 | US1.1 |
| ルール | ルールファイル(YAML)の読み込みと検証、表記ゆれの候補の提案 | US2.1 |
| 変更案 | ルールに沿った変更案の作成、保存と読み込み、IaC 管理の判定 | US3.1 |
| 影響分析 | IAM ポリシーとリソースポリシーの読み込みと、条件の照合 | US3.2 |
| 書き換え | apply と rollback によるタグの書き換え | US4.1、US4.2、US5.1 |
| 記録 | 書き換える前後の状態の記録、同時実行の防止 | US4.2、US5.1 |
| IaC への反映 | Terraform、CloudFormation、CDK への書き戻し、プルリクエスト(第3弾) | US7.1〜US7.3 |

B. 粗めに分ける(4個程度): CLI と表示、収集、分析(ルール、変更案、影響分析)、書き換え(書き換えと記録)
C. Not yet defined
X. Other (please specify)

B. 変更案の部品の中に含める
C. Not yet defined

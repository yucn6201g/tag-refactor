# Bolt の計画: tag-refactor

Bolt は、作業の一部を設計から実装まで一通り作り、動くものができるところまで進める1回分の作業です。この計画では、1つの Bolt に1つの作業単位(Unit)を入れ、U1 から U8 まで8つの Bolt を順番に進めます(`delivery-planning-questions.md` Q3、Q4)。

出典: `inception/units-generation/unit-of-work.md`、`unit-of-work-dependency.md`、`unit-of-work-story-map.md`、`inception/contract-design/contract-summary.md`、`inception/practices-discovery/team-practices.md`、チームの進め方(`aidlc/spaces/default/memory/team.md`)。

## 進め方の決まり

| 項目 | 決まり | 出典 |
|---|---|---|
| ブランチ | Bolt ごとに `main` から短命なブランチを作り、GitHub に push する | team.md §Way of Working |
| マージ | Bolt ごとにプルリクエストを1つ作り、CI(Linux、macOS、Windows のテスト、golangci-lint、govulncheck)が通ったら `main` に squash マージする。1つの Bolt が `main` の1つのコミットになる | team.md §Way of Working、Q3 |
| コミットメッセージ | Conventional Commits(例: `feat(scan): ...`) | team.md §Way of Working |
| 同時に進めるか | 1つずつ順番に進める(ワークフローの設定 `unit-major`、`serial`) | Q4、Q8 |
| 作業単位の中の順番 | 受け入れ条件(Given/When/Then)のテスト → 実装 → 細かい単体テスト → すべてのテストの実行 | team.md §Testing Posture |
| 完成の確認 | Bolt ごとに、人が承認した Construction 検証コマンドを実行し、チェックポイントで人が承認する。コマンドは U1 の完成時に決める | team.md §Walking Skeleton、Q7 |

要件の未決事項 OQ4(AI-DLC の作業のまとまりと、プルリクエストでのマージのつなぎ方)は、上の「ブランチ」と「マージ」の決まりで答えます。

| 順 | Bolt | 作業単位 | 段階 | 最小の一本 | 主なストーリー |
|---|---|---|---|---|---|
| 1 | B1 | U1 最小の一本(u1-walking-skeleton) | 第1弾 | はい | US1.1、US3.1、US3.2 の最小版 |
| 2 | B2 | U2 収集(u2-scan) | 第1弾 | — | US1.1、US1.2 |

この順番は、作業単位の依存関係(U1 → U2・U3 → U4 → U5 → U6 → U7、U4 → U8)を守っています。順番の理由は `risk-and-sequencing-rationale.md` にあります。

**エンジンが作る順番との関係:** AI-DLC のエンジンは、この表ではなく `unit-of-work-dependency.md` の依存関係から、次に作る作業単位を決めます。U2 と U3 は、どちらも U1 だけに依存するため、エンジンがどちらを先に選ぶかは依存関係からは決まりません。この計画では U2 を先にしたいので、U3 を先に提示された場合は、その場で U2 を先にするよう求めます。

## B1: 最小の一本(U1)

最小の一本(walking skeleton)は、端から端まで動く最小版のことです。本格的な機能を入れる前に、部品同士がつながることを確かめます。

- **作業単位:** U1(u1-walking-skeleton)
- **確かめる部分:** Cli → AwsAccess → Inventory → RuleEngine → Planner → ImpactAnalyzer → Display の、すべての部品の境目。加えて、ビルド、テスト、lint、CI の仕組み
- **完成の条件:**
  - `tag-refactor scan` が、検証用アカウントの1つのリージョンのリソースとタグを読み取り、表にして標準出力に出す
  - `tag-refactor plan --rules <file>` が、ルールファイルのキーの別名からキー名の変更の変更案を作り、IAM の管理ポリシーの条件キーとの照合の結果を表に出す
  - 終了コード(0、1、2)と、標準出力・標準エラーの分け方が、契約 C5 のとおり
  - 契約 C6、C7、C9、C11、C12 のインターフェースが、最小版として定義されている(後の作業単位が中身を足せる)
  - CI が Linux、macOS、Windows でテスト、golangci-lint、govulncheck を実行して通る。カバレッジは80%以上
  - 人が承認した検証コマンドで、検証用アカウントを実際に呼んで動く
- **確かめたいこと(仮説):** 決めた部品の分け方と Go のインターフェースで、AWS の読み取りから変更案と影響の表示まで、無理なくつながる。CI の3つの OS で同じように動く
- **見せるもの:** 検証用アカウントに対して `scan` と `plan` を実行し、表と終了コードを見せる。プルリクエストの CI が3つの OS で通っている画面
- **前提:** 開発用の道具、検証用アカウントと認証情報、IAM の管理ポリシーの確認用の例(`external-dependency-map.md` の E1、E2、E4)
- **決めること:** Construction 検証コマンド(このチェックポイントで提案する)、オプション名(scan、plan)、Go の最小バージョン(要件 OQ2)

## B2: 収集(U2)

- **作業単位:** U2(u2-scan)
- **完成の条件:**
  - 1アカウントの全リージョンを読み、読めなかったリージョンを記録する
  - 一度もタグが付いていないリソースを、AWS Config か Resource Explorer で探す。使えない場合は理由を出し、それだけでは終了コードを 1 にしない
  - グローバルなリソースを1回だけ数え、タグを変更できない種類と件数を出す
  - AwsAccess の時間の上限、再試行、呼び出し回数の上限への対応、権限不足の案内(足りない API の名前)
  - 進み具合を標準エラーに出す(端末と、端末でない場合)
- **確かめたいこと(仮説):** 1万件のリソースを10分以内に読める。AWS の呼び出し回数の上限に当たっても、再試行で最後まで読める
- **見せるもの:** 検証用アカウントの全リージョンに対する `scan`。性能の確認は、AWS の呼び出しを差し替えた1万件の模擬データで測る
- **前提:** AWS Config か Resource Explorer の有効化(E3)
- **決めること:** 一度もタグが付いていないリソースを探すときの件数の上限(要件 OQ5、契約の未決事項)、グローバルなリソースのリージョン

## B3: ルール(U3)

- **作業単位:** U3(u3-rules)
- **完成の条件:**
  - ルールファイル(契約 C1)のすべての項目を読み、誤りを行番号、キー、直し方とともに知らせる。知らないキーは誤りにする
  - `aws:` で始まるキーを無視して警告する
  - `rules suggest` が、収集の結果から表記ゆれの候補(略語の辞書、大文字と小文字、区切り文字)を含む下書きを出す
- **確かめたいこと(仮説):** 利用者が書くルールファイルの誤りを、利用者が自分で直せる案内で知らせられる。表記ゆれの候補が、手で直す手間を減らす
- **見せるもの:** 誤りを含むルールファイルでの案内と、`rules suggest` の下書き
- **前提:** なし(AWS を呼ばない)
- **決めること:** 条件ごとの値が複数当てはまる場合の規則(契約の未決事項)

## B4: 変更案(U4)

- **作業単位:** U4(u4-plan)
- **完成の条件:**
  - 4種類の変更(キー名の変更、値の変更、必須タグの追加、キーの削除)、値が未指定の必須タグ、消す候補、IaC の警告
  - 一覧、差分、JSON、Markdown の4つの形式で、件数が一致する。英語と日本語、色と `NO_COLOR`
  - 変更案を保存し(契約 C2)、読み込める。読めない `version` は止める
  - 影響分析のインターフェース(契約 C9)を定義する
- **確かめたいこと(仮説):** 利用者が、変更案を読んで「何がどう変わるか」を判断できる。保存した変更案が、後の apply と IaC への反映に必要な情報をすべて持つ
- **見せるもの:** 検証用アカウントに対する `plan` の4つの形式と、保存した変更案のファイル
- **前提:** なし(B1 で用意したものを使う)
- **決めること:** Markdown 出力の詳しい形(契約の未決事項)

## B5: 影響分析(U5)

- **作業単位:** U5(u5-impact)
- **完成の条件:**
  - IAM のユーザー・ロール・グループのポリシーと、S3・KMS・SQS・SNS・Secrets Manager のリソースポリシーを読む
  - タグに関する条件キーのすべての種類を照合し、キー名・値・削除の影響を `affected` か `undecided` に分ける
  - 読めなかったポリシーを記録し、影響分析が不完全であることを示す
  - テスト用のポリシーの集まりで、検出率100%(NFR2)を確かめる
- **確かめたいこと(仮説):** タグの変更で壊れるポリシーの参照を、見逃さずに見つけられる。判定できない条件を「影響なし」と誤って示さない
- **見せるもの:** 検証用アカウントの確認用ポリシーに対する `plan` の影響の表示。テスト用ポリシーの集まりに対する検出の結果
- **前提:** 検証用アカウントの確認用リソースとポリシー(E4)
- **この Bolt の後:** 第1弾が完成します。配布の仕組みを別の作業として作り、`vX.Y.Z` のタグ(`v0.1.0`)を人が付けて公開します(`external-dependency-map.md` の E6)

## B6: 書き換えと記録(U6)

- **作業単位:** U6(u6-apply)
- **完成の条件:**
  - 確認画面で影響のある変更を強調し、人が承認してから書き換える。`--yes` だけのときは、影響のある変更があれば止める(`--allow-impact` を併せて付けたときだけ進める)
  - 変更案のアカウントと今のアカウントが違えば止める。変更案の作成後にタグが変わっていたリソースは飛ばす
  - 書き換えの前に記録(契約 C4)を保存し、保存に失敗したら何も書き換えない。一部が失敗しても、他のリソースの結果を記録する
  - `aws:` のタグを変えない。タグ数の上限を超える変更を事前に止める
  - apply と rollback の同時実行を防ぐ
- **確かめたいこと(仮説):** 本番のタグを書き換えても、途中で止まった場合を含めて、何が起きたかが記録に残り、被害を広げない
- **見せるもの:** 検証用アカウントでの `apply`(確認画面、影響での停止、途中の失敗)
- **前提:** 検証用アカウントの確認用リソース(E4)
- **決めること:** 記録の既定の保存先、S3 の場合の同時実行の防ぎ方、オプション名(apply)

## B7: 取り消し(U7)

- **作業単位:** U7(u7-rollback)
- **完成の条件:**
  - 記録を読み、アカウントが違えば止める
  - 契約 C4 の判定の表のとおり、この apply が書いたリソースを元に戻し、後から変えられたリソースは飛ばす(`--force` で上書き)
  - 途中で止まった apply(中間の状態を含む)を戻せる。二重の rollback では何もしない
- **確かめたいこと(仮説):** apply の結果を、他の人の後からの変更を壊さずに元に戻せる
- **見せるもの:** 検証用アカウントでの `apply` → 手で一部のタグを変える → `rollback` の流れ
- **前提:** 検証用アカウントの確認用リソース(E4)
- **決めること:** オプション名(rollback)

## B8: IaC への反映(U8)

- **作業単位:** U8(u8-iac)
- **完成の条件:** 第3弾に取りかかる前の設計(要件 OQ3)で決めます。今わかっている範囲では、Terraform と CloudFormation への反映(Should)、CDK(TypeScript、Python)への反映とプルリクエストの作成(Could)です。
- **確かめたいこと(仮説):** 保存した変更案から、IaC のソースを、書式を壊さずに書き換えられる
- **見せるもの:** 確認用の Terraform と CloudFormation のソースへの反映の差分
- **前提:** 要件 OQ3 の設計。契約 C2 に追加の項目が必要か(契約の未決事項)

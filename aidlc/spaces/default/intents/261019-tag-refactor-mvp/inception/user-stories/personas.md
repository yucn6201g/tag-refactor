# ペルソナ: tag-refactor

出典: `ideation/intent-capture/intent-statement.md` §対象となる利用者、`ideation/intent-capture/stakeholder-map.md`、`user-stories-questions.md` Q1

## P1. 社内の担当者「佐藤さん」

| 項目 | 内容 |
|---|---|
| 役割 | 社内のプラットフォーム、FinOps、セキュリティのいずれかの担当者。会社の AWS アカウントのタグを整える責任がある |
| 目標 | ・本番環境を壊さずにタグを統一する<br>・コスト配分を正確にする<br>・タグ整理にかかる作業時間を減らす<br>・監査やコンプライアンスで、変更の記録を示せるようにする |
| 困っていること | ・`env` と `Environment` のような表記ゆれで、コストのレポートが分かれてしまう<br>・キー名を変えると IAM の条件などが壊れそうで、手を付けられない<br>・必須のタグが付いていないリソースがあり、持ち主が分からない |
| 技術への慣れ | 高い(AWS のコンソールと CLI を日常的に使う) |
| 使う頻度 | タグを整理するとき(月に数回程度を想定) |
| 重視すること | 安全性(壊さない、戻せる)を最も重視する |

## P2. OSS の利用者「Alex さん」

| 項目 | 内容 |
|---|---|
| 役割 | 自分や所属チームの AWS アカウントを管理している開発者。GitHub でこのツールを見つけて試す |
| 目標 | ・手間をかけずに導入して、自分のアカウントのタグの状態を知る<br>・書き込み権限を渡さずに、まず安全に試す<br>・自分の環境のリソースや参照元にも使えるか確かめる |
| 困っていること | ・既存のツールでは、タグを直したときに何が壊れるかを事前に確かめられない<br>・知らないツールに、いきなり書き込みの権限を渡したくない |
| 技術への慣れ | 高い |
| 使う頻度 | 最初は試しに1回。役に立てば定期的に使う |
| 重視すること | 導入の手軽さ(単一の実行ファイル、少ない設定)と、読み取りだけで試せること |

## ペルソナの関係と優先順位

- 2人とも同じコマンドを使い、求める振る舞いはほぼ共通です。違いは重視する点です。
- 優先順位は **P1 を主、P2 を従** とします。P1 の「本番を壊さない」は、P2 の「安全に試せる」も満たすためです。
- P2 は、最初の利用で読み取りのコマンド(scan、plan)だけを使うことが多いと想定します。そのため、読み取りのコマンドの導入のしやすさと、権限の案内は P2 のストーリーとして扱います。

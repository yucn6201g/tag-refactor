## グループ1: 調べる(scan)

### US1.1 アカウント全体のタグの問題を一覧にする

**P1(佐藤さん)として、1つの AWS アカウントの全リージョンのタグを調べ、表記ゆれと必須タグの欠落を件数つきで一覧にしたい。それは、どこから手を付ければよいかを判断するためだ。**

- 優先度: Must(第1弾)
- 要件: FR1.1〜FR1.8、NFR1、NFR5
- 依存: なし(すべての土台)

| ID | 受け入れ条件 |
|---|---|
| AC1.1.1 | **Given** アカウントの有効なリージョンが17個ある **When** `scan` を実行する **Then** 17個のリージョンすべてが調べられ、調べたリージョンの数が表示される(FR1.1) |
| AC1.1.2 | **Given** 一度もタグが付いたことのないリソースがあり、AWS Config か Resource Explorer が有効である **When** `scan` を実行する **Then** そのリソースも結果に含まれる(FR1.2) |
| AC1.1.3 | **Given** AWS Config も Resource Explorer も無効である **When** `scan` を実行する **Then** 「一度もタグが付いたことのないリソースは見つけられなかった」ことと理由が表示され、残りの結果は表示される(FR1.3) |
| AC1.1.4 | **Given** `scan` を実行している **When** リージョンを調べている間 **Then** リージョンごとの状態(済み、実行中、待ち)と経過時間が標準エラーに表示される(FR1.4) |
| AC1.1.5 | **Given** 1つのリージョンで読み取りが拒否される **When** `scan` を実行する **Then** そのリージョン名と理由が結果の先頭に示され、「結果は不完全」と表示される(FR1.5) |
| AC1.1.6 | **Given** `env`、`Env`、`environment` というキーが付いたリソースがある **When** `scan` を実行する **Then** 3つのキーが1つのグループとして、それぞれの件数とともに表示される(FR1.6) |
| AC1.1.7 | **Given** ルールファイルで `Owner` を必須にしている **When** `scan` を実行する **Then** `Owner` が付いていないリソースの件数が表示され、テストデータの件数と一致する(FR1.7) |
| AC1.1.8 | **Given** 問題のないリソースだけがある **When** `scan` を実行する **Then** 「問題なし」と、調べたリソースの件数が表示される(FR1.8) |
| AC1.1.9 | **Given** 全リージョンに合わせて10,000件のリソースがある **When** `scan` と `plan` を続けて実行する **Then** 合わせて10分以内に終わる(NFR1) |
| AC1.1.10 | **Given** AWS が呼び出し回数の上限を返す **When** `scan` を実行する **Then** 待ってから再試行し、処理が最後まで終わる(NFR5) |

### US1.2 読み取りの権限だけで安全に試す

**P2(Alex さん)として、書き込みの権限を渡さずに scan と plan を試したい。それは、知らないツールでも自分の環境を壊す心配なく、役に立つかを確かめるためだ。**

- 優先度: Must(第1弾)
- 要件: FR7.6、FR7.7、FR7.8、NFR3、NFR8
- 依存: なし

| ID | 受け入れ条件 |
|---|---|
| AC1.2.1 | **Given** ドキュメントにある読み取り用の IAM ポリシーだけを付けている **When** `scan`、`rules suggest`、`plan` を実行する **Then** 3つとも権限のエラーなく動き、書き込みの API は1回も呼ばれない(NFR3) |
| AC1.2.2 | **Given** 必要な読み取り権限の一部がない **When** `scan` を実行する **Then** 足りない操作(API)の名前が表示される(FR7.7) |
| AC1.2.3 | **Given** AWS の認証情報が設定されていない **When** 任意のサブコマンドを実行する **Then** 何が足りないかと設定方法が表示され、終了コードは1になる(FR7.8) |
| AC1.2.4 | **Given** `--profile` で特定のプロファイルを指定している **When** `scan` を実行する **Then** そのプロファイルの認証情報とリージョンが使われる(FR7.6) |
| AC1.2.5 | **Given** 任意のサブコマンドを実行した **When** 標準出力、標準エラー、ログを確かめる **Then** 認証情報(アクセスキー、シークレット、セッショントークン)はどこにも含まれない(NFR8) |

## グループ2: 基準を決める(rules)

### US2.1 統一の基準をルールファイルにする

**P1(佐藤さん)として、既存のタグから正しいキー名や値の候補を出してもらい、それを直してルールファイルにしたい。それは、統一の基準を一から考えずに、短い時間で決めるためだ。**

- 優先度: Must(第1弾)
- 要件: FR2.1〜FR2.5
- 依存: US1.1(タグの収集を使う)

| ID | 受け入れ条件 |
|---|---|
| AC2.1.1 | **Given** 表記ゆれのあるタグがある **When** `rules suggest` を実行する **Then** 正しいキー名・値の候補と別名を含むルールファイルの下書きが標準出力に出て、その下書きをそのまま読み込める(FR2.1、FR2.2) |
| AC2.1.2 | **Given** ルールファイルで `env` を `Environment` の別名にしている **When** `plan` を実行する **Then** `env` は `Environment` へのキー名の変更として扱われる(FR2.2) |
| AC2.1.3 | **Given** `Owner` の固定値と、リソースの種類が EC2 のときの値の両方を指定している **When** EC2 のリソースで `plan` を実行する **Then** リソースの種類の条件の値が使われる(FR2.3) |
| AC2.1.4 | **Given** ルールファイルで消すキー `tmp-owner` を指定している **When** `plan` を実行する **Then** `tmp-owner` だけが削除として扱われる(FR2.4) |
| AC2.1.5 | **Given** 書式の誤ったルールファイル **When** `plan` を実行する **Then** 誤りの行番号とキーと直し方が表示され、終了コードは1になる(FR2.5) |

## グループ3: 確かめる(plan)

### US3.1 変更案を確かめる

**P1(佐藤さん)として、ルールファイルに沿った変更案を、件数や形式を選んで確かめたい。それは、どのリソースがどう変わるかを、書き換える前にチームで確認するためだ。**

- 優先度: Must(第1弾)
- 要件: FR3.1〜FR3.7、FR7.5
- 依存: US2.1

| ID | 受け入れ条件 |
|---|---|
| AC3.1.1 | **Given** キー名の変更、値の変更、必須タグの追加、削除のすべてが起こるルールとタグ **When** `plan` を実行する **Then** 4種類の変更が、それぞれ正しい件数で表示される(FR3.1) |
| AC3.1.2 | **Given** 1つのリソースにキー名の変更と値の変更が重なる **When** `plan` を実行する **Then** 変更されるリソースの総数で、そのリソースは1件と数えられる(FR3.2) |
| AC3.1.3 | **Given** どの条件にも当てはまらず、必須タグの値が決まらないリソースがある **When** `plan` を実行する **Then** そのリソースは「値が未指定」に表示され、そのリソースの他の変更は変更案に残る(FR3.3) |
| AC3.1.4 | **Given** ルールファイルにないキーが付いたリソースがある **When** `plan` を実行する **Then** そのキーは「消す候補」に表示され、削除の変更案には入らない(FR3.4) |
| AC3.1.5 | **Given** 同じルールとタグ **When** 一覧、差分、JSON、Markdown の4つの形式で `plan` を出力する **Then** 4つの形式で変更の件数と影響の件数が一致する(FR3.5) |
| AC3.1.6 | **Given** `plan` の結果をファイルに保存した **When** 保存したファイルを確かめる **Then** 作成日時、アカウント、変更前のタグ、変更内容が含まれている(FR3.6) |
| AC3.1.7 | **Given** CloudFormation で作ったリソースが変更の対象に含まれる **When** `plan` を実行する **Then** そのリソースに「IaC で管理されている」と警告が表示される(FR3.7) |
| AC3.1.8 | **Given** `plan` の結果を標準出力からファイルに保存する **When** ファイルを確かめる **Then** 進み具合や案内のメッセージが混ざっていない(FR7.5) |

### US3.2 変更で壊れる参照元を事前に知る

**P1(佐藤さん)として、変更案のどの変更が IAM ポリシーやリソースポリシーの条件に影響するかを、書き換える前に知りたい。それは、権限やアクセス制御を壊さずにタグを変えるためだ。**

- 優先度: Must(第1弾)
- 要件: FR4.1〜FR4.7、FR3.8、NFR2
- 依存: US3.1

| ID | 受け入れ条件 |
|---|---|
| AC3.2.1 | **Given** IAM のロールに付いたポリシーが、条件で `env` のタグを使っている **When** `env` を `Environment` に変える `plan` を実行する **Then** そのポリシーが影響あり(`!`)として、ポリシー名、ステートメント、条件とともに表示される(FR4.1、FR4.6) |
| AC3.2.2 | **Given** S3 バケットのポリシーが、条件でタグの値 `Prod` を使っている **When** `Prod` を `prod` に変える `plan` を実行する **Then** そのバケットポリシーが影響ありとして表示される(FR4.2、FR4.3) |
| AC3.2.3 | **Given** ポリシーの条件がタグを消すと成り立たなくなる **When** そのタグを消す `plan` を実行する **Then** そのポリシーが影響ありとして表示される(FR4.3) |
| AC3.2.4 | **Given** ポリシーの条件がワイルドカードやポリシー変数を含む **When** `plan` を実行する **Then** その条件は「判定できない」(`?`)として表示され、影響なしとは表示されない(FR4.5) |
| AC3.2.5 | **Given** ポリシーを読む権限がない **When** `plan` を実行する **Then** 読めなかったポリシーの種類と理由が示され、「影響分析は不完全」と表示される(FR4.7) |
| AC3.2.6 | **Given** IAM ポリシーとリソースポリシー(S3、KMS、SQS、SNS、Secrets Manager)と、タグの条件キーのすべての種類を組み合わせたテスト用の参照 **When** 影響分析を実行する **Then** テスト用の参照が100%検出される(FR4.4、NFR2) |

## グループ4: 書き換える(apply)

### US4.1 確認してからタグを書き換える

**P1(佐藤さん)として、変更の要約と影響を確認してから、変更案どおりにタグを書き換えたい。それは、意図しない変更を防ぎつつ、手作業より速く統一するためだ。**

- 優先度: Must(第2弾)
- 要件: FR5.1〜FR5.5、FR5.11
- 依存: US3.1、US3.2

| ID | 受け入れ条件 |
|---|---|
| AC4.1.1 | **Given** 変更案がある **When** `apply` を実行し、確認で `yes` 以外を入力する **Then** 何も書き換えずに終了する(FR5.1) |
| AC4.1.2 | **Given** 保存した変更案のファイル **When** そのファイルを指定して `apply` を実行し、`yes` と入力する **Then** ファイルの内容どおりにタグが書き換えられる(FR5.2) |
| AC4.1.3 | **Given** 影響のない変更だけの変更案 **When** 確認を省くオプションで `apply` を実行する **Then** 確認の入力なしで書き換えられる(FR5.3) |
| AC4.1.4 | **Given** 影響のある変更を含む変更案 **When** `apply` を実行する **Then** 確認画面で影響のある変更が記号と文字で示され、`yes` の入力で書き換えられる(FR5.4) |
| AC4.1.5 | **Given** 影響のある変更を含む変更案 **When** 確認を省くオプションだけで `apply` を実行する **Then** 何も書き換えずに止まり、終了コードは2になる(FR5.5) |
| AC4.1.6 | **Given** 影響のある変更を含む変更案 **When** 確認を省くオプションと、影響を承知で進めるオプションを付けて `apply` を実行する **Then** 書き換えられる(FR5.5) |
| AC4.1.7 | **Given** `apply` が終わった **When** 結果を見る **Then** 実行IDつきの取り消しのコマンドが表示され、そのコマンドで rollback できる(FR5.11) |

### US4.2 書き換えの途中の問題で被害を広げない

**P1(佐藤さん)として、書き換えの途中で一部が失敗したり、状況が変わっていたりしても、被害を広げずに結果を把握したい。それは、本番環境で安心して apply を使うためだ。**

- 優先度: Must(第2弾)
- 要件: FR5.6〜FR5.10、NFR6、NFR7
- 依存: US4.1

| ID | 受け入れ条件 |
|---|---|
| AC4.2.1 | **Given** 変更案を保存した後に、対象のリソースのタグを手で変えた **When** 保存した変更案で `apply` を実行する **Then** そのリソースは書き換えられずに飛ばされ、最後に一覧で示される(FR5.6) |
| AC4.2.2 | **Given** 書き換える権限のないリソースが含まれる **When** `apply` を実行する **Then** 残りのリソースは書き換えられ、成功と失敗の件数と一覧が表示され、失敗の詳細がログファイルに残る(FR5.7) |
| AC4.2.3 | **Given** `apply` を実行する **When** 最初のタグを書き換える前 **Then** 書き換える前のタグの状態が、既定では手元のファイルに、指定すれば S3 バケットに記録されている(FR5.8) |
| AC4.2.4 | **Given** `aws:` で始まるタグを対象にしたルール **When** `apply` を実行する **Then** `aws:` で始まるタグは変更されない(FR5.9) |
| AC4.2.5 | **Given** 書き換えるとタグの上限数を超えるリソース **When** `apply` を実行する **Then** そのリソースは書き換えられず、理由とともに一覧に示される(FR5.10) |
| AC4.2.6 | **Given** 記録の保存中に処理を強制的に止めた **When** 記録のファイルを確かめる **Then** 記録は壊れていない(NFR6) |
| AC4.2.7 | **Given** 同じアカウントで2つの `apply` を同時に実行する **When** 両方が終わる **Then** どちらの記録も壊れていない(NFR7) |

## グループ5: 戻す(rollback)

### US5.1 書き換えを元に戻す

**P1(佐藤さん)として、apply で書き換えたタグを、実行IDを指定して元に戻したい。それは、問題が起きたときにすぐに元の状態に戻せるようにするためだ。**

- 優先度: Must(第2弾)
- 要件: FR6.1〜FR6.5、NFR4
- 依存: US4.1、US4.2

| ID | 受け入れ条件 |
|---|---|
| AC5.1.1 | **Given** `apply` を実行し、その後に別の変更が入っていない **When** その実行IDで `rollback` を実行し、`yes` と入力する **Then** 対象のリソースのタグが apply の前と完全に一致する(差分0)(FR6.1、NFR4) |
| AC5.1.2 | **Given** `rollback` を実行する **When** 確認画面で `yes` 以外を入力する **Then** 何も戻さずに終了する(FR6.2) |
| AC5.1.3 | **Given** apply の後に、対象のリソースのタグを手で変えた **When** 既定の設定で `rollback` を実行する **Then** そのリソースは戻されずに飛ばされ、一覧で示される(FR6.3) |
| AC5.1.4 | **Given** AC5.1.3 と同じ状態 **When** 上書きのオプションを付けて `rollback` を実行する **Then** そのリソースも記録した状態に戻される(FR6.3) |
| AC5.1.5 | **Given** `rollback` が終わった **When** 結果を見る **Then** 戻した件数、飛ばした件数、失敗した件数が表示される(FR6.4) |
| AC5.1.6 | **Given** `apply` を途中で強制終了した **When** その実行IDで `rollback` を実行する **Then** 書き換えた分だけが記録した状態に戻される(FR6.5) |

## グループ6: コマンド全体

### US6.1 自分の環境に合った表示で使う

**P2(Alex さん)として、自分の言語や端末の設定に合った表示で、スクリプトからも扱いやすい形でツールを使いたい。それは、日常の作業や自分のスクリプトに無理なく組み込むためだ。**

- 優先度: Must(第1弾)
- 要件: FR7.1〜FR7.5、NFR11
- 依存: なし

| ID | 受け入れ条件 |
|---|---|
| AC6.1.1 | **Given** ツールを入れた **When** 各サブコマンドのヘルプを表示する **Then** `scan`、`rules suggest`、`plan`、`apply`、`rollback` のヘルプが表示される(FR7.1) |
| AC6.1.2 | **Given** OS の言語設定が日本語 **When** 言語の設定なしで `scan` を実行する **Then** 日本語で表示される。日本語でも英語でもない言語設定では英語で表示される(FR7.2) |
| AC6.1.3 | **Given** `NO_COLOR` 環境変数を設定している **When** `plan` を実行する **Then** 色は出ず、変更の種類と影響は記号と文字で分かる(FR7.3、NFR11) |
| AC6.1.4 | **Given** `scan` で問題が見つかった **When** 終了コードを確かめる **Then** 2になる。問題がなければ0、エラーなら1になる(FR7.4) |
| AC6.1.5 | **Given** `scan` の結果を JSON で標準出力に出す **When** 標準出力だけを読む **Then** 正しい JSON として読める(進み具合のメッセージは標準エラーに出る)(FR7.5) |

### US6.2 手軽に入手して使い始める

**P2(Alex さん)として、自分の OS で、追加の準備なしにツールを入手して実行したい。それは、試すまでの手間を最小にするためだ。**

- 優先度: Must(第1弾の公開 `v0.1.0` まで)
- 要件: NFR9、NFR12
- 依存: なし

| ID | 受け入れ条件 |
|---|---|
| AC6.2.1 | **Given** Linux、macOS、Windows のいずれか **When** GitHub Releases からその OS 用の実行ファイルを入手して実行する **Then** 追加のランタイムなしで動く(NFR9、NFR12) |
| AC6.2.2 | **Given** Go の開発環境がある **When** `go install` でツールを入れる **Then** ツールが実行できる(NFR12) |
| AC6.2.3 | **Given** GitHub Releases の公開物 **When** 中身を確かめる **Then** 実行ファイルのチェックサムのファイルが含まれ、ダウンロードした実行ファイルのチェックサムと一致する(NFR12) |

## グループ7: IaC に反映する(第3弾・大まかなストーリー)

第3弾の詳しい振る舞いは未決です(要件定義の OQ3)。ここでは大まかなストーリーだけを置き、受け入れ条件は第3弾に取りかかる前に詳しくします(Q4)。

### US7.1 タグの変更を IaC に反映する

**P1(佐藤さん)として、apply したタグの変更を Terraform の設定と CloudFormation のテンプレートに反映したい。それは、次に IaC を適用したときにタグが元に戻されないようにするためだ。**

- 優先度: Should(第3弾)
- 要件: FR8.1、FR8.2
- 依存: US3.1

| ID | 受け入れ条件(大まかなもの) |
|---|---|
| AC7.1.1 | **Given** Terraform で管理されたリソースを含む変更案 **When** IaC への反映を実行する **Then** Terraform の設定ファイルが、変更後のタグを表すように書き換えられる(FR8.1) |
| AC7.1.2 | **Given** CloudFormation で管理されたリソースを含む変更案 **When** IaC への反映を実行する **Then** テンプレートが、変更後のタグを表すように書き換えられる(FR8.2) |

### US7.2 タグの変更を CDK のソースに反映する

**P1(佐藤さん)として、CDK(TypeScript、Python)で作ったリソースのタグの変更を、CDK のソースに反映したい。それは、CDK を使っているチームでも変更が元に戻されないようにするためだ。**

- 優先度: Could(第3弾)
- 要件: FR8.3
- 依存: US3.1

| ID | 受け入れ条件(大まかなもの) |
|---|---|
| AC7.2.1 | **Given** CDK(TypeScript または Python)で作ったリソースを含む変更案 **When** IaC への反映を実行する **Then** CDK のソースが、変更後のタグを表すように書き換えられる(FR8.3) |

### US7.3 IaC の修正をプルリクエストで出す

**P1(佐藤さん)として、IaC の修正を GitHub のプルリクエストとして出したい。それは、チームのレビューを通して IaC の変更を取り込むためだ。**

- 優先度: Could(第3弾)
- 要件: FR8.4
- 依存: US7.1 または US7.2

| ID | 受け入れ条件(大まかなもの) |
|---|---|
| AC7.3.1 | **Given** IaC の修正がある **When** プルリクエストの作成を実行する **Then** 修正を含むプルリクエストが GitHub に作られる(FR8.4) |

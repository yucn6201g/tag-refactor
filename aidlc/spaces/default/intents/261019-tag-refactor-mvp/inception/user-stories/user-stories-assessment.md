# ユーザーストーリーの要否の評価: tag-refactor

## 判断

**作成する(Execute)**

## 理由

- **利用者に直接見える機能が中心である。** scan、plan、apply、rollback はすべて利用者が端末で操作し、結果を読んで判断する機能です(`requirements.md` FR1〜FR7)。利用者が何を見て、どう判断するかを、受け入れ条件として具体的に決める価値があります。
- **利用者が2種類いる。** 社内の担当チームと、OSS の外部利用者で、期待することが違います(`ideation/intent-capture/intent-statement.md` §対象となる利用者)。前者は本番を壊さないことやコスト配分の正確さを、後者は導入の手軽さや書き込み権限なしで試せることを重視します。
- **判断の分かれ目が多い。** 影響のある変更をどう扱うか(FR5.4、FR5.5)、後から変わったリソースをどう扱うか(FR5.6、FR6.3)など、場面ごとの振る舞いが細かく決まっています。これを Given/When/Then の受け入れ条件にすることで、チームの進め方(受け入れ条件を先にテストにする)にそのまま使えます(`team-practices.md` §Testing Posture)。

## 考慮した点

| 観点 | 評価 |
|---|---|
| プロジェクトの種類 | 新規開発の CLI ツール |
| 利用者に見える範囲 | 広い(すべてのサブコマンドの出力と確認画面) |
| 複雑さ | 中〜高(ポリシーの条件の解析、書き換えと取り消しの安全性) |
| チームの進め方との関係 | 受け入れ条件を先に自動テストにする進め方のため、ストーリーの受け入れ条件がテストの元になる |

## ストーリーが最も役に立つ部分

1. plan の影響分析で、利用者が何を見て変更を判断できるか
2. apply と rollback で、本番を壊さないための確認と取り消しの流れ
3. 権限が足りない、一部が失敗したなどの、うまくいかなかった場面の振る舞い

# 制約の一覧: tag-refactor

出典の書き方は feasibility-assessment.md と同じです(「意図 §…」は intent-statement.md、「F-Q…」はこのステージの回答)。

## 技術的な制約

| ID | 制約 | 影響 | 出典 |
|---|---|---|---|
| C-T1 | 実装言語は Go を使う | ツールは単一のバイナリで配れる。一方、CDK の TypeScript や Python のソースを直すには、Go 以外の仕組みが必要になる見込み | F-Q3、F-Q9 |
| C-T2 | 対象は1アカウントのみ。複数アカウント(Organizations)の横断はしない | SCP と RCP は影響分析の対象外になる | 意図 §最初のバージョンに含めないもの、F-Q7 |
| C-T3 | 影響分析の対象は、IAMポリシー(ユーザー・ロール・グループ)とリソースポリシー(S3、KMS、SQS、SNS、Secrets Manager など)の条件キー | AWS Backup、DLM、SSM、Resource Groups、Auto Scaling のタグ指定は、最初のバージョンでは調べない | 意図 §成功の基準、F-Q7 |
| C-T4 | IaCへの書き戻しは Terraform、CloudFormation、CDK(TypeScript と Python)に対応する | 3種類・4つの書式を直す仕組みが必要 | F-Q8、F-Q9 |
| C-T5 | IaCの修正は GitHub のプルリクエストとして出せる | 利用者の GitHub の認証情報を扱う必要がある | F-Q1 |
| C-T6 | 性能目標: 1アカウント・全リージョン・10,000リソースで、scan と plan が合わせて10分以内 | APIの呼び出し回数の上限の中で、並行して処理する必要がある | 意図 §成功の基準 |
| C-T7 | 影響を受ける参照元は、テスト用に用意した参照の検出率100%で示す | 判定できない条件(ワイルドカードなど)は、「判定できない」と明示する必要がある | 意図 §成功の基準 |

## 組織上の制約

| ID | 制約 | 影響 | 出典 |
|---|---|---|---|
| C-O1 | 開発は依頼者1人で、範囲や優先順位も1人で決める | 作業量の大きい機能は、順番を決めて進める必要がある | 意図 §関係者 |
| C-O2 | 期限は決めない | 期限による範囲の削減は起きないが、完成時期の見通しが立てにくい | F-Q4 |
| C-O3 | 組織上の制約はない | — | F-Q5 |
| C-O4 | 検証に使えるのは個人の検証用アカウントだけ | 大量のリソースを使う性能試験や、本番に近い環境での試験は難しい | F-Q6 |

# チームの進め方: tag-refactor

## Way of Working

私たちはトランクベース開発で進めます。

- すべての作業は、短命なブランチ(目安は1〜2日)を経由して `main` に統合します。`develop` やリリース用ブランチのような、長く残るブランチは作りません。
- Construction の作業ブランチ(worktree)は、GitHub の最新の `main` から作り、`main` に戻します。手元の `main` が古いままのことがあるので、作る前に GitHub の `main` に合わせます。
- ブランチは GitHub に push し、プルリクエストで `main` に squash マージします。マージの前に CI を実行し、CI(必須のチェック `ci-gate`)が通ったものだけをマージします。
- GitHub の設定でもこれを守ります。マージの方法は squash だけを許し、`main` への直接の push、強制の push、削除を禁じ、`ci-gate` の成功を必須にします。マージしたブランチは自動で消します。
- 開発は1人なので、プルリクエストのレビューの承認は必須にしません。
- 1つの Bolt は、`main` 上の1つのコミットになります。途中のコミットは `main` には残りませんが、AI-DLC の監査ログに作業の経過が残るので、この点は受け入れます。
- AI-DLC の記録(`aidlc/` の下)は、コードと同じブランチにコミットし、同じプルリクエストで `main` に入れます。
- コミットメッセージは Conventional Commits(`feat:`、`fix:` などの接頭辞)に従います。Dependabot のプルリクエストも、`chore(deps)` と `ci` の接頭辞を使います。
- リリースの区切りは、ブランチではなくタグ(`vX.Y.Z`)で表します。

## Walking Skeleton

私たちは、リリースの単位になる作業ごとに、最初に端から端まで動く最小の一本(walking skeleton)を作ります。最小の一本の中身と、それを確かめるコマンドは、作業ごとに決めます。

- 最初の Unit を、この最小の一本にします。後の Unit より先に、Code Generation まで作り切ります。ビルド、テスト、lint、CI の準備も、この一本に最初から含めます。
- 最小の一本が動いたことは、人が承認した Construction 検証コマンド(Construction Verification Command)で確かめます。このコマンドは、その作業で作るものが端から端まで実際に動くことを示すものにします。
- 検証のあと、最小の一本のチェックポイントで人の承認を得ます。設計段階のレビューを通っただけでは、最小の一本が動いたことにはしません。
- 最小の一本の承認後に、残りの Construction を自動で続けるか(`autonomous`)、チェックポイントごとに確認するか(`gated`)を選びます。
- これまでの記録: 第1弾(`v0.1.0`)の最小の一本は、`scan` の最小版(1つのリージョンのタグを読み取り、表にして出す)と、`plan`(影響分析)の最小版でした。検証コマンドは、個人の検証用 AWS アカウントを実際に呼びました(AWS の認証情報と少額の費用が要りました)。
- 第2弾(`v0.2.0`)の最小の一本は、CDK の反映とプルリクエストの作成の2つを細く通すものです。TypeScript の最小の CDK アプリを対象に、保存した変更案の1つのキー名の変更を、`cdk synth` で得たリソースとソースの対応を使ってソースに反映し、テスト専用のリポジトリにプルリクエストを作るところまでです。Python の CDK、ほかの書き方、ほかの種類の変更は、後の Unit で足します。CI の新しい準備(3つの OS への Node.js、Python、CDK の CLI の導入と、テスト専用のリポジトリのトークンの secret)も、この一本に最初から含めます。
- 第2弾の検証コマンドは、個人の検証用 AWS アカウントを使います。実際の AWS から `plan` で変更案を作り、その変更案で `iac --pr` を動かして、テスト専用のリポジトリにプルリクエストができることを確かめます。AWS の認証情報と少額の費用のほかに、手元の Node.js、CDK の CLI、`gh` と、テスト専用のリポジトリが要ります。

## Testing Posture

私たちはテストを、すべての Bolt で作る成果物の一部として扱います。

- **Methodology**: custom
- **Methodology evidence**: 前の作業(`261019-tag-refactor-mvp`)の面談で、テストの進め方の質問の回答は C(受け入れ条件(Given/When/Then)を先にテストにし、細かい単体テストは実装のあとに書く)でした。テストを先に書く部分と、実装のあとに書く部分が混ざっているため、`tdd`、`bdd`、`atdd`、`test-after` のどれにも当てはまらず、`custom` とします。コミットの履歴にも、`iac` の受け入れ条件のテストを実装の前に足したコミット(`2296959`)があり、この進め方が守られています。
- **Ordering**: まず受け入れ条件(Given/When/Then)を自動テストとして書き、次にそれを満たす実装を書き、実装のあとで細かい単体テストを書いて、すべてのテストを実行する。
- カバレッジの下限は80%です。Go の標準の測り方(`go test -cover` の文(statement)単位)で測ります。コマンドの入口などの配線部分も、外のプログラム(`git`、`gh`、`cdk`、Node.js、Python)を呼ぶ部分も、計測の対象から外しません。外のプログラムの呼び出しは差し替えてテストします。
- マージの前に、プルリクエストの CI でテストを実行します。
- AWS を呼ぶ部分の単体テストでは、AWS の呼び出しを差し替え、AWS の認証情報なしで CI で実行します。実際のアカウントを使う結合テストは、手元だけで実行します。CI から実際の AWS アカウントは呼びません。`cdk synth` には AWS の認証情報を渡さず、テストには AWS を呼ばない CDK のアプリだけを使います。
- GitHub については、CI でも実際の GitHub にプルリクエストを作る結合テストを実行します。テスト専用のリポジトリを1つ用意し、そこにだけ書ける fine-grained トークンを CI の secret に置きます。secret の無い実行(fork からのプルリクエスト、Dependabot のプルリクエストなど)では、このテストを飛ばします。テストで作ったブランチとプルリクエストは、テストのあとで閉じて消します。
- CI のテストは、Linux、macOS、Windows の3つの OS と、Go の `stable` と `oldstable` の2つの版で、配るバイナリと同じ `CGO_ENABLED=0` で実行します。Linux では `-race` 付きでも実行します。
- `cdk synth` を動かすテストも、CI の3つの OS すべてで実行します。そのために、CI に Node.js、Python、CDK の CLI を入れます。
- `cdk synth` を動かすテストで Node.js、Python、CDK の CLI が見つからないとき、CI ではテストを失敗にします(飛ばして通すことはしません)。手元では、理由を出してテストを飛ばします。
- テストのデータとして置く CDK のアプリ(TypeScript と Python)の依存(npm と pip のパッケージ、CDK の CLI)は、版を固定し、Dependabot で更新します。
- テストの量と種類は、ワークフローのテスト戦略(Test Strategy)で決まります。上の下限は、それに加わる条件です。下限を下げて Build and Test を通すことはしません。

## Deployment

このツールは利用者が自分の端末で動かす CLI で、サーバーには配置しません。リリースは次のように進めます。

- `main` に取り込むたびに、CI が確認用のバイナリを、公開と同じ6つの OS と CPU の組み合わせ(linux/amd64、linux/arm64、darwin/amd64、darwin/arm64、windows/amd64、windows/arm64)でビルドし、7日だけ残します。このバイナリは公開しません。
- 公開するのは、人が `main` にあるコミットに `vX.Y.Z` のタグを付けて push したときだけです。タグを付ける操作が、公開に対する人の承認にあたります。`main` に取り込むたびに自動で公開することはしません。
- タグの push で公開のワークフロー(`.github/workflows/release.yml`)が動きます。テストと `govulncheck` のあと、6つの OS と CPU の組み合わせのバイナリを `CGO_ENABLED=0`、`-trimpath` でビルドし、ライセンスの文と一緒にアーカイブにし、3つの OS で動くことを確かめてから GitHub Releases に載せます。タグが `main` にない、Go の版が決めた下限より古い、バイナリの版(`--version`)がタグと違う、のどれかにあたるときは公開しません。
- 配り方は、GitHub Releases(OS ごとのバイナリ)と `go install` の2つです。
- 配るバイナリには、SHA-256 のチェックサムを付けます。署名とビルドの来歴の証明は付けません。
- 最初の公開 `v0.1.0`(第1弾)は 2026-11-07 に出しました。次の公開は `v0.2.0` で、`iac` の CDK(TypeScript と Python)の反映と、プルリクエストの作成の2つがそろったときに出します。片方だけでは公開しません。

## Code Style

私たちは、リポジトリのルートに置く設定ファイルに従います。

- 整形には `gofmt` だけを使います。`goimports` や `gofumpt` は使いません。
- lint には `golangci-lint` を使い、既定の linter だけを有効にします(設定ファイルは置かず、版は CI で固定します)。CI でマージの前に実行し、失敗したらマージしません。
- `.gitattributes` で、Go のファイルを含むすべてのテキストのファイルの改行コードを LF に固定します。ファジングの種はバイトのまま扱います。
- 依存ライブラリの既知の脆弱性を、CI で `govulncheck` を使って確かめます(プルリクエストごとと毎週)。依存ライブラリと GitHub Actions のアクションの更新には Dependabot を使います。
- Go の依存ライブラリは、必要なら足してよいことにします。足すときは、ライセンス(配るアーカイブの `THIRD_PARTY_NOTICES.txt` に載せられること)と `govulncheck` を確かめます。
- GitHub Actions のアクションは、コミットのハッシュで固定します。
- テストのデータとして置く CDK のアプリ(TypeScript と Python)は、いろいろな書き方をそのまま試すために、整形も lint もしません。
- tag-refactor 自身が TypeScript や Python の補助のプログラムを持つ場合は、その整形を CI で確かめます(TypeScript は Prettier、Python は Black)。
- 名前の付け方は Go の慣習に従います。プロジェクト独自の名前の規則は、チームで決めない限り設けません。
- AI のエージェントがコードの書き方を提案するときは、先にプロジェクトの lint の設定を読み、lint で扱っていない点についてだけ提案します。

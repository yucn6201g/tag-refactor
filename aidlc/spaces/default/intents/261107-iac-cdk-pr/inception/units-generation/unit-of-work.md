## U1: 最小の一本(u1-walking-skeleton)

- 説明: CDK の反映とプルリクエストの作成の2つを、端から端まで細く通す最初の単位です(UG-Q2、チームの進め方の Walking Skeleton)。
- 責任:
  - `iac` に `--pr` と、CDK のアプリの発見(`cdk.json` を1つ)を足す
  - TypeScript の CDK アプリ1つで `cdk synth` を実行する(AWS と GitHub の認証情報を渡さない、時間の上限、一時的な出力先)
  - synth の出力からリソースとコンストラクトのパスを読み、TypeScript の補助のプログラムで、`Tags.of(x).add('キー', '値')` の文字列のタグの箇所と作成の箇所を見つける
  - キーの名前の変更を1つ、今の反映の仕組み(範囲の書き換え、読み直し、差分、置き換え)で反映する
  - `--pr` で、最低限の確かめ(gh があってログイン済み、リモートが GitHub、HEAD がブランチ)のあと、ブランチ、コミット、push、`gh pr create` を行い、URL を出す
  - CI の準備: 3つの OS に Node.js、Python、CDK の CLI を入れる。テスト専用のリポジトリの secret を使い、実際のプルリクエストを作る結合テストを足す(secret の無い実行では飛ばす)
- 含めないもの: 残りの確かめと途中の失敗(U2)、複数のアプリと絞り込みと失敗の扱い(U3)、ほかの書き方と変更の種類(U4)、Python(U5)、手で直す一覧の CDK の理由(U6)
- 実装の注意:
  - 検証コマンドは、検証用の AWS アカウントで `plan` を作るところから通す(チームの進め方)。最小の CDK アプリを検証用のアカウントに置く方法と片付け方は、この単位の設計で決める
  - 補助のプログラムを埋め込む形と、そのライセンスの表示の扱いを、この単位で決める(ADR-003)
  - CDK のアプリが無いときの `iac` の振る舞いを変えない(NFR5)

## U2: プルリクエストの作成(残り)(u2-pull-request)

- 説明: U1 の `--pr` を、要件のとおりに仕上げます。
- 責任:
  - 書き換えの前の確かめのすべて(リモートの決め方、行き先のブランチがリモートにあるか、同じ名前のブランチ、`--dir` が git の作業ツリーか、入力の誤り)
  - `--pr-branch`、`--pr-title`、`--pr-body-file` と既定の値
  - コミットに書き換えたファイルだけを入れること、フックと署名を利用者の設定のままにすること
  - 途中の失敗のときの「どこまで済んだか」と続きの命令
  - プルリクエストの本文(変更したファイル、手で直す一覧、`--lang`、ARN を載せない)
  - 変えるものが無いとき、手で直すものだけが残るときの扱いと終了コード
  - git と gh の呼び出しの時間の上限、トークンを出さないこと
- 実装の注意: CDK の有無によらず、Terraform と CloudFormation の書き換えでも使えるようにする(FR1.2)

## U3: CDK の synth と対応づけ(残り)(u3-cdk-synth)

- 説明: U1 の synth と対応づけを、要件のとおりに仕上げます。
- 責任:
  - 複数のアプリの発見、`--cdk-app` での絞り込み、`node_modules` などを見ないこと
  - `--synth-timeout`、一時的な出力先の後片付け(中断のときも)
  - CDK v1 のアプリを外すこと、道具が無いときの失敗、AWS が要るアプリの失敗
  - 一部のアプリが失敗したときに、ほかを続けること
  - 変更案のリソースを CDK のものと決める規則(失敗したアプリのリソースの扱いを含む)
  - 作成の箇所が決まらないときに、作成の記録を出す設定で synth し直して補うこと(ADR-004)
  - 進み具合の表示(端末と、端末でないとき)
- 実装の注意: 認証情報の遮断は、環境変数のほか、設定の読み込み経路も止める方法を設計で決める(ドメインの設計のレビューの指摘 R-02)

## U4: TypeScript への反映(u4-cdk-typescript)

- 説明: TypeScript の CDK のソースへの反映を、要件のとおりに仕上げます。
- 責任:
  - 必ず自動にする4つの書き方(文字列そのまま、同じファイルの定数、同じファイルの辞書を回す、別のファイルからの引数)と、必ず扱う形(`Tags.of(x).add` / `remove`、スタックの `tags`)
  - 4種類の変更(キーの名前、値、追加、削除)
  - スコープに付けたタグは、変更案がそのスコープのすべてのリソースを同じように変えるときだけ書き換えること
  - 反映済みの数え方、範囲だけの書き換え、読み直し、`aws:` のキー
- 実装の注意: 書き換え後の内容を、ディスクに書く前に補助のプログラムで読み直せる形にする(ドメインの設計のレビューの指摘 R-03)

## U5: Python への反映(u5-cdk-python)

- 説明: Python の CDK のソースへの反映を、U4 と同じ範囲で仕上げます。
- 責任: U4 と同じ(Python の補助のプログラムと Python の書き方)
- 実装の注意: Python の引用符(`'`、`"`)と、辞書と引数の書き方の違いに合わせる

## U6: 反映できないものの一覧とその他の書き方(u6-cdk-manual)

- 説明: 自動で反映できない CDK のタグを、理由つきで示し、必ず自動にする形の外の書き方もできるだけ反映します。
- 責任:
  - 手で直す一覧の CDK の理由(値が式、スコープ全体のタグ、ほかのリソースと共有、synth の失敗、対応が取れない、CDK v1、対応していない書き方)と、英語と日本語の文
  - L1 のコンストラクトの `tags` のプロパティなど、必ず扱う形の外の書き方を、できるだけ自動で反映すること。できないものは黙って飛ばさず一覧に出すこと
- 実装の注意: 「できるだけ」の範囲は、この単位の設計で、代表的な形について期待する結果を1つに決める(ユーザーストーリーのレビューの指摘 R-03)

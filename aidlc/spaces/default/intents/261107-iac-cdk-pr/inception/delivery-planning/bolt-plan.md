# Bolt の計画: iac への CDK の反映とプルリクエストの作成

この文書は、Construction で作業の単位(U1〜U6)をどの順番で作るかを決めます。Bolt は、1つ以上の単位を設計からコードまで通し、動くものができたところで終わる1回の作業です。この作業では1つの単位を1つの Bolt にします(DP-Q3)。単位の中身は `inception/units-generation/unit-of-work.md`、依存は `unit-of-work-dependency.md`、ストーリーとの対応は `unit-of-work-story-map.md` です。出典の DP-Q… は、このステージの `delivery-planning-questions.md` の回答です。

## 進め方の前提

- 作る順番は U1 → U2 → U3 → U4 → U5 → U6 です(DP-Q1)。依存の図(DAG)の並びに沿っており、図に反する並びはありません。
- 1つずつ順に作ります(DP-Q4)。AI-DLC の設定は unit-major、serial のままです。unit-major は、1つの単位について設計の段階から Code Generation までを通してから次の単位に移る進め方です。serial は、単位を同時に作らない進め方です。
- Bolt ごとに、GitHub の最新の `main` からブランチを作ります。プルリクエストで `main` に squash マージし、`main` の1つのコミットにします(チームの進め方、DP-Q3)。AI-DLC の記録(`aidlc/` の下)も、同じプルリクエストに入れます。
- push とプルリクエストの作成は、人に頼まれたときだけ行います。マージは人が squash で行います。
- 最初の B1 は、最小の一本(walking skeleton)です。最小の一本は、端から端まで細く通す最初の一本のことです。B1 の検証と人の承認が済むまで、後の Bolt には進みません(チームの進め方)。
- `v0.2.0` は、6つの Bolt がすべて `main` に入ったあとに、人がタグを付けて出します。片方の機能だけでは出しません(チームの進め方)。

## すべての Bolt に共通の「済んだ」の条件

- プルリクエストの CI(必須のチェック `ci-gate`)が通る。3つの OS と Go の `stable`、`oldstable`、`CGO_ENABLED=0` で動き、Linux では `-race` 付きでも動く。
- Go の文(statement)単位のカバレッジが 80% 以上である。外のプログラム(`git`、`gh`、`cdk`、Node.js、Python)の呼び出しは差し替えてテストし、計測から外さない。
- 受け入れ条件(Given/When/Then)を先に自動テストにし、実装のあとで細かい単体テストを書く(チームのテストの進め方)。
- `gofmt`、`golangci-lint`、`govulncheck` が通る。補助のプログラムを持つ Bolt では、Prettier(TypeScript)と Black(Python)の整形の確かめも通る。
- 利用者が触る契約(X1 のオプションと終了コード、X2 のプルリクエストの本文)を変えた Bolt では、README の `iac` の節を同じプルリクエストで直す。
- CI から実際の AWS を呼ばない。`cdk synth` に AWS の認証情報を渡さない。
- その Bolt の単位の設計と Code Generation が人の承認を得ている。

## B1: 最小の一本(U1)

- 中身: `iac --pr` と、CDK のアプリの発見(`cdk.json` を1つ)を足します。TypeScript の CDK アプリ1つを、認証情報を遮断して `cdk synth` します。TypeScript の補助のプログラムで `Tags.of(x).add('キー', '値')` の文字列のタグを見つけ、キーの名前の変更を1つ反映します。テスト専用のリポジトリに、ブランチ、コミット、push、`gh pr create` でプルリクエストを作ります。
- 確かめる部分: CLI の入口(`IacCommand`)、`cdk synth`(`CdkSynthesizer`)、補助のプログラムの JSON(`CdkSourceAnalyzer`、契約 C4)、範囲の書き換え(`IacWriter`)、`git` と `gh`(`PullRequestPublisher`)、表示(`IacDisplay`)のすべてを1本で通します。
- CI の準備も含みます。3つの OS への Node.js、Python、CDK の CLI の導入、テスト用の CDK アプリの依存の版の固定と Dependabot、テスト専用のリポジトリのトークンの secret、実際の GitHub にプルリクエストを作る結合テスト(secret の無い実行では飛ばす)です。
- 「済んだ」の条件(共通の条件に加えて):
  - 認証情報の遮断(契約 C5)を、差し替えた実行の口のテストで確かめる。3つの OS の CI で、実際の `cdk synth` が通る(DP-Q6)。
  - CDK のアプリが無いときの `iac` の出力と終了コードが変わらない(NFR5)。
  - 人が承認した Construction の検証コマンドで、端から端まで動くことを確かめ、人の最小の一本のチェックポイントの承認を得る。
- 確かめたいこと(confidence hypothesis): 認証情報を渡さない `cdk synth` が3つの OS で動き、synth の結果から TypeScript のソースの1か所を正しく書き換え、テスト専用のリポジトリにプルリクエストを作れること。
- 見せるもの(demo): 検証用の AWS アカウントから `plan` で作った変更案で `iac --pr` を動かし、テスト専用のリポジトリにキー名の変更のプルリクエストができ、その差分が TypeScript の1行だけであること。
- 前に要るもの: external-dependency-map.md の E1(テスト専用のリポジトリとトークン)と E2(検証用のアカウントの最小の CDK アプリ)。U1 の Code Generation の前までにそろえます(DP-Q5)。
- 検証コマンド: 検証コマンドは U1 の Code Generation で作るので、ここではまだ決めません。U1 の検証の前に、人に承認を求めます。

## B2: プルリクエストの作成の残り(U2)

- 中身: 書き換えの前の確かめのすべて、`--pr-branch`、`--pr-title`、`--pr-body-file`、書き換えたファイルだけのコミット(`git commit --only`)、途中の失敗と続きの命令、本文(固定の文と伏せ字、契約 X2)、変えるものが無いとき、時間の上限です。
- 「済んだ」の条件: US1.1 の受け入れ条件(11個)が自動テストで通る。本文に ARN、アカウント ID、トークン、外のプログラムの出力が出ないことを、受け入れテストで確かめる。Terraform と CloudFormation の書き換えでも `--pr` が使える(FR1.2)。
- 確かめたいこと: 途中で失敗しても利用者が続きを手で行え、手元の作業ツリーのほかの変更を巻き込まないこと。
- 見せるもの: push のあとにプルリクエストの作成を失敗させ、どこまで済んだかと続きの命令(PowerShell 用、sh 用)が示されること。

## B3: CDK の synth と対応づけの残り(U3)

- 中身: 複数のアプリの発見と `--cdk-app`、`--synth-timeout`、一時的な出力先の後片付け、CDK v1 と版が分からないアプリを外すこと、道具が無いときや AWS が要るときの失敗、一部のアプリの失敗、照合の規則(契約 C7 の `match_rule`)、作成の記録による補い(ADR-004)、進み具合の表示です。
- 「済んだ」の条件: US2.1 の受け入れ条件(7個)が自動テストで通る。環境を決めたスタックの S3 バケットと IAM ロールが正しく照合される(契約 C7 の `match_tests`)。
- 確かめたいこと: 1つのアプリが失敗しても、ほかのアプリの反映が続き、失敗したアプリのリソースが手で直す一覧に出ること。
- 見せるもの: 2つのアプリのうち1つが失敗する状態で、状態の行と手で直す一覧が出ること。

## B4: TypeScript への反映(U4)

- 中身: 必ず自動にする4つの書き方(文字列そのまま、同じファイルの定数、同じファイルの辞書を回す、別のファイルからの引数)、4種類の変更(キーの名前、値、追加、削除)、スコープに付けたタグの判断、書く前の読み直し(Recheck)です。
- 契約の設計で残した指摘(R-15〜R-17)を、この単位の設計で決めます。R-15 は今の `iac` の場合分けの引き継ぎ、R-16 は `Tags` の参照と import、R-17 は挿入の位置とコンマの扱いです。
- 「済んだ」の条件: US3.1 の受け入れ条件(5個)が通る。書き換えたあとの `cdk synth` の結果が変更後のタグになる(AC3.1.1)。
- 確かめたいこと: よくある書き方の TypeScript のソースが、余計な行を変えずに正しく書き換わること。
- 見せるもの: 4つの書き方を含むテスト用のアプリで、4種類の変更が反映され、synth し直した結果が変更案と同じになること。

## B5: Python への反映(U5)

- 中身: U4 と同じ範囲を Python で行います(標準の `ast` を使う補助のプログラム)。R-15〜R-17 は、U4 で決めた形を Python に合わせます。
- 「済んだ」の条件: US3.2 の受け入れ条件(5個)が通る。書き換えたあとの `cdk synth` の結果が変更後のタグになる(AC3.2.1)。
- 確かめたいこと: Python の引用符と、辞書と引数の書き方の違いがあっても、TypeScript と同じ結果になること。
- 見せるもの: B4 と同じ変更案を、Python のテスト用のアプリに反映できること。

## B6: 反映できないものの一覧とその他の書き方(U6)

- 中身: 手で直す一覧の CDK の理由(英語と日本語の文)、L1 のコンストラクトの `tags` などの、必ず扱う形の外の書き方です。
- 「済んだ」の条件: US4.1 の受け入れ条件が通る。代表的な形ごとに期待する結果を1つに決め、テストで固定する(ユーザーストーリーのレビューの指摘 R-03)。
- 確かめたいこと: 自動で反映できないタグが、黙って飛ばされずに理由つきで示されること。
- 見せるもの: 値が式のタグや共有された定数のタグが、理由つきで一覧に出ること。
- この Bolt が `main` に入ると、`v0.2.0` を出す条件がそろいます。

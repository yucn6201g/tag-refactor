# ユーザーストーリーの要否の判断: iac への CDK の反映とプルリクエストの作成

## 判断

**作る(Execute)**

## 理由

- 利用者が直接使う機能の追加です。`iac` に `--pr` と CDK の反映が加わり、端末の表示、終了コード、プルリクエストの本文が変わります(`requirements.md` の FR1〜FR3、`wireframes.md`)。
- 業務の規則が多く、受け入れ条件で合否をはっきりさせる必要があります。必ず自動にする書き方、手で直す一覧に出す条件、プルリクエストの途中の失敗、終了コードの決まりなどです(`requirements.md` の FR1.5、FR1.12、FR1.13、FR3.3〜FR3.5)。
- チームの進め方では、受け入れ条件(Given/When/Then)を先に自動テストにします(`team-practices.md` の Testing Posture)。ストーリーの受け入れ条件が、そのままテストの元になります。

## 考えた点

| 観点 | 内容 |
|---|---|
| 種類 | 既存のコマンドの機能の追加(コードの記録 `business-overview.md`、`component-inventory.md` の `internal/iac`、`internal/cli`) |
| 利用者が触れる範囲 | 端末の表示、オプション、終了コード、GitHub のプルリクエスト |
| 複雑さ | 標準。CDK の書き方の多様さと、外のプログラムの扱い |
| 利用者像 | P1(佐藤さん)だけ(意図の段階の Q2) |

## ストーリーが特に役に立つところ

- 必ず自動にする書き方と、その4種類の変更の受け入れ条件(US3.1、US3.2)
- プルリクエストの前の確かめと、途中の失敗の扱い(US1.1)
- 手で直す一覧に出す条件と理由(US4.1)

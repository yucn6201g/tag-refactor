## 1. 意図の分析

### 目的

CDK で作ったリソースのタグを `apply` で変えても、CDK のソースが古いままだと、次の `cdk deploy` で元に戻ります。また、`iac --write` のあと、プルリクエストを出すまでの手作業(ブランチ、コミット、push、作成)が手間です(意図 §Problem Statement)。この版では、`iac` が CDK のソース(TypeScript と Python)も同じ変更にそろえ、書き換えを1回の実行で GitHub のプルリクエストにできるようにします(範囲 §この版の目的)。

### 種類と規模

- 種類: 既存のコマンド `iac` の機能の追加(記録 §business-overview.md、§architecture.md の iac の流れ)
- 範囲: `iac` のコマンドと、その下の部品(`internal/iac`、`internal/cli`、記録 §code-structure.md)。新しく、外のプログラム(`cdk`、Node.js、Python、`git` の書き込みの操作、`gh`)を呼ぶ
- 複雑さ: 標準。CDK のソースの書き方の多様さ(R1)と、外のプログラムの扱いが難しさの中心
- 詳しさ: Standard

### 完成の定義

`v0.2.0` は、次の2つがそろった時点で完成とします(範囲 §最小の範囲、C-O2)。

1. Terraform、CloudFormation、CDK の書き換えを、1回の実行でプルリクエストにできる(FR1)
2. TypeScript と Python の CDK のソースで、必ず自動にする4つの書き方について、4種類の変更を反映できる(FR2、FR3)

意図の成功の基準(前 AC7.2.1 と前 AC7.3.1 を自動テストで満たす)は、FR3 と FR1 の受け入れ条件で満たします(意図 §Success Metrics)。

| FR1.9 | プルリクエストを作る前に確認は求めず、作ったあとで、ブランチ、コミット、push、プルリクエストの URL を1行ずつ示すこと | 実行すると問いは出ず、最後に URL が1行で表示される | M-Q4、画面3 |
| FR1.10 | プルリクエストの本文には、変更したファイル(IaC の種類つき)と「手で直す一覧」を載せること。タイトルと本文は `--lang` の言語で書くこと | `--lang ja` で、本文が日本語になり、手で直す一覧の行が載る | M-Q5、M-Q6、画面4 |
| FR1.11 | 変えるものが無いときは、ブランチもプルリクエストも作らず、「反映するものはありません」と示すこと | すでに反映済みの変更案で実行すると、プルリクエストは作られず、終了コードは 0 | R-Q5 |

| FR1.13 | 終了コードは、手で直すものが無ければ 0、手で直すものを本文に載せてプルリクエストを作ったときは 2、入力の誤りや確かめ、書き出し、ブランチ、コミット、push、作成の失敗は 1 とすること | 手で直すものが1件ある変更案で `--pr` を付けて実行すると、プルリクエストが作られ、終了コードは 2 | R-Q6、記録 §architecture.md の終了コード |

### FR2. CDK のアプリの見つけ方と `cdk synth`(IB-04)

出典: F-Q1、F-Q2、F-Q9、M-Q2、M-Q3、R-Q7〜R-Q10、C-T2〜C-T4

| ID | 要件 | 合否の基準 | 出典 |
|---|---|---|---|
| FR2.1 | `--dir` の下で `cdk.json` を探し、見つかったフォルダーを CDK のアプリとして扱うこと。新しいオプションで、対象のアプリを絞り込めること | `--dir` の下に2つのアプリがあると両方が対象になり、オプションで1つに絞ると1つだけが対象になる | M-Q2 |
| FR2.2 | CDK のアプリを探すときも、今の `iac` と同じく `.git`、`node_modules`、`cdk.out` の中と、シンボリックリンク、ジャンクションは見ないこと | `node_modules` の中の `cdk.json` は対象にならない | 記録 §architecture.md、洗い出し |
| FR2.3 | 各アプリについて、利用者の端末の CDK の CLI と Node.js(Python のアプリでは Python も)を使って `cdk synth` を実行し、リソースとソースの中の場所の対応を得ること | TypeScript と Python のテスト用のアプリで、リソースの論理 ID からソースのファイルと行が分かる | F-Q1、F-Q2、C-T2、C-T3 |
| FR2.4 | `cdk synth` には AWS の認証情報を渡さないこと。AWS を呼ばないと synth できないアプリ(保存されていない値を AWS から引くもの)は、そのアプリを失敗として扱い、理由と対処を示すこと | AWS から値を引く書き方で、値が保存されていないアプリは失敗になり、対処が表示される。AWS への呼び出しは起きない | F-Q9、C-T4 |
| FR2.5 | `cdk synth` には、アプリごとに時間の上限を置くこと(既定は 10 分、オプションで変えられる)。超えたら止めて、そのアプリを失敗として扱うこと | 上限を 1 秒にして実行すると、そのアプリは時間切れの失敗になる | R-Q8、R3 |
| FR2.6 | `cdk synth` の出力は一時的なフォルダーに置き、終わったら(失敗や中断のときも)消すこと。利用者の `cdk.out` は変えないこと | 実行の前後で、アプリの `cdk.out` の中身が変わらず、一時的なフォルダーも残らない | R-Q9 |
| FR2.7 | `cdk synth` の間、標準エラーに、アプリごとの状態(待ち、実行中、済み、失敗)と経過時間を文字で示すこと | 実行中に、アプリごとの状態の行が表示される | M-Q3、画面1 |
| FR2.8 | CDK の CLI、Node.js、Python のどれかが無いアプリは、そのアプリを失敗として扱い、無いものの名前と入れ方を示すこと | Python の無い環境で Python のアプリを対象にすると、Python が無いことが表示される | IB-04、R2 |
| FR2.9 | 一部のアプリだけが失敗したときは、失敗したアプリのリソースを理由つきで「手で直す一覧」に出し、ほかのアプリと Terraform、CloudFormation の処理は続けること。`--pr` でもプルリクエストを作ること | 2つのアプリのうち1つを失敗させると、もう1つのアプリの書き換えは行われ、終了コードは 2 | R-Q7 |
| FR2.10 | 対象は CDK v2 のアプリだけとし、v1 のアプリは理由を示して対象から外すこと | v1 のテスト用のアプリは、理由つきで「手で直す一覧」に出る | R-Q10 |
| FR2.11 | 変更案のリソースのうち `aws:cloudformation:stack-name` と `aws:cloudformation:logical-id` のタグがあるものは、synth の出力のスタックと論理 ID に照らして CDK のリソースかどうかを決めること。CDK のリソースは、synth の出力が持つ対応(コンストラクトのパスとソースの場所)から、書き換えるソースを決めること。対応が取れないものは「手で直す一覧」に出すこと | テスト用のアプリで作ったリソースの変更が、そのリソースを作ったソースの行に反映される。対応の情報が無いアプリでは、理由つきで一覧に出る | F-Q2、R5、記録 §architecture.md |

### FR3. CDK のソースへの反映(前 FR8.3、前 AC7.2.1)

出典: S-Q1、S-Q2、S-Q6、S-Q7、M-Q5、IB-05〜IB-07、IB-11

| ID | 要件 | 合否の基準 | 出典 |
|---|---|---|---|
| FR3.1 | TypeScript と Python の両方の CDK のソースに反映すること | TypeScript と Python のテスト用のアプリの両方で、変更が反映される | S-Q6 |
| FR3.2 | キーの名前の変更、値の変更、必須タグの追加、削除の4種類の変更を扱うこと | 4種類の変更を含む変更案で、それぞれがソースに反映される | S-Q2 |
| FR3.3 | 次の4つの書き方は、必ず自動で書き換えること。(1) タグのキーと値が文字列でそのまま書かれているもの(タグを付ける関数の呼び出しの引数、コンストラクトの `tags` のプロパティの中)、(2) 同じファイルの中で、文字列を入れただけの定数をキーや値に使っているもの、(3) 同じファイルの中の、文字列だけの辞書(オブジェクト)を回してタグを付けているもの、(4) 別のファイルから、スタックの引数として渡した文字列を値に使っているもの | 4つの書き方それぞれのテスト用のソースで、4種類の変更が反映される | S-Q7 |
| FR3.4 | 上の4つ以外の書き方も、できるだけ自動で書き換えること。書き換えられないものは、理由つきで「手で直す一覧」に出すこと | 値を計算で作る書き方は、「値が式」の理由で一覧に出る | S-Q1、IB-11 |
| FR3.5 | 書き換えると、変更案にないほかのリソースのタグも変わってしまう場合(同じ定数や同じ引数を、ほかのリソースも使っている)は書き換えず、理由つきで「手で直す一覧」に出すこと | 2つのスタックに同じ引数を渡しているとき、一方だけの変更は一覧に出る | 洗い出し(仮定 A4)、記録 §architecture.md(Terraform の `count`・`for_each` と同じ考え方) |
| FR3.6 | 今の `iac` と同じく、ソースの値が変更の前の値と同じときだけ書き換え、すでに変更の後の値なら「反映済み」に数えること。同じ変更案でもう一度動かしても差分は出ないこと | 書き換えたあとにもう一度実行すると、差分は出ず、反映済みに数えられる | 記録 §business-overview.md、§architecture.md |
| FR3.7 | 変えるのはキーと値の範囲だけで、コメント、ほかの行、インデント、改行の種類、引用符の種類は変えないこと。書き換えたあとのファイルをもう一度読み、意図した形でなければそのファイルは書き換えないこと | 書き換えの前後の差分が、変えたキーと値の範囲だけになる | 記録 §architecture.md |
| FR3.8 | `aws:` で始まるキーは、足さず、変えず、消さないこと | `aws:` で始まるキーの変更を含む変更案でも、そのキーは変わらない | 記録 §architecture.md |
| FR3.9 | 差分の形(変える行と前後3行)と、「手で直す一覧」の行(ファイル、行、リソース、理由)は、今の `iac` と同じ形で CDK のソースにも示すこと | CDK のソースの差分と一覧の行が、画面2の形で表示される | 画面2、記録 §architecture.md |

## 5. 仮定

| ID | 仮定 | 理由 |
|---|---|---|
| A1 | CDK を使う利用者の端末には、Node.js と CDK の CLI が入っている(Python のアプリなら Python も) [assumption] | 実現性の段階の前提(F-Q1、F-Q2)。無いときは FR2.8 で示す |
| A2 | テスト専用の GitHub のリポジトリとトークンは、人が用意する [assumption] | 実現性の段階の前提(Q10)。用意の時期は Open questions に残す |
| A3 | `--pr` のコミットには、`iac` が書き換えたファイルだけを入れる(FR1.8) [assumption] | 利用者のほかの作業中の変更を、知らないうちにプルリクエストに混ぜないため。利用者が別の振る舞いを望めば直す |
| A4 | 書き換えるとほかのリソースまで変わる場合は書き換えない(FR3.5) [assumption] | 変更案にない変更を IaC に入れないため。今の `iac` が Terraform の `count`・`for_each` を手で直す一覧に出すのと同じ考え方 |

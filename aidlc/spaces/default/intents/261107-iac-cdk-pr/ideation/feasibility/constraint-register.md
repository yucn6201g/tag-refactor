# 制約の一覧: iac への CDK の反映とプルリクエストの作成

出典の書き方は `feasibility-assessment.md` と同じです。意図の文書は `ideation/intent-capture/intent-statement.md` です。

## 技術的な制約

| ID | 制約 | 影響 | 出典 |
|---|---|---|---|
| C-T1 | 実装の言語は Go で、単一のバイナリで配る | Node.js や Python の解析の仕組みは、バイナリの中ではなく、外のプログラムとして呼ぶ | 前 C-T1、Q1 |
| C-T2 | CDK のソースを読むために、利用者の端末の Node.js(TypeScript)と Python(Python)を呼んでよい | それらが無い端末では CDK の反映はできない。無いことを分かるように示す必要がある | Q1 |
| C-T3 | CDK のリソースとソースの対応は、tag-refactor が `cdk synth` を実行して得る | 利用者の端末に CDK の CLI とアプリの依存が要る。利用者のアプリのコードが動く | Q2 |
| C-T4 | `cdk synth` に AWS の認証情報を渡さない。`iac` は今までどおり AWS の認証情報が要らない | AWS から値を引くアプリで、その値が保存されていないものは synth できない。止めて理由と対処を示す | Q9 |
| C-T5 | プルリクエストは利用者の `gh` を呼んで作り、push は利用者の `git` を使う。tag-refactor は GitHub のトークンに触れない | `gh` の無い端末ではプルリクエストを作れない。作成先は GitHub だけになる | Q3 |
| C-T6 | 認証情報を表示、記録、ログに出さない | `gh` や `git` や `cdk` の出力をそのまま出すときも、この条件を守る | 前 NFR8 |
| C-T7 | Go の依存ライブラリは、必要なら足してよい。ライセンスと脆弱性(`govulncheck`)を確かめ、更新は Dependabot で行う | 依存を足すたびにライセンスの確認が要る | Q6、規則 §Code Style |

## テストと CI の制約

| ID | 制約 | 影響 | 出典 |
|---|---|---|---|
| C-Q1 | CI から実際の AWS アカウントは呼ばない | `cdk synth` のテストは、AWS を呼ばないアプリで行う | 規則 §Testing Posture、Q9 |
| C-Q2 | CI でも、実際の GitHub にプルリクエストを作るテストを動かす。テスト専用のリポジトリと、そこにだけ書ける fine-grained トークンを CI の secret に置き、secret の無い実行では飛ばす | テスト専用のリポジトリとトークンの用意、テストのあとの片付けが要る | Q4、Q10 |
| C-Q3 | `cdk synth` を動かすテストは、CI の3つの OS(Linux、macOS、Windows)すべてで動かす | CI に Node.js、Python、CDK を入れる手順が要り、CI の時間が延びる | Q5、規則 §Testing Posture |
| C-Q4 | カバレッジの下限は80%(文の単位)で、受け入れ条件を先にテストにする | 外のプログラムを呼ぶ部分も、差し替えてテストする必要がある | 規則 §Testing Posture |

# RAID ログ: iac への CDK の反映とプルリクエストの作成

出典の書き方は `feasibility-assessment.md` と同じです。意図の文書は `ideation/intent-capture/intent-statement.md` です。

## Risks(危険)

| ID | 危険 | 起きやすさ | 影響 | 対処 | 出典 |
|---|---|---|---|---|---|
| R1 | CDK のタグの書き方が多様で、自動で書き換えられないものが多く残る | 高 | 中 | 書き換えられないものは理由つきで「手で直す一覧」に出す。自動の範囲は要件で決める | 評価 FR-1 |
| R2 | `cdk synth` に必要なものが利用者の端末にそろっていない | 中 | 中 | 足りないものを名前で示して止まる | 評価 FR-2 |
| R3 | `cdk synth` で利用者のアプリのコードが動き、時間がかかる、止まらない、ファイルを書く | 中 | 中 | 時間の上限を置き、出力は一時的なフォルダーに書かせる | 評価 FR-3 |
| R4 | AWS から値を引くアプリは、認証情報を渡さないので synth できない | 中 | 低 | 止めて理由と対処を示す | 評価 FR-4、Q9 |
| R5 | synth の出力に、リソースとソースの場所の対応が無いアプリがある | 低 | 中 | 対応が取れないものは「手で直す一覧」に出す | 評価 FR-5 |
| R6 | `gh` が無い、ログインしていない、版が古い | 中 | 低 | 足りないものと対処を示して止まる | 評価 FR-6 |
| R7 | CI で実際の GitHub を使うテストが不安定になる、テスト用のブランチやプルリクエストが残る | 中 | 低 | テストのあとで片付ける。secret の無い実行では飛ばす | 評価 FR-7、Q10 |
| R8 | 3つの OS で `cdk synth` のテストを動かすので、CI の時間が延び、Windows に特有の失敗が出る | 中 | 低 | CI の時間を測り、必要なら見直す | 評価 FR-8、Q5 |
| R9 | 同じリポジトリのほかの作業と変更が重なる | 中 | 低 | マージのときに直す | 評価 FR-9、Q8 |

## Assumptions(前提)

| ID | 前提 | 確かめ方 | 出典 |
|---|---|---|---|
| A1 | CDK を使う利用者の端末には、Node.js と CDK の CLI(Python のアプリなら Python も)が入っている [assumption] | 要件の分析で、無い場合の振る舞いとあわせて決める | Q1、Q2 |
| A2 | テスト専用の GitHub のリポジトリとトークンは、人が用意する [assumption] | CI の構成の段階で、人に用意を頼む | Q10 |

## 結論

**実現できる。ただし、利用者の端末と CI に外部のツールが増えることによる危険がある。**

意図の文書(`intent-statement.md`)の2つの問題、つまり CDK のタグが次の `cdk deploy` で元に戻ることと、プルリクエストを出すまでの手作業(意図 §Problem Statement)は、どちらも今の `iac` の外側に仕組みを足せば解けます。ただし、前の intent の `iac` は「tag-refactor のバイナリだけで動き、AWS の認証情報も要らない」ものでした。今回は利用者の端末の Node.js、Python、CDK、`gh` を呼ぶので(Q1、Q2、Q3)、それらが無い、版が違う、止まる、といった場合の扱いが、実現の成否を左右します。

## 機能ごとの実現性

| 機能 | 実現性 | 理由 | 出典 |
|---|---|---|---|
| CDK のソース(TypeScript と Python)の読み取り | 実現できる(中程度の危険) | 利用者の端末の Node.js と Python を呼んでよいので、それぞれの言語の解析の仕組みを使える。ただし、タグの付け方は CDK では多様で、すべてを自動で書き換えられるとは限らない | Q1、意図 §Initial Scope Signal |
| CDK のリソースとソースの対応づけ | 実現できる(中程度の危険) | tag-refactor が `cdk synth` を実行し、その出力からリソースとソースの中の場所の対応を得る。synth にはアプリの依存(npm や pip のパッケージ)が入っている必要がある | Q2 |
| AWS の認証情報なしでの synth | 実現できる(条件つき) | AWS から値を引く書き方を使い、その値が保存されていないアプリは synth できない。その場合は止めて理由と対処を示す | Q9 |
| GitHub のプルリクエストの作成 | 実現できる(低い危険) | 利用者の `gh` と `git` を呼ぶので、tag-refactor はトークンに触れない。前 NFR8(認証情報を表示、記録、ログに出さない)を守りやすい | Q3、前 NFR8 |
| CI での確かめ | 実現できる(中程度の危険) | 3つの OS で `cdk synth` を動かし、実際の GitHub にプルリクエストを作る。CI の時間と、外部のサービスによる不安定さが増える | Q4、Q5、Q10 |

## 技術的な危険の分析

| ID | 危険 | 起きやすさ | 影響 | 対処の方向 | 出典 |
|---|---|---|---|---|---|
| FR-1 | CDK のタグの書き方が多様(コンストラクトのプロパティ、タグを付ける関数の呼び出し、ループや条件の中など)で、自動で書き換えられないものが多く残る | 高 | 中 | 書き換えられないものは、今の `iac` と同じく「手で直す一覧」に理由つきで出す。どこまで自動にするかは要件で決める | Q1、意図 §Initial Scope Signal |
| FR-2 | `cdk synth` の実行に必要なもの(Node.js、CDK の CLI、アプリの依存、Python の仮想環境)が利用者の端末にそろっていない | 中 | 中 | 足りないものを名前で示して止まる | Q1、Q2 |
| FR-3 | `cdk synth` は利用者のアプリのコードを実行する。時間がかかる、止まらない、ファイルを書く、ことがある | 中 | 中 | 実行の時間に上限を置く。出力は一時的なフォルダーに書かせる | Q2 |
| FR-4 | AWS の認証情報を渡さないため、AWS から値を引くアプリは synth できない | 中 | 低 | 止めて理由と対処(値の保存など)を示す | Q9 |
| FR-5 | synth の出力に、リソースとソースの場所の対応が入っていない設定のアプリがある | 低 | 中 | 対応が取れないリソースは「手で直す一覧」に出す | Q2 |
| FR-6 | `gh` が入っていない、ログインしていない、版が古い | 中 | 低 | 足りないものと対処を示して止まる。ファイルの書き換えは済んでいる状態で止める | Q3 |
| FR-7 | CI で実際の GitHub を使うテストが、ネットワークや GitHub の都合で不安定になる。テスト用のブランチやプルリクエストが残る | 中 | 低 | テストのあとで閉じて消す。secret のない実行では飛ばす | Q4、Q10 |
| FR-8 | 3つの OS で Node.js、Python、CDK を入れるので、CI の時間が延び、Windows に特有の失敗が出る | 中 | 低 | CI の構成で時間を測り、必要なら見直す | Q5 |
| FR-9 | 同じリポジトリのほかの作業と、変更が重なる | 中 | 低 | マージのときに直す | Q8 |

## 未決のまま次に渡すこと

- どのタグの書き方まで自動で書き換えるか(FR-1)は、要件の分析で決める。意図の文書では、この版で作らないものは「特になし」になっている(意図 §Initial Scope Signal)。
- プルリクエストのブランチ名、コミットメッセージ、本文、作成先のリポジトリの決め方は、要件と設計で決める。

## Assumptions & Open Questions

- CDK を使う利用者の端末には、TypeScript のアプリなら Node.js と CDK の CLI が、Python のアプリなら Python と Node.js と CDK の CLI が入っている。[assumption]
- テスト専用の GitHub のリポジトリと、そのリポジトリにだけ書けるトークンは、人が用意する。[assumption]

## この版(`v0.2.0`)の目的

CDK で作ったリソースのタグが次の `cdk deploy` で元に戻らないように、CDK のソース(TypeScript と Python)を同じ変更にそろえられるようにします。あわせて、`iac` で書き換えた IaC の修正を、手作業なしで GitHub のプルリクエストとしてチームのレビューに出せるようにします(意図 §Problem Statement)。2つの機能がそろったら `v0.2.0` として公開し、タグを付けるのは人です(C-O2)。

## 範囲に入らないもの

| 項目 | 理由 | 出典 |
|---|---|---|
| GitHub 以外(GitLab など)へのプルリクエストやマージリクエスト | プルリクエストは利用者の `gh` で作るため | C-T5 |
| tag-refactor が GitHub のトークンを読むこと | `gh` と `git` の認証を使い、トークンに触れないため | C-T5 |
| `cdk synth` に AWS の認証情報を渡すこと | `iac` は今までどおり AWS の認証情報が要らないため | C-T4 |

意図の段階で、利用者は「この版で作らないもの」を「特になし」と答えています(意図 §Initial Scope Signal)。上の表は、その後の実現性の段階で決めた制約から出たものだけです。

## 最小の範囲(MVP の境界)

`v0.2.0` は、次の2つがそろった時点で完成とします(C-O2、S-Q6)。

1. Terraform、CloudFormation、CDK の書き換えを、1回の実行でプルリクエストにできる(S-Q3、S-Q4)
2. TypeScript と Python の CDK のソースで、必ず自動にする4つの書き方について、4種類の変更を反映できる(S-Q2、S-Q7)

意図の文書の成功の基準(AC7.2.1 と AC7.3.1 を自動テストで満たす)は、この2つで満たします(意図 §Success Metrics)。

## 進める順番

プルリクエストの作成を先に作り、CDK の反映をあとに作ります(S-Q5)。プルリクエストは今の Terraform と CloudFormation の書き換えでもすぐ使え、危険が小さいためです。CDK は、実現性の評価でいちばん大きい危険(R1、タグの書き方の多様さ)を持つので、プルリクエストの仕組みができたあとで取りかかります(実現性 §技術的な危険の分析)。
